## 1. `# allow:` 缺省是否改为默认拒绝

### 1.1 现状与冲突事实

- 基线口径：`dsl-spec-v0.1.md:55`「头部元数据在脚本开头，可选。缺省时继承内核默认策略。」、`:224`「`# allow:` 缺省时继承注册表级白名单。」。注意 `:205-214` 的"注册表级"只描述 `tool_registry_add`，**没有任何"默认可见集"的数据结构**——所以"默认拒绝"不是改一个常量，是新增一个概念。
- `:226`「`# deny:` 优先级高于 allow。」且全文**没有禁止只写 `# deny:`**。在继承语义下，`# deny: http_post, exec` 是"除了这两个都能用"；在默认拒绝下，同一份脚本变成"什么都不能用"，且**加载期无报错**——这是本条最大的隐性误伤，不是理论问题。
- `:510`「向后兼容是硬约束：新语法增量添加，旧脚本不写新语法照常跑。」`：511`「脚本可声明版本 `# dsl-version: 2`」，但 `docs/design/dsl-discussion.md:194`（P0-8）倾向 MVP 直接报错、不支持版本选择。

### 1.2 四个选项的成本（按性价比降序）

| 选项 | 改动落点 | 行数（含错误信息） | 误伤 | 更便宜？ |
| --- | --- | --- | --- | --- |
| A 维持继承（现状） | 无 | 0 | 无（安全面最大） | — |
| B 告警 + 审计日志（讨论稿 P1-8 倾向） | loader 出 warn 行 + 审计一条 | 15–25 | 无 | 是，但只买可观测，不买安全 |
| C 严格默认拒绝 | `ToolDef` 加 `default_exposed`（`:259-266` +1 行）、loader 构造空策略、错误信息 + hint、deny-only 报错 | 25–40 | ① LLM 漏 header → 加载失败多一次往返；② deny-only 脚本静默全拒（若不加校验）；③ 未来所有测试夹具/eval 脚本必须带 header | 否 |
| D 默认最小只读集 + 审计 | C + 注册表默认集 + 分级错误 | 40–60 | 只读脚本照跑，写脚本被拦 | 中 |

**最便宜的等效做法**：保持严格默认拒绝，把 header 的负担前移到**生成侧**——few-shot 模板与 eval 脚手架统一注入 `# allow:` 骨架，运行时零妥协。这样运行时只花 25–40 行，且不引入 D 的"读也是默认开放"的通道（在 M8 路径约束落地前，默认开放 `read` 本身就是泄露面，`dsl-spec-v0.1.md:243` 的路径前缀约束此时还不存在）。生成侧成本 ≈ 改几段 few-shot + 一个脚本模板，0 运行时行数。

### 1.3 §13 是否冲突

**文本层冲突成立，但可裁定为不冲突，条件是现在定。**

- §13 的硬约束字面只约束"新语法增量添加"；但"缺省策略"是脚本可观察的行为，改它等于让旧脚本"没写新语法却跑不起来"，与该句的**意图**相悖。
- §13 给的救济手段是 `dsl-version`（`:511`），而 P0-8 倾向 MVP 不支持版本选择——两者同时成立时，默认值一旦发布就无法再改而不违背 §13。
- 结论（成本席裁定建议）：不改 §13 措辞，改**时序**——默认值必须在"首个实现发布、存量脚本 > 0"之前定死；在 §13 补一句「安全默认值属于基线，不随增量语法演进」。这样默认拒绝与 §13 可同时成立。动作成本：规范 1 句。

### 1.4 测试怎么写

loader golden（每例一个脚本 + 期望 rc/错误码，约 10–15 行/例）：

- `311_deny_only_no_allow.error`：只写 `# deny:` → 必须报"`# allow:` 缺失"，**不得**静默变成空集（这条是补丁，不是可选）。

## 2. 白名单热更新：执行快照 vs 实时生效

### 2.1 成本

| 方案 | 改动落点 | 行数 | 隐性成本 |
| --- | --- | --- | --- |
| 实时生效 | 每次工具调用前查全局策略 + 读写锁 | 30–50 | 加载期 AST 校验与执行期参数校验会看到不同策略 → "加载时允许、运行时拒绝"的竞态分支，每个调用点多一条错误路径（+10 行）；撤销生效无延迟，但审计里同一次 `dsl_exec` 的权限前后不一致，事后无法复现 |
| 快照（P1-7，`dsl-discussion.md:299-306`） | `PolicySnapshot{const Policy*, uint64 gen}`、`dsl_exec` 增参、调用点读快照、热更新换指针 | 60–80 | 必须加"撤销延迟生效"说明 + 内核强杀开关（+15 行） |
| 快照 + 不可变策略 | 同上，但 `Policy` 本身 immutable，快照只持引用 | **40–60** | 无需逐字段拷贝/RCU 细节，release 时整份 free |

**更便宜的等效做法**：不可变 `Policy` + 指针交换。省掉快照深拷贝与细粒度锁，语义与 P1-7 完全一致，且天然满足 `dsl-spec-v0.1.md:512`「白名单配置热更新需人工审批或审计日志」——审计只需记 `policy_gen`，一行。

### 2.2 误伤

只有一种：撤销权限对长脚本不即时（最长 = 单次 `dsl_exec` 的 `timeout_ms`，`dsl-spec-v0.1.md:293`）。这是可量化的上界，不是缺陷。实时方案反而会误伤"同一次执行内策略抖动"导致的可重放性。

### 2.3 测试

- `320_snapshot_survives_swap.pass`：注入 fake tool，在其 handler 里触发策略替换，断言后续调用仍用旧 `policy_gen`。**单线程确定性**，约 40 行。
- `321_new_load_sees_new_policy.deny`：替换后再 `dsl_exec` 新脚本 → 拒绝。
- 不建议写并发测试：要可控时钟 + 线程同步，约 150 行且易 flaky，收益不抵。

### 2.4 回退

读快照改成读全局，约 10 行，删除引用计数。**但要先有快照才能回退到实时**，反向不成立——顺序上有不对称。

## 3. 审批放内核还是 DSL；边界是否写进规范

### 3.1 成本对比

| 方案 | 行数 | 说明 |
| --- | --- | --- |
| 审批在内核，DSL 只出元数据（P1-9，`dsl-discussion.md:317-324`） | `ToolDef` +1 字段（`dsl-spec-v0.1.md:259-266`）、`error_kind=approval_required` 枚举 +1、executor 分支 8–12 | 暂停/恢复完全在 `dsl_exec` 之外，DSL 无状态假设不破 |
| DSL 加 `approve` 语句 | 关键字 1 + 产生式 2 + AST 15 + 语义 **150–300** | 需求：执行中阻塞等待审批 → 解释器必须可暂停/可恢复/可序列化栈 → 与"单次执行、无跨轮状态"（`dsl-discussion.md:269-276`）直接冲突，会滚成 checkpoint/restore，**成本无上界** |
| 规范写"运行时边界"一节（P1-4） | 40–60 行 prose，0 实现 | 唯一作用：把"审批/主循环/记忆/压缩"挡在 DSL 文法外 |

### 3.2 误伤 / 测试 / 回退

- 误伤：无。唯一风险是 `requires_approval` 元数据被工具作者滥用导致调用大面积失败，靠"默认 false"控制。
- 测试：`330_requires_approval.error` 断言 `error_kind` 与工具未执行（handler 计数为 0），约 20 行。
- 回退：删字段与分支，约 10 行，无外部影响。
- **性价比最高的一条**：40–60 行文字就永久封死一个 150–300 行且语义不自洽的方向。

## 4. 参数级约束的强度

### 4.1 拆开算，别当成一件事

| 约束 | 诚实实现行数 | 打折实现行数 | 误伤 |
| --- | --- | --- | --- |
| 路径前缀 | 40–60（`realpath` + 前缀比对） | 0（只做字符串前缀） | 字符串前缀可被 `/workspace/../etc/passwd` 绕过，等于没做 |
| + TOCTOU 硬化 | **150–250**（`openat` + `O_NOFOLLOW` 逐级遍历） | — | workspace 为 symlink 挂载点的部署全部误杀；macOS 默认大小写不敏感，白名单行为与 Linux 不一致 |
| 命令字符串白名单 | 80–120 | — | 漏 `;`/`&&`/`$()`/env 前缀任一即 RCE；`git log --format='%s %h'` 这类合法参数被误杀 |
| argv[0] 白名单 + 禁 shell | **25–40** | — | 几乎无误伤；不拼 shell 就没有注入面 |
| payload 浅校验（type + required） | 40–60 | — | 低 |
| payload 完整 JSON Schema 子集 | 150–250 | — | `additionalProperties:false` 会打挂 LLM 常见的多余字段（`read "x" limit 10`），把可容忍变成重试 |
| 域名 / 数值范围 / 正则 | 各 15–30 | — | 低 |

### 4.2 关键判断

- **argv 白名单**：规范 `dsl-spec-v0.1.md:243` 写的是"命令白名单"，按字面最容易被实现成字符串黑名单——**贵且不安全**。换成"argv[0] 白名单 + 工具禁止拼 shell"，成本降一个数量级、安全性升一档。这是本条唯一"更便宜且更好"的选项。
- **realpath**：真正的安全收益要 TOCTOU 硬化才算数，成本 150–250 行且误伤面最大（symlink 挂载、大小写）。**只做 `realpath` + 前缀比对是"看起来安全"**：比不做贵 40–60 行，比做对便宜 100 行，但挡不住换链。规范要么主张硬化，要么明确"本期不主张"，**不能写 `realpath` 就宣称路径安全**。
- **payload schema**：浅校验够用；`additionalProperties:false` 的严格模式是负收益（增加 LLM 重试成本）。
- **单向门**：参数约束"只能放宽不能收紧"——发布后收紧会把历史合法调用变成拒绝，回退只有放宽一条路。所以这一条**最应该晚定、且先按最弱可主张写**。

### 4.3 测试

`340_path_traversal.deny`、`341_symlink_escape.deny`（这一条会把 4.2 的结论变成可执行判据）、`342_argv0_not_listed.deny`、`343_shell_meta_in_arg.deny`、`344_extra_field_tolerated.pass`。约 80–100 行夹具，其中 symlink 用例需要真实建链，是唯一有环境依赖的用例（建议标记为需要 POSIX 环境）。

## 5. 横向排序

**性价比（单位规范文本 + 单位实现行数买到的风险下降）**：

1. 争点 3 边界一节 —— 40–60 行文字封死 150–300 行的不自洽方向
2. 争点 2 快照 —— 40–60 行买到"加载/执行同一份策略"，且满足 `:512` 审计要求
3. 争点 1 默认拒绝 —— 25–40 行，且规范内 5 个示例全部带 header（`§8`），零示例迁移
4. 争点 4 参数硬化 —— 100–400 行，误伤最大，且只能放宽不能收紧

**必须现在定的紧急度**：争点 1 > 争点 2 > 争点 3 > 争点 4。争点 1、2 都属于"现在定成本≈0，发布后定成本含迁移与 §13 违约"的类型。

## 6. 一句话

**必须现在做的是争点 1 的默认值口径（严格默认拒绝 + `# deny:` 单独出现必须报错），实现仍留 M8；可以留到 M8 再谈的是争点 4 的参数级约束强度——现在规范只写"argv[0] 白名单 + 禁 shell + payload 浅校验"，realpath/TOCTOU 硬化与完整 JSON Schema 一律标本期不主张。**

## 我可能错在哪

1. **行数全是估的**：仓库无实现、无构建（`docs/spec/S-001-call-form.md:46`），我给的行数无法用 E1 复核，误差可能 ±50%。若有实现，真实数字可能推翻"争点 2 比争点 4 便宜"的排序。
2. **"存量脚本=0"是可失效前提**：只要有任一外部方按 v0.1 写了无 header 脚本，争点 1 从"现在最便宜"翻转为"现在最贵"，我的结论整条反转。
3. **我把 LLM 漏 header 的失败率当风险而非判据**：没有数据，我无法量化"多一次往返"的成本；若 M1 验收显示漏 header 率极高，严格默认拒绝的实际总成本会显著高于 25–40 行。
4. **我可能低估 argv 方案的误伤**：`argv[0]` 白名单对"通过包装脚本调用"（`sh -c`、`bash wrapper.sh`）的工具有系统性误杀，而这类工具在 agent 里很常见；禁 shell 与"能跑复杂命令"本身是对立需求。
5. **争点 3 我给"成本无上界"，这是判断不是计量**：如果实现方选择"审批期间不阻塞、直接返回 pending 由内核重跑"，DSL 侧成本可能只有几十行，我的排序会变。
6. **我假设策略快照可以用不可变引用实现**：若策略对象含可变的 constraint 版本号并被原地修改，40–60 行不成立，会回到 60–80 行。
