## 1. B2-1：`|?` vs `retry n { fallback: }` vs try/catch

### 1.1 四个方案的成本

| 方案 | lexer | parser | interp | 代码合计 | 测试增量 | 测试折行 | 文档返工 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **A0** 左右值都限定为单次调用，`|?` 比 `|>` 紧，`(a |? b) |> c` | 8（自估） | 10（自估） | 45（自估） | **63（自估）** | 10 用例 | ~80 | 0 行 |
| **A1** 讨论稿提案：`fallback_expr := pipe_expr ("|?" pipe_expr)*`，`|?` 比 `|>` 松，失败单元=左侧最后一次调用 | 8（自估） | 35（自估） | 90（自估） | **133（自估）** | 18 用例 | ~145 | 0 行 |
| **B** `retry n { fallback: }` | 10（自估） | 70（自估） | 180（自估） | **260（自估）**；引用量级 400 | 25 用例 | ~200 | 回滚 §2.3 + Q 清单，2 文件 |
| **C** try/catch | 10（自估） | 80（自估） | 220（自估） | **310（自估）** | 30 用例 | ~240 | 回滚 §9「明确不做 try/catch」，1 文件 + R4 重写 |

引用 400 与我拆出的 260 的差额主要是测试、文档、示例（约 140 行）。也就是说引用量级本身不矛盾，但它 **不含** 重试语义下沉后的工具侧成本，见 1.4。

### 1.2 方案排序（按代码+测试+文档的总代价）

**A0（~143）< A1（~278）< B（~460 + 文档回滚）< C（~550 + 文档回滚）**。A0 与 A1 的差全部来自"左值能不能是整条管道 / 失败单元是不是最后一次调用"——这两个语义选择值 70 行 + 8 个用例。

### 1.3 对示例脚本 token 的影响

计数口径：标识符、字符串、数字、运算符、标点各 1 token，空白不计。

| 写法 | token |
| --- | --- |
| `read "a" \|? read "b"` | 5 |
| `retry 3 { read "a" fallback: read "b" }` | 10 |
| `try { read "a" } catch e { read "b" }` | 11 |
| `(read "a" \|? read "b") \|> grep "x"` | 10 |
| `read "a" \|? read "b" \|> grep "x"` | 8 |

- v0.1 五个示例（[spec L355-L420](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L355-L420)）零处使用 `|?`，**token 影响 0**。
- 最小回退点 `|?` 比 retry 省 5 token、比 try/catch 省 6 token。
- **A1 的解析陷阱（代价，不是风格问题）**：按讨论稿文法 [dsl-discussion.md L416-L418](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L416-L418)，`read "a" |? read "b" |> grep "x"` 解析为 `read "a" |? (read "b" |> grep "x")`——右管道整段成为 fallback。要让回退结果继续走管道，必须写括号，**每个"回退后继续管道"点 +2 token**，且 LLM 极可能漏写。A0 把这个点消掉了：`|?` 落在 `|>` 内部，`(a |? b) |> c` 就是自然读法。

### 1.4 隐性成本（表里看不到的那部分）

1. **重试下沉**：用户已定"重试次数走工具参数"（[discussion L70-L78](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L70-L78)）。于是"重试 ≈400 行"没有消失，只是从 interp 搬进了工具库：每个需要重试的工具 +10~15 行（schema + 循环 + 退避）（自估），随工具数线性放大。选 A0 不等于总成本 63，而是 63 + N×12。
2. **`$` 顺序**：[discussion L231-L232](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L231-L232) 自认未定。若左右两侧的工具都 `accepts_context`，两侧都会追加 `$`，需要在 interp 里写死"两侧都追加"或"只右侧追加"，约 10 行 + 4 个用例。A0 因为右值也是单次调用，这个规则可以一句话写死；A1 右值是整条管道，要逐级决定，行数上去。
3. **副作用重放**：这是 B 的致命项。`retry` 会把 `write` 也重放，必须给工具加幂等元数据，否则重试一次写两次。B 的 260 行里不含这笔；加上后与 C 同档。A0 没有这个问题（fallback 是另一次调用，不重放左侧）。

### 1.5 返工风险

| 方案 | 触发条件 | 返工面 |
| --- | --- | --- |
| A0 | LLM 想把"整条左管道失败"当作回退条件 | 语义扩成 A1，+70 行 +8 用例 |
| A1 | 失败单元定义与直觉不符：`read |> grep |? cached` 在 grep 失败时回退并丢掉 read 结果 | 改语义即改 parser 层级 + interp + 全部 `|?` 用例 |
| B | 副作用重放 / 与用户已定的"不新增语句形态"冲突 | 回滚 2 份文档 + 全部实现 |
| C | 与 §9「MVP 不做 try/catch」（[spec L428](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L428)）直接冲突 | 同上，另加 R4 重写 |

### 1.6 E2 锚点

- 支持"`|?` 是唯一形态、成本最低"：[discussion L74-L78](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L74-L78)。
- 不利于"`|?` 很便宜"：[discussion L218-L232](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L218-L232) 自己承认优先级、失败单元、`$` 顺序三项全未定；以及 [discussion L416-L418](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L416-L418) 的产生式会把右侧管道吞进 fallback。

### 1.7 E4 回退步骤

A0 回退 = 删 1 个 token、1 层产生式、1 个 AST 节点、1 个 eval 分支，无数据结构变更，**1 个提交**。B/C 回退还要回滚 `dsl-discussion.md` §2.3/§9 与 Q 清单，**2 个文件**，且已写脚本不向后兼容（v0.1 §13 是硬约束，[spec L508-L512](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L508-L512)）。

## 2. B2-2：截断元数据暴露方式

### 2.1 成本表

| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **C** 伪字段 `r.truncated` / `meta r` | 0 | 10（自估） | 60（自估） | 15（自估） | **85（自估）** | 11 用例（~90） | 0 | 低中 |
| **B** 仅声明元数据的工具返回记录 | 0 | 0 | 65（自估） | 30（自估） | **95（自估）** | 14 用例（~110） | 0 | 中 |
| **A** 所有调用结果都是记录 | 0 | 0 | 55（自估） | 10（自估） | **55（自估）**，但见 2.3 | 20 用例（~160） | 5 个示例全改 | 高 |
| **D** 仅发生截断时返回记录 | 0 | 0 | 20（自估） | 0 | **20（自估）** | 8 用例，形状随数据变 | 0 | 最高 |
| **`limit N lines` 后缀**（已否） | 6（自估） | 35（自估） | 25 + 每工具 10~20（自估） | — | 66 + N×15（自估）；引用量级 300 | 10/工具 | — | 高 |

### 2.2 排序

只按代码：**D（20）< A（55）< `limit`（66+N×15）< C（85）< B（95）**。
按总代价（含测试、示例返工、可预测性）：**C（~175）< B（~205）< A（~215 起，见 2.3）< D（不可计价）**。
引用 300 对应的是"B 或 A 的整条链"（含工具侧 metadata 产出与文档），不是纯 DSL 三段；我的 B 只有 95，因为把工具侧单列了。

### 2.3 A 的真实代价不在 interp

A 只改 55 行，但记录会穿透三个现有语义点：

1. **管道传值**：`content |> grep` 传的是记录还是 `.value`？若传记录，每个 handler 都要改；若 interp 自动解包，`r.value` 就自相矛盾。
2. **`$`**：示例 2/5 的 `$.server.port`、`$.length` 都要变成 `$.value.server.port`（+2 token/处）。
3. **fn 返回**：示例 3 的 `find_issues` 返回 `matches`，若返回记录，`a + b` 直接算术失败（+2 token/操作数）。

逐点清点，示例 1/2/3/4/5 受影响使用点 ≥12 处（自估），每处 +2 token，另加一条"哪里自动解包"的新规则要写进规范。A 的账应记作 55 代码 + 12 处示例改动 + 1 条新语义规则，不是 55。

### 2.4 token 账

| 方案 | 现有示例 | 新脚本每个读取点 |
| --- | --- | --- |
| A | ≥12 处 +2 token（自估） | +2（`.value`） |
| B | 0（现有工具未声明 metadata） | +2（`.value`）+ 2（`.truncated`） |
| C | 0 | +2（`.truncated`），管道与 `$` 不变 |
| D | 0 | 无法静态预知写不写 `.value` |

### 2.5 返工风险

- **D 必返工**：行为随数据变化，LLM 无法从规范推出形状；测试也不稳定。代码最便宜，总代价最高。
- **C 的唯一硬点**：JSON 自带的 `truncated` 字段冲突（[discussion L65-L66](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L65-L66) 已列）。修法是"元数据优先 + 取 JSON 字段用 `r["truncated"]`"，代价是 +1 条规则、+3 用例，仍低于 A 的穿透成本。
- **B** 的规则局部，但"同一工具静态确定形状"要写进 ToolDef（+1 字段），且管道消费方仍需 unwrap 规则，风险中。
- **`limit N lines`**：与工具已有 `limit` 参数双重指定（[discussion L52-L61](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L52-L61) 用户已给出否决理由），每工具实现一遍后缀，成本随工具数放大；token 上还是加 4 token，没有节省。排序最后。
- **接口侧**：`DslResult` 目前只有 `value_json`（[spec L272-L278](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L272-L278)），任何"把 metadata 带出执行"的方案都要扩接口 +5~10 行，且内核读方要同步改。这笔不在 DSL 三段里。

### 2.6 E2 锚点

- 支持 C 最省："DSL 层只规定通用结果元数据、字段访问必须能读到 `truncated`"（[discussion L57-L59](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L57-L59)）——伪字段正好满足，且不动管道与 `$`。
- 不利于 C："普通值/JSON 对象本身有 `truncated` 字段时如何避免冲突"（[discussion L65-L66](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L65-L66)）是 C 独有的成本。

### 2.7 E4 回退步骤

四个方案都在 interp 内，回退 = 删字段解析分支 + 删静态检查，1 个提交；无 lexer/parser 变更（`limit` 除外，需删 2 个上下文关键字与 1 层后缀，1 个提交）。示例改动只在 A 下发生，回退时要还原 5 个示例。

## 3. B2-3：`while` / `break` / `continue` + `x = expr`

### 3.1 切片成本

| 切片 | lexer | parser | interp | 语义检查 | 合计 | 测试 | 引用 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 赋值 `x = expr` | 0 | 25（自估） | 55（自估） | 15（自估） | **95（自估）** | 10 用例（~80） | — |
| `break` / `continue` | 10（自估） | 20（自估） | 45（自估） | 15（自估） | **90（自估）** | 6 用例（~50） | — |
| `while` | 5（自估） | 20（自估） | 55（自估） | 10（自估） | **90（自估）** | 7 用例（~55） | — |
| **整包** | 15（自估） | 65（自估） | 155（自估） | 40（自估） | **275（自估）** | 23 用例（~185） | 引用 300 |

整包 275 与引用 300 基本吻合；差额在文档与 `ExecLimits` 计数口径。这组是四项里估算最可信的——控制流信号是成熟套路，没有语义新发明。

### 3.2 排序与"能不能拆"

- 按代码：赋值 95 < break/continue 90 < while 90（几乎持平）。
- **但拆开做会产生一个死中间态**：赋值单独上，线性脚本里没有消费者（想改值直接重写 `let`）；`while` 单独上则改不了条件变量。讨论稿自己也承认这点（[discussion L242-L243](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L242-L243)）。所以真正的选择只有两个：**整包 275** 或 **只做 `break`/`continue` 90**（它单独对现有 `for` 有价值）。
- 强行拆三段的总成本 275 不变，还多两次提交与两次文档同步。

### 3.3 token 账

- 现有五个示例：0 影响（无一处需要 `while` 或赋值）。
- 新循环：`while` 关键字 + 条件 + 块，最小开销约 4 token/循环；相比"无法表达"是从 0 到 1，不是压缩。
- `x = expr` 比 `let x = expr` 省 1 token，但只在循环体内有意义。

### 3.4 返工风险

- **低-中**。主要风险不是行数，是三个边界：
  1. `break` 在 `fn` 内、`fn` 在循环内 → 必须静态禁止跨函数 `break`，否则运行时要穿两层栈。+15 行检查 +2 用例。
  2. `while` 与 `ExecLimits.max_steps` 的计数口径（每次迭代算几步）不写死，超限行为不可测。[spec L284-L295](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L284-L295) 现有字段没有"每迭代步数"定义。
  3. `x = 1` 与 `x == 1` 的笔误：`=` 不报错、静默赋值，是 LLM 高频错误，需要"赋值结果不可作表达式"的规则（+1 条）。
- 引用 300 不含上述 1、2 两条的新增，我的 275 已含部分。

### 3.5 E2 锚点

- 支持"可以推后"：v0.1 示例 1–5 全部是线性 + `if` + `for` + `into`（[spec L355-L420](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L355-L420)），零处需要 `while`。
- 不利于"推后"：评审已把该条列进 M4（[discussion L240-L247](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L240-L247)），且 M4 预算 800 行（[spec L494](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L494)）本已为控制流留了额度，推后不省预算、只挪排期。

### 3.6 E4 回退步骤

整包回退 = 删 3 个产生式、3 个关键字、1 个信号枚举与 2 个循环分支，无数据结构变更，1 个提交；但已写脚本会失效，需 v0.1 §13 的兼容口径（[spec L508-L512](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L508-L512)）。这也是"要么现在做、要么明确不做"比"先做一半"便宜的原因。

## 4. B2-4：R4 错误传播表述要不要改

### 4.1 现状是硬矛盾，不是措辞偏好

- R4：失败"中止当前 block 并向上传播……MVP 不做 try/catch"（[spec L152-L154](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L152-L154)）。
- `|?`：左侧调用失败则尝试右侧（[discussion L75-L76](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L75-L76)）。

后者就是表达式级捕获。两句并存，规范自相矛盾，必须改一句。所以本条不是"要不要改"，是"改多少"。

### 4.2 成本表

| 方案 | 文档 | lexer | parser | interp | 测试 | 引用 |
| --- | --- | --- | --- | --- | --- | --- |
| **R4-0** 不改 | 0 | 0 | 0 | 0 | 0 | — |
| **R4-1** 措辞补丁：R4 = 默认传播；`|?` 是唯一表达式级捕获；写死中止粒度（表达式/语句/块/脚本）与"哪些错误可捕获" | 12~15 行 | 0 | 0 | 0 | 0~2 用例 | — |
| **R4-2** R4-1 + `error_kind` 可捕获标记 | 5 行 | 0 | 0 | 40（自估） | 8 用例（~65） | — |
| **R4-3** R4-2 + 全量错误升级（did-you-mean/片段/插入符） | 20 行 | 0 | 0 | 50（自估） | 15 用例 | 引用 ~200 |

### 4.3 排序

### 4.4 R4-2 那 40 行的真实动因是安全，不是美观

如果 `|?` 能捕获**白名单拒绝**（[spec L243](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L243)）或 `ExecLimits` 超限，脚本就能用"降级到另一个工具"绕过 deny 意图。因此必须把错误分成"工具业务失败（可捕获）"与"策略/预算失败（不可捕获）"，这就是 40 行的实际内容。R4-1 只写文档不做标记时，实现者一定会在第一版里捕错；但那是实现期的事，不影响现在只改措辞。

## 6. 如果这组只能先做两件

做 **B2-1（A0 口径）** 与 **B2-2（C 方案）**；**B2-4 的措辞补丁作为 B2-1 的同提交附带项，不占名额**——它是 B2-1 的前置，边际成本约 15 行文档，单独排期反而更贵。

理由只有三句：

1. B2-1 已被用户定为唯一降级形态，重开 retry/try-catch 的代价是 2~3 倍代码加 2 份文档回滚；而 A0 是全组里唯一"用户已定 + 63 行 + 消掉右管道吞并陷阱"的方案。
2. B2-2 是 M2 范围，决定每个工具结果的形状；拖到实现中期再定，就要改所有 handler 与全部示例（A 方案 ≥12 处使用点），是所有项目里返工面最大的一笔。
3. B2-3 推后不省预算（M4 800 行本已预留），但 v0.1 五个示例零处需要 `while`；先做它等于在无人使用的语法上花 275 行。

## 7. 我可能错在哪

- **引用量级的宿主不匹配**：Trae 评测的 300/400/300/200 很可能来自 JS/TS。CT 无运行时错误类型（[discussion §5](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L360-L361)），我这边的 interp 自估可能整体偏低 20~30%，尤其 B2-1 的 A1 与 B2-4 的 R4-2。
- **parser 行数对风格敏感**：若照 CT `Expr.h.ct` 那种显式节点 + 长文件风格写，parser 行数可能翻倍；若用表驱动，我给的数又偏高。我没看到任何实现，无法校准。
- **测试折行系数 8 行/用例是拍脑袋**：golden 脚本可能只有 3 行，实际 ±40%。
- **价值判断依赖 v0.1 示例集**：若真实 LLM 任务集包含"轮询到成功 / 逐条处理直到空结果"，B2-3 的 `while` 价值会上升，我的"推后"结论要重算。
- **A0 的优先级主张可能与评审判定相反**：评审要求"`|?` 优先级低于 `|>`"（[discussion L228-L229](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-discussion.md#L228-L229)）。我按"紧于 `|>`"算账，因为那样自然读法是 `(a |? b) |> c`；若裁判采纳评审口径，1.3 的 token 账要重算（每个"回退后继续管道"点 +2 token，且 LLM 漏括号率未知）。
- **我把"重试下沉到工具"当成纯外部成本**：如果工具库只有 2~3 个工具，这笔可以忽略，我的排序不变；如果有几十个工具，B2-1 的总代价会追平 B2-2，两件套的第二个名额应换给 B2-4 的 R4-2。
- **没有 E1**：本报告没有一条可重跑证据，所有行数都是 pre-code 估算。若证据席实测出某一项与我的估算差 2 倍以上，§5/§6 的排序就作废。
