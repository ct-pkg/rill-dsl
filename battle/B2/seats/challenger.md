## 1. B2-1 `|?`：优先级、失败单元、与 `$` 的顺序

### 1.1 失效场景：失败单元是"最后一次调用"，但 LLM 把它读成"整条表达式 or else"

```
# 意图：配置文件坏了就用默认端口
let port = read "conf.json" |> json_parse |> get "port" |? default_port "8080"
```

主张方语义（P0-11）：失败单元 = 最后执行的调用 `get "port"`。于是：

- `read` 失败（文件不存在）→ 不在失败单元 → 按 R4 中止整块（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L154) L154），`|?` 不生效。
- `json_parse` 失败（文件存在但不是 JSON）→ 不在失败单元 → 整块中止，`|?` 不生效。
- 只有 `get` 失败才走 `default_port`。

而真实任务里"配置坏了"最常见的形态恰恰是 read 失败或 json_parse 失败。LLM 写 `|?` 时的心智模型是"这条链不行就换默认值"，不是"只有取键那一步不行才换"。结果：兜底写了，等于没写，脚本照样整块失败。

**错在哪一层**：语义层（求值单元定义与用户意图错位），不是解析层。
**LLM 会不会察觉**：不会。语法合法、加载期无告警，运行时直接报 read/json_parse 的错误，LLM 看到错误会去改路径或改内容，而不是意识到"`|?` 管不到这两步"。

### 1.2 失效场景：失败单元依赖"工具失败"的定义，而规范没定义工具失败是什么

规范只说动态值有 `null`（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L156-L158) R5），字段访问"返回 borrow 或 null"（§10 表）。那么：

```
let port = get "port" |? default_port "8080"
```

- 若 `get` 缺键返回 `null` 而不是失败（按 R5 与 §10 表，这是可辩护的实现）：`|?` 永远不触发，`port` 是 `null`，下游拿到 null。LLM 以为兜底生效，实际拿到 null。
- 若 `get` 缺键算失败：`|?` 触发。同一份脚本，两个都合规范的实现，行为相反。

**错在哪一层**：工具契约层。`|?` 的语义建立在"失败"上，但"失败"没有 enum：`not_found | invalid_input | denied | limit | timeout | transient`。没有这张表，`|?` 的触发条件不可判定。
**LLM 会不会察觉**：不会，而且它无法从规范里查到，只能猜。

### 1.3 失效场景：`|?` 把权限拒绝/预算超限也吞掉

```
read "/etc/passwd" |? read "/workspace/fallback.txt"
```

第一次 `read` 会被第三层 `ParamConstraint` 拒绝（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L231-L243) §5.3）。如果 `|?` 把"参数越界"也当成可降级失败：越权尝试被静默改写成一次合法读取，脚本成功退出。**这是把安全事件洗成正常结果**，而且审计上看不到"曾经尝试越权"。

同理 `max_tool_calls` / `timeout_ms` 超限（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L284-L294) §6.3）：若 `|?` 捕获 limit 错误，循环里的兜底会不断"再试一次"，把预算耗尽变成一串兜底调用，最终结果看起来"成功但都走了兜底"。

**错在哪一层**：安全/预算层。
**LLM 会不会察觉**：不会，而且拿到 `ok=1` 会当成任务完成。

### 1.4 失效场景：`$` 与 `|?` 的注入顺序没有定义，两个实现会分叉

P0-11 L230 明写"与 `$` 同时出现时的追加顺序仍待定"：

```
read "conf.json" |> json_parse into {
    get "port" |? default_port "8080"
}
```

两种都合现有文本的实现：

- 实现甲：先给 `get` 注入 `$` → `get("port", $)`；失败后右侧 `default_port "8080"` 也接受上下文 → `default_port("8080", $)`。
- 实现乙：先在"调用参数已定"的层级做 `|?`，右侧不注入 `$` → `default_port("8080")`。

若 `default_port` 内部依赖 `$` 判断默认值来源，两者结果不同。更糟的是 `|?` 右侧如果是字面量 `null`（文法上 `fallback_expr` 允许，§6.2 L416-418），注入与否都"能跑"，差异完全不可见。

**错在哪一层**：求值顺序层。
**LLM 会不会察觉**：不会，连规范读者都要读到 L230 才知道这里空着。

### 1.5 失效场景：`|?` 表达不了 agent 最需要的"按项隔离，跳过坏项"

这是我认为最致命的一条。真实任务 top-3 里必然有"多文件批处理"：

```
# 意图：逐个文件分析，坏文件跳过
for f in files {
    let content = read f
    let hits = content |> grep "TODO"
    write "issues.txt" hits
}
```

R4 说块内失败整块中止（L154），所以任何一个文件读失败，整个脚本死掉，前面已写的结果也停。LLM 想用 `|?` 救：

```
for f in files {
    let content = read f |? null
    let hits = content |> grep "TODO"   # content 为 null 时这条照样失败
    write "issues.txt" hits
}
```

`|?` 只能替换**一次调用**，替换成 `null` 之后下一条 `grep null` 仍然失败并中止整块。要真正"跳过坏项继续下一条"，需要的是**块级恢复**（`try { ... } catch { continue }` 或 `for ... on_error continue`）。而块级恢复恰好被用户更正否掉了（§2.3 L73-76，只留 `|?`），try/catch 也被 §9 明确不做（L428）。

结论：**`|?` 是调用级兜底，但 agent 的常见恢复粒度是迭代级。** 现在的 B2 组合（只许 `|?` + 不做 try/catch + R4 整块中止）在"批量任务里一个坏输入"这个场景下是功能缺口，不是风格选择。LLM 会写出上面这段，然后要么整块失败，要么写出 `|? null` 后继续失败，两次都学不到"该用块级恢复"，因为规范里没有这个东西。

### 1.6 失效场景：重试走工具参数 = 把刚否掉的东西换个位置塞回去

§2.3 L76"需要重试次数时，用工具参数表达"。这等于要求每个工具 schema 自带 `retry` 参数。但 §2.2 L62 否掉 `limit N lines` / `head N chars` 的理由正是"语法关键字会逼每个工具都实现一遍后缀式参数"。同一个理由原样适用于 `retry`：要么每个工具都实现一遍重试，要么重试根本没实现。

而且脚本层重试无法知道幂等性：

```
write "out.txt" payload retry 3
```

若 `write` 在"写了一半超时"后重试，产出重复/半截内容。工具 schema 里没有 `idempotent` 字段（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L259-L266) ToolDef 无此字段），脚本层也无从判断。

**错在哪一层**：工具契约层 + 副作用层。
**LLM 会不会察觉**：不会，重试成功与非幂等副作用同时发生，结果"看起来成功"。

### 1.7 主张方最可能的漏洞

1. 用"失败单元 = 最后一次调用"给了一个**语法上确定、语义上不落地**的定义：没有定义"失败"的枚举，没有定义 `null` 算不算失败，没有定义 denied/limit 是否可捕获。
2. 会说"R4 没被破坏，`|?` 只是显式 opt-out"——回避了"块不再中止"和"已发生的副作用不回滚"这两个后果（见 §4）。
3. 会把重试甩给工具参数，却没注意这复刻了被否掉的"每个工具实现一遍后缀参数"。
4. 会把"与 `$` 的顺序待定"留成 TODO，而这在实现上是两个都合法、结果不同的分支，不是文档措辞问题。

### 1.8 我认可的替代

**方案 R1（最小可判定）**

1. `|?` 左操作数**只允许一个语法上的工具调用**，不允许整条管道：`fallback_expr := call_or_atom ("|?" call_or_atom)?`，其中左侧若是 `pipe_expr` 且含 `|>` 则**加载期报错**：`'|?' must follow a single tool call; wrap the pipeline or put '|?' on the call whose failure you mean`。失败单元从"运行时最后执行的那次"变成"源码上那个 token 左边的那次"，可静态检查，LLM 也能自纠。
2. 失败可捕获集合显式化，且**排除** `denied`、`limit`、`load`：
   - 可捕获：`not_found | invalid_input | transient`
   - 不可捕获（一律中止并上报）：`denied | limit | internal`
   写进 R4 的表格（见 §4 替代）。
3. `|?` 触发时给 `DslResult` 置 `degraded=1`，并 `emit tool_failed`（事件名由内核固定，不需要脚本声明）。否则内核无法区分"全部正常"与"全部兜底"。
4. 重试移出脚本语法：`ToolDef` 增加 `retry_policy { max_attempts, backoff_ms, idempotent }`，由内核执行；`write` 这类非幂等工具 `idempotent=0` 即不重试。脚本层只保留 `|?` 做"换一条路"。
5. `$` 顺序写死：先按参数列表补齐显式参数，再注入 `$`（即 `$` 永远是最后一个隐式参数），`|?` 两侧各自独立补齐。理由：与 R3 现有"追加到参数列表末尾"一致（L137-138），不需要第二套规则。

**方案 R2（如果连 R1 的复杂度都不想付）**：MVP 砍掉 `|?`。等 M1 的 20 条真实脚本统计出"降级"出现频次再决定。理由见 §5 的账：绝对 token 收益太小，语义风险太大。

## 2. B2-2 截断元数据的暴露方式；`limit N lines` / `head N chars` 后缀

先说结论：**后缀语法否得对，但理由要补强；元数据暴露 A/B/C/D 四个选项我全不接受，MVP 应选 E（工具侧信封，DSL 零改动）。**

### 2.1 先补强"后缀语法不该进 DSL"

用户给的理由是"逼每个工具实现一遍 + 与工具参数名冲突"（§2.2 L62）。还有一条更硬的：**它在现有空格实参文法下不可解析**。

```
read "a.log" limit 100 lines
```

按 §6.2，`tool_call := IDENT arg+`，`arg := postfix_expr`（L430-432），所以 `limit`、`100`、`lines` 全是实参。要把 `limit` 变成关键字，就会在 `grep limit "file"` 里把用户的实参 `limit` 吃掉。这直接踩 P0-7"关键字与工具名/字段名冲突"（L180-184），而 P0-7 的倾向里还专门写了"`limit` / `head` 不进入保留字"（L184）。所以后缀语法否掉是正确的，且理由比用户给的更强。

### 2.2 A（调用结果始终是记录）的失效场景

```
let content = read "big.log"        # 绑定记录
let hits = content |> grep "ERROR"  # 管道把记录追加到 grep 实参末尾
```

R2 隐式传参（L110-120）规定左值追加到参数末尾。现在左值是记录，`grep` 的 schema 期望字符串：

- 实现甲：`grep` 收到记录 → 参数浅校验失败（R5 只做浅校验，L158）→ 运行时报错。LLM 看到 "expected string, got record"，会到处补 `.value`，token 反而上涨。
- 实现乙：管道自动解包 `.value` → `content.truncated` 能读，但 `write "o" content` 又自动解包，而 `let x = content` 传给用户函数是否解包未定义。

两个都合规范，行为不同。**错在求值/类型层**；LLM 察觉不到实现乙下的"有时解包有时不解包"。

### 2.3 B（只有声明元数据的工具返回记录）的失效场景

P1-2 倾向 B（L259）。问题是记录会**经用户函数和管道泄漏**，而规范没定义传播规则：

```
fn load p {
    let r = read p        # 若 read 声明返回元数据 → r 是记录
    return r              # 返回值是记录还是 .value？未定义
}
let x = load "a.log"
write "o" x               # x 是记录 → write 收记录
```

同一个脚本，`let x = read "a.log"` 与 `let x = load "a.log"` 的 `x` 形态取决于函数体是否被内联——LLM 完全无法预测。**错在函数/管道交界层。**

### 2.4 C（伪字段 `r.truncated`）的失效场景：JSON 自带 `truncated`

真实任务里 JSON 载荷常有同名字段：

```
let status = get "status"    # 载荷 {"truncated": false, "ok": true}
if status.truncated {
    # 作者以为是"结果被截断"，实际读到的是业务字段
}
```

两条规则（元数据优先 / 载荷优先）都说得通，语义相反且无报错。要消歧就得用专用操作符（`meta r` / `r.@truncated`），那 C 的"token 成本更低"就消失了。

### 2.5 D（只在截断时产生记录）的失效场景：小夹具过、大文件崩

```
let x = read "f"
if x.truncated { ... }
```

小文件不截断 → `x` 是字符串 → `.truncated` 报错或 null；大文件截断 → `x` 是记录 → 正常。golden 测试用小夹具全绿，生产第一次遇到大文件就换分支。这是最坏的一类：**测试通过不代表对**。

### 2.6 主张方最可能的漏洞

1. 把 A/B/C/D 当成"token 与规则局部性"的二维权衡，漏掉**算子叉乘**：一旦有记录，`|>`、`+`、`==`、`[...]`、管道追加、fn 返回、`$` 注入每一条都要补 record/value 规则。这是 B2 里语义面积最大的一项。
2. 说"B 规则局部、可静态校验"，但 DSL 是动态类型（R5 L158），"静态校验"只能校验"这个绑定来自声明了元数据的工具"，无法校验它经 fn/管道后的形态。
3. 默认所有工具都声明元数据，但 ToolDef 没有 `returns_meta` 字段（L259-266），需要先加接口；这笔改动没进账。
4. 没处理"JSON 自带 `truncated`"这个必然冲突。

### 2.7 我认可的替代

**E（工具侧信封，DSL 零改动）**：

- 截断元数据只存在于**工具返回值内部**：需要元数据的工具返回普通 JSON 对象 `{ "value": ..., "truncated": true, "original_size": 12345 }`。
- DSL 不做任何特殊处理：`r.value`、`r.truncated` 就是普通字段访问，与现有 `x.a.b` 语义一致（§10 表）。
- 不需要 `.value` 自动解包、不需要 record 类型、不需要算子叉乘规则；不碰管道、不碰 fn 返回、不碰 `$`。
- "JSON 自带 truncated 冲突"不存在：信封的 `truncated` 就是载荷字段，工具作者自己负责命名（可以叫 `_meta`）。
- 代价：想拿元数据的脚本要多打 `.value`（约 2 token/次），不想拿的脚本完全不受影响。这正好符合"按需付费"。

**如果规范非要 DSL 层统一元数据**：选 B，但必须加一条硬规则——"记录只允许出现在 `let r = <meta-call>` 的绑定位置与字段访问；把记录放进管道、工具实参、算术、比较、fn 返回一律**加载/运行错误**，hint 为 `use r.value`"。也就是记录不泄漏，unwrap 边界显式。且 `.truncated` 在普通 `json_object` 上永远是载荷字段，元数据只能走 `r.meta.truncated`。这样至少把静默错误变成可报错。

**明确反对 A、C、D。**

## 3. B2-3 while / break / continue 与 `x = expr` 对"let 唯一定义点"的破坏

先把"破坏"说准：v0.1 并没有条文说"let 是唯一定义点"，只是**没有赋值**（§3.2 L59-72、§9 L425-434）。真正的隐含不变量是"每个名字在 `let` 处形状固定、之后只读"，作用域分析因此可以一次成型。赋值会打破它。

### 3.1 失效场景：没有赋值时，LLM 用 `let` 写累加，静默产出空结果

```
let report = ""
for f in files {
    let chunk = read f
    let report = report + chunk   # 每轮新建一个遮蔽绑定
}
write "all.txt" report            # 外层 report 仍是 ""
```

脚本合法、退出 0、写出空文件。**错在作用域层，属于静默错误，退出码正常，LLM 完全察觉不到**（它看到 no error 就认为成功）。这是"禁止赋值"基线最实打实的失败，也是加 `x = expr` 的最强理由。

### 3.2 失效场景：加了赋值但不管遮蔽，LLM 仍会在 `let` / `=` 之间选错

```
let total = 0
for x in xs {
    let total = total + x   # 本意累加，实际遮蔽
}
```

只要允许同名 `let` 在同作用域内遮蔽，上面照样静默错。所以**赋值必须配套一条加载期规则**：同一函数作用域内，`let` 重新声明一个当前可见的名字 = 加载错误，hint `did you mean 'total = total + x'?`。否则加赋值只是给了 LLM 第二种写错的方式。

### 3.3 失效场景：`while` 取消了"结构上有界"这个保证

```
while not done {
    let status = poll "job"
    if status == "done" { done = true }
}
```

- 若 `poll` 永远不返回 `"done"`（任务失败、工具抖动、字段名写错），循环跑到 `timeout_ms` 或 `max_tool_calls` 才停。
- 同一个任务用 `for i in range(20) { ... }` 表达，天然有界；超时变成"跑满 20 次后正常退出并返回部分结果"，可诊断。
- 更糟：`while` 一旦配上 `continue`，跳过自增就是死循环（见 3.4）。

**错在控制流/预算层。** LLM 察觉不到：它只会收到 `limit exceeded`，然后**重写同一个循环再试**，因为它不知道是循环本身不可终止。

### 3.4 失效场景：`continue` 跳过自增

```
let i = 0
while i < n {
    if bad i { continue }
    i = i + 1
}
```

经典死循环。LLM 写 `for` 时不会遇到（自增由 for 管），一引入 `while` + `continue` 就必然踩。**错在控制流层，后果是挂起到超时。**

### 3.5 失效场景：`break` / `continue` 穿过 `into` / `fn` 的绑定未定义

```
for f in files {
    read f into {
        if $.bad { break }   # 退出 into？退出 for？还是加载错误？
    }
}
```

- 若 `break` 只退出 `into`：等价于"跳过这个文件"，作者可能正是这个意思；
- 若 `break` 退出 `for`：后续文件全不处理，**静默少处理**；
- 若加载错误：最好，但规范没写。

`fn f() { break }` 讨论稿说要在加载期报错（P1-1 L244），但 `into` 没说。**错在作用域/跳转层，行为随实现分叉，LLM 察觉不到**（少处理文件不报错）。

### 3.6 主张方最可能的漏洞

1. 把 while/break/continue/赋值打包成"M4 一起做"，不区分**哪个是必需、哪个是风险源**。必需的是赋值（3.1 的静默错），风险源是 while + continue（3.3、3.4）。
2. 用"有 ExecLimits 兜底"回答终止性问题——但 ExecLimits 只把"挂死"变成"报错"，LLM 会重试同样的循环，运营成本照付。
3. 不定义 break/continue 与 `into` / `fn` 的交叉语义，留给实现"自然选择"。
4. 不处理 `let` 遮蔽，认为"允许赋值就够了"。

### 3.7 我认可的替代

1. **允许 `x = expr`**，但：仅语句位置（不能当表达式，避免 `if x = 1` 静默赋值）；目标必须是当前函数作用域已可见的绑定；`let` 在同作用域重名 = 加载错误（hint 指向 `=`）。
2. **允许 `break`，仅用于 `for`**；`break` 在 `into` 内 = 加载错误（hint：把判断移到 into 外），`break` 在 `fn` 内 = 加载错误。不给"穿层"留模糊。
3. **MVP 不做 `while`，不做 `continue`**。轮询任务写成 `for i in range(N) { ... if done { break } }`，有界、可诊断、不需要新跳转语义。若将来必须加 `while`，要求带硬上界 `while cond max N`，并把超界定义为正常结束（返回部分结果），而不是错误。
4. 需要"跳过坏项"时，用 §1.8 的块级恢复或 `|?`（取决于 B2-1 的裁决）；不要让 `continue` 成为唯一手段。

## 4. B2-4 引入 `|?` 后 R4"失败即中止整块"是否自相矛盾

### 4.1 严格说：不字面矛盾，但已经变成一句错话

R4 原文（[dsl-spec-v0.1.md](file:///Users/samxx/trae-ws/rill-dsl/docs/design/dsl-spec-v0.1.md#L152-L154) L152-154）：

> 工具调用失败时，默认中止当前 block 并向上传播（类似 Rust ?）。if/for/into/fn 块内失败，整个块中止。MVP 不做 try/catch。

加上 `|?` 后：

- "默认中止"仍成立（`|?` 是显式例外）——这一半没错。
- "**if/for/into/fn 块内失败，整个块中止**"——只要失败调用是 `|?` 的左操作数，**就不中止**。这句话在含 `|?` 的块里是假的。R4 必须加限定，否则规范自相矛盾。
- "**MVP 不做 try/catch**"——`|?` 就是"捕获一次失败并替换为另一个值"，是**调用级 try/catch**。说"不做"是把"没有 block 级 catch"说成了"没有任何 catch"。

所以准确结论：**R4 与 `|?` 不是逻辑矛盾，是 R4 的表述过时且两处为假；不改 R4 而只加 `|?`，就是规范内部不一致。**

### 4.2 更硬的问题：`|?` 让内核丢失失败信号，且不回滚副作用

```
write "tmp.txt" payload |> upload "s3://bucket" |? notify_fail "upload_failed"
```

- `upload` 失败 → `notify_fail` 执行 → 块继续 → `DslResult.ok = 1`。
- `tmp.txt` 已经写下去了，没有回滚。
- 内核只知道"脚本成功"，不知道"主力路径失败、走了兜底"。

调用方（agent 主循环）会把这次执行当作成功，不会重规划。**错在可观测性/错误传播层。** LLM 不会察觉，因为它拿到的是成功。

这正是"块级中止"原本要防的事：失败要么修，要么停。`|?` 把失败变成"局部替换 + 继续"，但没有配套的"降级可见"机制。

### 4.3 三套失败行为没有统一表

现有文本已经有三套：

| 构造 | 失败行为 | 出处 |
| --- | --- | --- |
| 工具调用（默认） | 中止整块并向上传播 | v0.1 L154 |
| `emit` | 丢弃 + 记日志，脚本不受影响 | v0.1 L192-196 |
| `|?` 左操作数 | 替换为右侧，继续 | §2.3 L75 |

三种都合理，但规范没有一张表把它们并列，也没有说明"哪些错误可被 `|?` 捕获"。`|?` 一进来，这张表从"可选"变成"必需"。

### 4.4 主张方最可能的漏洞

1. 用"`|?` 是显式 opt-out"证明 R4 没矛盾，但不改 R4 的第二、三句。
2. 不区分 error kind，把所有失败都当可捕获。
3. 不给 `DslResult` 加 `degraded`，导致"全部走兜底"与"全部正常"对调用方不可区分。
4. 不声明"`|?` 不回滚已发生的副作用"，读者会以为它是事务性的。

### 4.5 我认可的替代

把 R4 重写成一张表，并补 `degraded`：

```
失败行为表
| 构造                         | not_found/invalid_input/transient | denied/limit/internal |
| 普通工具调用                  | 中止块，向上传播                   | 中止块，向上传播       |
| 工具调用作为 |? 左操作数        | 执行右侧，置 degraded=1，emit tool_failed | 不捕获，中止块 |
| emit                         | 丢弃 + 记日志（永不失败）           | 同左                   |
| 记录为元数据（若采纳 B）        | 不适用                             | 不适用                 |
```

并明确：

- `DslResult` 增加 `degraded`（0/1），`ok=1 && degraded=1` 表示"完成但有降级"，主循环必须知道。
- `|?` 不回滚任何已发生的副作用；需要回滚时由工具自己提供补偿，DSL 不做事务。
- R4 的"整块中止"改为"整块中止，除非失败调用是 `|?` 的左操作数且错误属于可捕获集合"。
- 删除"MVP 不做 try/catch"，改为"MVP 只有调用级降级，没有块级恢复"——把缺口写明，而不是用一句否认掩盖。

## 5. 账：token / 实现复杂度 / 十次真实任务翻车率

估算口径：token 为单次使用相对"最朴素等价写法"的差值；LOC 为实现净增（lexer+parser+eval+诊断+测试）；翻车率为"10 个真实 agent 任务（读、搜、条件写、多文件、配置解析为主）中至少一次触发该糖失效/静默错的概率"。**这些是估计，不是测量**（仓库无实现、无任务集，无法跑 E1）。

| 糖 | 省 token/次 | 实现净增 | 主要风险层 | 10 次翻车（估） | 翻车是否静默 |
| --- | --- | --- | --- | --- | --- |
| `|?`（调用级） | 6–12（对比 `try{}catch{}`）；绝对收益在一套任务里约 20–40 token | lexer 1 token + 1 优先级层 + 可捕获错误表 + `$` 顺序 + `degraded` 字段；约 120–200 LOC，20–30 用例 | 语义/安全/可观测性 | 6–8 | **是**（走错分支、吞掉 denied、成功但降级不可见） |
| 截断元数据 A/B/C | A/B 反而 +2 token/次（`.value`）；C 约 0 | 每算子 record/value 规则 + 全量 golden 重写；约 300–600 LOC（若 M2 已有 tagged Value，可降到 50–100） | 类型/求值/函数边界 | 5–7 | **是**（记录进管道、JSON 同名字段） |
| 截断元数据 E（工具信封） | 0（需要时 +2） | DSL 0 LOC；每工具约 10–20 LOC | 工具契约 | 1–2（且是显式字段错） | 否（字段不存在会报错） |
| `x = expr` | 4/次 | 约 50 LOC + 遮蔽检查 + 10 用例 | 作用域 | 2–3（多为可报错的遮蔽） | 部分（3.1 那种反向静默错被修掉） |
| `while` | 10–20（对比有界 for） | 约 80 LOC + 终止语义 + 与 into/fn 的跳转规则，15–20 用例 | 控制流/预算 | 5–8 | 部分是（超时是响的，但会重试） |
| `continue` | 3–5 | 约 40 LOC + 跳转/标签交互 | 控制流 | 3–5 | **是**（跳过自增 → 挂起；跳过更新 → 静默少做） |
| `limit` / `head` 后缀 | 3–5 | 关键字化 + 实参消歧 + 每工具实现 | 文法/工具契约 | 4–6 | 否（可报错） | |

**排序结论**：

1. **最可能在十次任务里翻车的是 `|?`**，因为它的错误是静默的、跨语义/安全/可观测三层，且"失败单元 + 失败定义 + `$` 顺序"三个洞都没堵。
2. 其次是**截断元数据 A/B/C**（记录污染整门语言），但 E 方案可以把这块风险压到接近 0。
3. `while` 的翻车率也高，但它的失败大多是"响的"（超时/限额），可被 harness 捕获；`|?` 的失败不响，所以更危险。
4. 唯一强烈建议保留的是 `x = expr`，因为不加它会产生 3.1 那种**退出码 0 的空结果**，这是当前基线里最糟的一类错误。
5. `continue` 收益最小、风险不低，建议不做。`limit`/`head` 后缀已否，正确。

**净建议（按优先级）**：

- 必做：`x = expr` + 同作用域 `let` 重名报错。
- 必做：R4 重写为失败行为表 + `DslResult.degraded`。
- 条件做：`|?` 只在 §1.8 R1 的五条约束下做；否则 MVP 砍掉。
- 必做：截断走 E（工具信封），DSL 零改动。
- 不做：`while`、`continue`、`limit`/`head` 后缀。
- 可选：`break`（仅 `for`）。

## 7. 我可能错在哪

1. **token 与翻车率全是估计。** 仓库没有 10 个真实任务，也没有 M1 的 20 条 LLM 脚本样本，我给不出 E1。若实际任务集里几乎没有"降级/截断分支/轮询"，`|?` 与 `while` 的翻车率会显著低于我的估计，我的"砍掉"就偏保守。
2. **我假设 LLM 把 `|?` 读成"整条表达式 or else"。** 这是先验，不是测量。一个仔细读规范的模型可能正确理解"失败单元 = 最后一次调用"，那 1.1 的场景就弱化成"文档不够醒目"而不是"语义错误"。
3. **我假设工具会区分"失败"与"返回 null"。** 如果运行时明确"缺键返回 null、永不失败"，`|?` 的可捕获面缩小，1.2 的冲突消失，`|?` 的风险主要剩 1.3/1.5。
4. **LOC 假设 M2 没有 tagged Value。** 动态 JSON 值本来就需要类型标签；如果 M2 已把值统一为 tagged union，加一个 `Result` tag 可能只要 50–100 行，2.x 的成本被我高估。
5. **我可能低估了块级恢复的必要性。** 我把 `|?` 的局限（1.5）说成"要么改 `|?` 要么砍"，但也可能正确答案是**加回块级 catch**（用户更正可能被新证据推翻）。如果裁判认为用户更正是硬约束，那我的替代 R1 只是次优。
6. **我可能高估了 `x = expr` 的安全性。** 赋值 + 动态类型会让"这个名字现在是什么形状"随执行路径变化；若没有静态作用域检查，它可能引入新的静默错。我把它列为"必做"，前提是配套 3.7 的遮蔽/作用域规则；只加赋值不加规则，我不支持。
7. **锚点会漂。** docs 有并行会话在改（`git status` 已显示 `docs/spec/`、`docs/decisions/`、`docs/requirements/` 为未跟踪）。我引用的行号基于本次读取；若 HEAD 移动，请按原文片段重新核对，不要只认行号。
8. **我没有出替代方案的完整文法。** §1.8/§3.7/§2.7 是约束集合，不是可直接实现的产生式；若主张方要求"给出完整 grammar 才算替代"，我这条不满足 E4 的"改动行数可核对"，需要证据席补写。
