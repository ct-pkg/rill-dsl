# RILL v1.3 闭合核验
> 只核裁定是否闭合，不复核原文；编号沿用 v1.2-closure 与 v1.2-response-audit。
## 仍未闭合
- **R-04 非终结符**：§三 只补 `block := "{" statement* "}"`，`expr` 与 `condition` 仍无产生式，`each [in]`、`break <值>`、`if <条件>` 仍无法从文法推导。
- **`[results]`（N1/N2）**：裁定要求全部分支完成后触发一次，而 `[ok]/[error]` 逐分支触发只能写在分支内；§三 仍把二者放在 `parallel_body` 之后，位置未改，且 `[results]` 未进 §2/§4.5/§4.8 三张表，执行顺序无法落地。
- **成败通道（R-06/N2）**：裁定未定义动词用异常、status 字段还是返回值报告成败；若看返回值即与 §五「不做类型判断」冲突，若走异常则 §4.10 的字符串错误无法区分「成功返回空串」与失败。
- **N6（I-32/C-7）**：§4.16 只允许加空格、缩进、展开映射三件事，加双引号是第四种变换；引号内 `"`/`\` 的转义及展示→压缩回读规则未定义，可逆性仍不成立。
- **N7（R-21/R-22）**：同一长词在内外层各绑一个短词时，可见链上已出现两个绑定，违反「可见链唯一」；若内层覆盖生效，反向映射就有两个候选，除非按位置限定，裁定未写。
- **`]` 首字符（I-08/I-09）**：`<send> "x" [ok] user { ... }` 的 `]` 后首字符是裸词，被归入「独立且必须跟 `{`」支，`[ok]` 因此脱离 `<send>`；同理 `<merge> feature [into] main` 也被判非法，而 §4.5 仍把 `[into]/[ok]/[error]` 列为常用介词。
- **Shell 类型槽（N11/N14）**：`file:`/`dir:`/`net:` 未指定占主语、宾语前缀还是状语，只给了宿主分工；「未知动词加载期报错」也未定义加载期相对 parse/exec 的阶段，核心无动词表无法判定由谁在何时报错。
- **N13（R-15）**：`fn_def := "@" fn_template trailing_block* block` 的尾随块要作用于「前置语句结果」，但定义期前置的是模板不是运行值，尾随块无对象；若推迟到调用期，归属哪个结果也未写。
- **R-14 调用产生式**：N13 只补 `fn_def`，`@` 调用仍无 `call_stmt`；调用与定义都可带尾随块，只能靠「末尾是否还有函数体块」区分，该判定规则与调用在管道中的位置都未写。
- **each/parallel 输出与状态（N3/R-12）**：结果数组的入组粒度未定（每轮最后一句、每句还是整轮值）；`[results]` 的「状态」没有类型/字段；parallel 分支内 `$` 仍按 §4.8 指尚未产生的最终数组，成环未解；分支内 `[error]` 处理过的失败算成功还是失败也未定。
- **N5 默认值跳位**：实参按模板 `$变量` 出现顺序绑定已给出，但 `$var?默认值` 声称支持跳位，纯位置绑定无法判定省略的是哪个中间参数；缺 named/marker 语法，绑定位次仍不唯一。
- **R-27**：判闭合的理由「失败不触发 `[ok]`」回答的是 R-06，不是「顶层默认错误是否终止整个 program」；§4.10 的「中断管道」与 §4.15 的「中断当前语句」仍给出两种终止范围。
- **计数口径**：只声明「修正」，未给唯一问题数与逐项去重结果；`R-28` 在 `I-37/R-28`、`I-39/R-28` 两行重复，`I-04/R-04/R-24` 三合一未拆，按行计与按问题计仍对不上。
