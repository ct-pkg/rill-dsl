## 一、解析与词法边界

### I-01 扫描器把关键字语句读成主语
- **裁定**：已闭合。
- **v1.2 依据**：§三 关键字表「if / else / else-if / each / parallel / break」；§七.2「语句起始位置先查关键字表……命中即按对应语句类型解析」；§七.3「非符号字符 → 主语（直到 `<`），先查关键字表」。
- **说明**：关键字优先已成为扫描器第一步；关键字作普通主语须加引号（§三）。

### I-02 §三 的语句产生式覆盖不了四类语句
- **裁定**：已闭合。
- **v1.2 依据**：§三 `statement := simple_stmt | connector_clause | break_stmt | fn_def`，`connector_clause := if_clause | each_clause | parallel_clause`，并给出 `break_stmt`、`fn_def`。
- **说明**：`parallel { ... }` 可由 `parallel_clause` 推导，四类语句都进了产生式。

### I-03 零空格态下 `else if` 无法书写
- **裁定**：已闭合。
- **v1.2 依据**：§三 `if_clause := "if" condition block ("else-if" condition block)* ("else" block)?`；§4.19「连词之间 else-if 用连字符，不用空格」；§4.12 示例 `} else-if$cfg<contains>release=true {`。
- **说明**：`else-if` 是一个关键字，零空格可写，不再需要词间空格。

### I-04 条件「任何表达式」没有表达式文法
- **裁定**：部分闭合。
- **v1.2 依据**：§4.12「条件就是一条普通语句（或管道），可带尾随块」；§三 `condition := simple_stmt_or_pipeline_with_trailing_blocks`。
- **仍剩**：
  1. 两个非终结符 `expr`（用于 `prep_phrase`、`break_stmt`）和 `simple_stmt_or_pipeline_with_trailing_blocks` 在全文没有定义；
  2. 规范自己的条件示例 `if$cfg<contains>debug=true` 无法从 §三 的 `simple_stmt` 推出：§二 主语只能是裸词/引号，§4.1 主语是角色，`$cfg` 没有槽位；
  3. `=true` 的比较/赋值形式没有文法，§五.5 又声明「DSL 不做类型判断」。
- **代码**：`if$cfg<contains>debug=true { <send> "on" [to] user }`
  - 读法一：`$cfg` 是主语、`<contains>` 是动词、`debug=true` 是宾语（违反 §二/§4.1 的主语定义）；
  - 读法二：整句不合法，条件无法构造。
- **结论**：条件的**外壳**有了，条件的**内容**仍不能唯一解析。

### I-05 `[in]` 在循环头与介词位同形
- **裁定**：已闭合。
- **v1.2 依据**：§三 `each_clause := "each" $变量 prep_phrase`、`prep_phrase := "[in]" expr`；§4.13「[in] 是普通介词，带宾语（动宾从句），不是特殊标记」；示例 9 逐处标注两处 `[in]`。
- **说明**：循环头 `[in]` 由 `each_clause` 产生式吃掉，循环体里的 `[in] $file` 属于 `介宾补语`，位置不同，读法唯一。

### I-06 `{}` 既是块又被列为 falsy 值
- **裁定**：已闭合。
- **v1.2 依据**：§4.12 falsy 列表写作「`{}`（来自工具结果的空对象值）」；§4.3 宾语只允许裸词/引号；全文无对象字面量产生式。
- **说明**：`{}` 只能是块标记；作为值只可能来自工具结果。`if$cfg{} { ... }` 的第一个 `{}` 只能是 if 块，无第二种解析。

### I-07 状语的「并列等价项」没有组合语义
- **裁定**：部分闭合。
- **v1.2 依据**：§4.4「逗号分隔为并列项，顺序保持书写顺序，组合语义由底层库解释」；同节又写「支持带参数：名称:值。一个状语一个参数，多参数用多个状语表示」。
- **仍剩**：「一个状语一个参数」与「逗号分隔并列项」直接冲突，规范自己的示例 `(utf-8,backup:daily,timeout:30)` 一格里就有三个项；`(global,backup:daily)` 仍有两种读法。
- **代码**：`<read> config.yml (global,backup:daily)`
  - 读法一：`global` 与 `backup:daily` 是两个并列项（一个裸词项 + 一个具名项）；
  - 读法二：按「一个状语一个参数」，整组只能算一个参数，示例本身违规。
- **结论**：顺序已定，**项的划分与个数**未定。

## 二、结构标记的角色冲突

### I-08 `[into]` 介词位与尾随位同形
- **裁定**：部分闭合。
- **v1.2 依据**：§4.9「解析规则：`]` 后第一个字符是 `{` → 尾随形式；不是 `{` → 独立形式」；独立形式只允许 `[into] $cfg { ... }` 或 `[into] <语句> { ... }`。
- **仍剩**：这条 lookahead 把 §4.5 的普通介词用法一并判成「独立形式」，而独立形式的宾语不能是裸词，于是 §4.5 自己的例句反而不合法；规范没有「`[into]` 何时作普通介词」的规则。
- **代码**：`<merge> feature [into] main`
  - 读法一：§4.5 的介词短语，`main` 是介宾宾语，合法；
  - 读法二：§4.9 `]` 后不是 `{`，判为独立形式，宾语必须是 `$变量` 或 `<语句>`，`main` 不合法。
- **结论**：尾随/独立两种**块形式**分开了，普通介词与独立形式的**边界**没分开。

### I-09 `[ok]/[error]` 既在介词表里又是块头
- **裁定**：部分闭合。
- **v1.2 依据**：§4.10「[ok] / [error] 是介词，本质是 if 的真值条件变体，宾语位置规则同 [into]」，数量各 0..1。
- **仍剩**：§4.5 仍把 `[ok] [error]` 列在常用介词表，且没有限定宾语只能是 `$变量` 或前置语句结果；`[ok]` 后接裸词既不是尾随形式也不是 §4.10 的独立形式。
- **代码**：`<send> "x" [ok] user`
  - 读法一：§4.5 的介词短语，`user` 是宾语，语句合法但语义空洞；
  - 读法二：§4.10 的独立形式，宾语必须是 `$变量`，故非法。
- **结论**：块形式分开了，**介词身份**没删干净。

### I-10 尾随块挂在 `if/for/parallel` 上时触发面不明
- **裁定**：已闭合。
- **v1.2 依据**：§4.12「if 是纯条件判断，不产生动作，不挂尾随块」；§4.13「each 有隐藏的『do』动作，尾随块挂在『do』上，捕获整个循环动作的成败」；§4.14 同；§三 `each_body := block trailing_block*`、`parallel_body := block trailing_block*`，`if_clause` 无 `trailing_block*`。
- **说明**：`if` 后的 `[error]` 现在是语法错误；`each/parallel` 的捕获面是隐藏 do，含块内全部语句。

### I-11 `[into]` 与 `[in]` 的对照例子缺失
- **裁定**：已闭合。
- **v1.2 依据**：示例 9「[in] / [into] 对照」，覆盖循环头 `[in]`、循环体内 `[in]`、`[into]` 尾随形式、`[into]` 独立形式四处。

## 三、错误与控制流

### I-12 不写 `[error]` 时「错误被忽略」没有后状态
- **裁定**：已闭合。
- **v1.2 依据**：§4.10「不写 [error] 时，失败默认执行 `break "RILL DSL ERROR"`，中断管道。用户写 [error] 覆盖默认实现」；§4.11「失败且无 [error] → 默认 `break`，中断管道」；示例 11 注明「`<write>` 不执行」。
- **说明**：失败、输出、后续是否执行三件事都有唯一答案。

### I-13 `for` 的 null 从句双重归类
- **裁定**：已闭合。
- **v1.2 依据**：§4.13 判定顺序「1. 从句求值为 null → error，走 [error]（或默认 break），循环体不执行；2. 数组 → 正常遍历；3. 其他非数组值 → 单元素数组，执行一次」。
- **说明**：null 先判，互斥分支，不再双重命中。

### I-14 多个 `[into]` 与 `[error]` 的失败中断顺序未定义
- **裁定**：部分闭合。
- **v1.2 依据**：§4.11「[into] 失败：默认 break，中断管道，后续 [into] 不执行」。
- **仍剩**：「后续 [into] 不执行」已闭合；但用户写了 `[error]` 时，[into] 失败是走这个 `[error]` 还是直接 break，两节给出相反读法（§4.10「用户写 [error] 覆盖默认实现」 vs §4.11「默认 break」）。
- **代码**：`<read> a.yml [into] { $ <replace> [with] 1 } [into] { $ <replace> [with] 2 } [error] { <send> "fail" [to] user }`
  - 读法一：第一个 `[into]` 失败 → 触发 `[error]`，第二个 `[into]` 不执行；
  - 读法二：第一个 `[into]` 失败 → 直接 `break "RILL DSL ERROR"`，`[error]` 块不执行。

### I-15 `break` 出现在 `[ok]/[error]` 里时场域不明
- **裁定**：已闭合。
- **v1.2 依据**：§4.15「场域：由所在区块决定。任何区块内触发 break 都中断当前管道，一视同仁」；§4.11「若块内 break 则中断管道」。
- **说明**：反例中 `[error]` 里的 `break` 中断当前管道，下游不执行；值按 §4.15 交给管道外部或被丢弃。**注**：§4.15 第 1 条与第 4 条在循环体内互相冲突，见新矛盾 C-6。

### I-16 `break <值>` 没有捕捉语法
- **裁定**：已闭合。
- **v1.2 依据**：§三 `break_stmt := "break" [expr] [->$变量]`；§4.15「捕捉：`break <值> -> $var`，值传给管道外部」；示例 6 `break "done" -> $result`。
- **说明**：捕捉语法与示例都有了（`-> $var` 与 `->$变量` 的空格差异不影响解析）。

### I-17 `[error]` 的错误对象没有字段表
- **裁定**：已闭合。
- **v1.2 依据**：§4.10「[error] 的 `$`：错误信息字符串，默认值 `"RILL DSL ERROR"`，无结构化字段。用户要结构化信息，自己在块内加工」；§4.8 表格同。
- **说明**：明确为字符串，`$.kind` 这类写法不再被暗示为合法。

### I-18 `parallel` 没有汇合与失败语义
- **裁定**：部分闭合。
- **v1.2 依据**：§4.14「输出：按源序的结果数组」「失败语义：任一分支失败则整体失败，[error] 的 `$` 是失败分支的错误信息」。
- **仍剩**：多个分支**同时**失败时 `$` 取哪一个（源序第一个/最后一个）未定；失败后其余分支是否取消也未定。
- **代码**：`parallel { <read> a.yml <read> b.yml } [error] { <send> $ [to] user }`，若 a、b 都失败：
  - 读法一：`$` 是 a 的错误（源序第一个）；
  - 读法二：`$` 是 b 的错误（最后完成/最后失败）。

## 四、作用域与变量

### I-19 `->$x` 同时是声明和赋值，与「禁止重名」互斥
- **裁定**：部分闭合。
- **v1.2 依据**：§4.7「无声明/赋值区分。`->$x` 就是『把值放进 $x』：外层已存在则覆盖，不存在则建局部变量」；「块级：块内建的变量块外不可见；外层已存在的变量：子级场域直接读写」。
- **仍剩**：①「禁止重名」已删除，矛盾本身闭合；②每轮 `each` 是否新作用域没写；③「外层已存在则覆盖，不存在则建局部」依赖**运行时**是否存在，同一行代码在不同调用点语义不同，静态无法判定。
- **代码**：`each$f[in]xs { <send> $x [to] user <read> $f->$x }`
  - 读法一：第 2 轮能看到第 1 轮建的 `$x`（同一块实例复用）；
  - 读法二：每轮是新块，第 2 轮首句 `$x` 未定义（未定义变量的行为规范也没写）。

### I-20 `parallel` 分支写同一外部变量没有冲突规则
- **裁定**：已闭合。
- **v1.2 依据**：§4.7「parallel 分支禁止写外部变量——共享访问通过动词封装」；§4.14 同。
- **说明**：`$x` 在外部存在时，分支写它即违规；不存在时各分支建局部，互不冲突，判定唯一。

### I-21 `[into]` 的重名禁令在尾随形式里没有指代对象
- **裁定**：已闭合。
- **v1.2 依据**：§4.9「独立形式重名禁令：`[into]$cfg{...}` 块内禁止声明与 `$cfg` 同名的变量。尾随形式无此禁令」。

### I-22 `if` 不是表达式、`->$x` 只能声明，分支无法产值
- **裁定**：已闭合。
- **v1.2 依据**：§4.7 取消声明/赋值区分，外层已存在则覆盖；§4.12 仍规定「if 不参与管道」。
- **说明**：分支可以通过覆盖外层变量把值带出去（先在外层 `->$x` 建立，再在两个分支覆盖）；`if` 不产值这一点已被显式写成规则而非遗漏。规范未给 if 专用示例，但不影响行为唯一性。

### I-23 `$` 既是固定 self 又是变量前缀
- **裁定**：已闭合。
- **v1.2 依据**：§4.8「区分规则：`$name` 是变量，`$`（后不跟标识符）是 self，`.name` 是 self 字段」；§七.3 扫描器「`$` → 后跟标识符是变量，不跟是 self」。

## 五、`$` 语义

### I-24 `$` 的四种指代在嵌套时没有优先级
- **裁定**：部分闭合。
- **v1.2 依据**：§4.8「嵌套时最近包围块优先」+ 五语境表格；示例 5 给 `each` 内嵌 `[into]` 再嵌 `[ok]` 的标注。
- **仍剩**：嵌套优先级已闭合；但 §4.8 首句「`$` 是最近介词宾语（self）」与表格冲突——`each/[ok]/[error]/parallel` 的 `$` 并不是「最近介词宾语」。
- **代码**：`each$f[in]xs { <send> $ [to] user }`
  - 读法一：表格，`$` = 当前迭代项；
  - 读法二：首句，`$` = 最近介词宾语，即 `[in]` 的宾语（整个数组）。
- **结论**：嵌套规则有了，**基准指代**仍有两种读法。

### I-25 `[into]` 示例假设 `<read>` 返回已解析对象
- **裁定**：已闭合。
- **v1.2 依据**：示例 1 改为 `<read> /app/config.yml |> <parse> yaml [into] { .database ... }`，解析步骤显式化；§五.5「DSL 不做类型判断」。
- **说明**：示例不再依赖「read 自动解析」这一未声明假设。

## 六、管道与尾随区块

### I-26 `|>` 「只能在行尾」与所有示例冲突
- **裁定**：已闭合。
- **v1.2 依据**：§4.6「优先一行表达；太长折行时 `|>` 留在前一段行尾，不放在下一段开头」；§4.19「管道续行 `|>` 留在前一段行尾」；§三 `[|> simple_stmt]` 允许同行。
- **说明**：同行合法，跨行时留在物理行尾，冲突消失。

### I-27 `[ok]/[error]` 的「最后执行」与管道取输出冲突
- **裁定**：已闭合。
- **v1.2 依据**：§4.11 执行顺序「`[into]`（按书写顺序，0..N）→ `[ok]/[error]`（场景触发，最后）→ 段输出 → `|>` 下游」，并给出「段输出默认值」四种情形。
- **说明**：顺序与输出均有唯一规则；反例中 `[error]` 执行后输出 `$` 最终值（错误串），下游收到该值。

### I-28 尾随块覆盖「本段」还是「整条管道」不明
- **裁定**：已闭合。
- **v1.2 依据**：§4.6「尾随块只覆盖本段，`|>` 之后是下一条语句，互不影响」。
- **说明**：按段覆盖，`[error]` 不跨 `|>`。

### I-29 尾随块数量在 §三 / §4.10 / §4.11 之间不一致
- **裁定**：已闭合。
- **v1.2 依据**：§三 `trailing_block := "[ok]" block // 0..1 | "[error]" block // 0..1 | "[into]" block // 0..N`；§4.10「数量：[ok] 0..1，[error] 0..1」。
- **说明**：§三 与 §4.10 一致，§4.11 只讲叠加顺序，不再讲数量。

### I-30 `[ok]` 自己的输出通道没写
- **裁定**：已闭合。
- **v1.2 依据**：§4.11「成功且有 [ok] → [ok] 执行后 `$` 的最终值；只有修改 `$` 才改变输出，块内其他语句值不参与」。

## 七、`//map`

### I-31 「只有反引号才展开」与 `<read>`→`<r>` 自相矛盾
- **裁定**：已闭合。
- **v1.2 依据**：§4.17「引用：`<>` 内的单词和反引号包裹的裸词，共用一张映射表查表展开；其他裸词不查」；映射声明新增 `r<read` 形式。
- **说明**：`<r>` 与 `` `r` `` 走同一张表，矛盾消失。

### I-32 映射值含空格时 token 边界不明
- **裁定**：部分闭合。
- **v1.2 依据**：§4.17「标记符号之后到行尾是长词，按字面量处理，不转义、不解析」；示例 `my app`my application`。
- **仍剩**：展开后是否作为**单个**宾语 token 仍未明写；且 §4.16 展示→压缩「去掉空白（引号内保留）」，含空格长词在展示态没有引号，先删空白会变成另一个词，回不了表。
- **代码**：`//map{ p`my file }` 后写 `<read> `p``
  - 读法一：展开为单个字符串 `my file`；

- **说明**：I-33 反例中的「管道续行中间定义」现在直接非法。

### I-34 `//map` 短词字符集缺示例

## 十、v1.2 声称已改、实际改出新矛盾

以下每条都是 v1.2 变更摘要（§九）声称处理过的区域，但两处文字互相打架，实现者会得到两条路径。

### C-1 `[into]` 的 lookahead 规则吃掉 §4.5 的普通介词
- **涉及**：I-08。
- **矛盾**：§4.9「`]` 后第一个字符是 `{` → 尾随形式；不是 `{` → 独立形式」，而独立形式只允许 `$变量` 或 `<语句>`；§4.5 却把 `<merge> feature [into] main` 当合法介词短语。
- **代码**：`<merge> feature [into] main`
  - 读法一：普通介词短语，合法；
  - 读法二：独立形式，宾语 `main` 类型非法。
- **后果**：所有 `[into] <裸词>` 的既有写法都可能被解析器拒掉。

### C-2 `[ok]/[error]` 仍是 §4.5 的常用介词
- **涉及**：I-09。
- **矛盾**：§4.10 说二者「是介词，本质是 if 的真值条件变体」，独立形式宾语必须是 `$变量`；§4.5 仍无条件列为常用介词，可接裸词。
- **代码**：`<send> "x" [ok] user` —— 介词短语（合法、语义空洞）或非法独立形式。

### C-3 §4.4「一个状语一个参数」与并列项示例互斥
- **涉及**：I-07。
- **矛盾**：同节既说「逗号分隔为并列项」，又说「一个状语一个参数，多参数用多个状语表示」，而其示例 `(utf-8,backup:daily,timeout:30)` 一格三项。
- **代码**：`<read> config.yml (utf-8,backup:daily,timeout:30)` —— 一个参数还是三个参数。

### C-4 §4.8 首句「$ 是最近介词宾语」与五语境表格冲突
- **涉及**：I-24、I-47。
- **矛盾**：首句是总定义，表格是分语境定义；`each`、`[ok]`、`[error]`、`parallel` 四行的 `$` 都不是「最近介词宾语」。
- **代码**：`each$f[in]xs { <send> $ [to] user }` —— `$` 是当前项，还是 `[in]` 的宾语（整个数组）。

### C-5 §4.10「用户写 [error] 覆盖默认实现」与 §4.11「[into] 失败默认 break」
- **涉及**：I-14。
- **矛盾**：前者说任何失败都可被用户 `[error]` 接管，后者说 `[into]` 失败直接 break。
- **代码**：`<read> a.yml [into] { $ <replace> [with] 1 } [error] { <send> "fail" [to] user }` —— `[error]` 执行与否。

### C-6 §4.15 第 1 条与第 4 条对 break 场域给出不同答案
- **涉及**：I-15。
- **矛盾**：第 1 条「任何区块内触发 break 都中断当前管道，一视同仁」；第 4 条「顶层独立语句的 break：中断最近的包围场域（管道、循环、块）」。
- **代码**：`each$f[in]xs { <read> $f [ok] { break } } <send> "after" [to] user`
  - 读法一：只中断该段的管道，循环继续；
  - 读法二：中断最近的场域（循环），`<send>` 不执行。

### C-7 含空格长词与「展示→压缩去空白」破坏双向可逆
- **涉及**：I-32、I-35。
- **矛盾**：§4.17 允许长词含空格（`my app`my application`）；§4.16 展示→压缩「去掉空白（引号内保留）」，而展示态展开的长词没有引号；同节又保证「双向可逆」。
- **代码**：`//map{ p`my file }` + ``<read> `p` `` —— 展示态 `my file` 去空白成 `myfile`，回表失败；或先换短词再删空白才可逆，但规范未定顺序。

### C-8 `@` 的调用没有产生式，且示例 7 出现两个块
- **涉及**：I-49。
- **矛盾**：§三 `statement` 只有 `fn_def`（`@` + `fn_template` + `block`），没有调用形式；§4.18 却定义调用 `@ "engineer" <read> ...`。示例 7 的模板里先写 `[into] { ... }` 再写函数体 `{ ... }`，而 `fn_template` 产生式不含尾随块。
- **代码**：`@ "prod" <read> "config.yml" |> <send> "完成" [to] user` —— 定义还是调用；示例 7 两个块哪个是模板尾随块、哪个是函数体。

### C-9 条件的示例形状推不出 §三 的 condition 产生式
- **涉及**：I-04。
- **矛盾**：§三 `condition := simple_stmt_or_pipeline_with_trailing_blocks`，`simple_stmt` 的主语只允许裸词/引号；§4.12 的规范示例却写 `if$cfg<contains>debug=true`，`$cfg` 没有槽位。此外 `expr` 与 `simple_stmt_or_pipeline_with_trailing_blocks` 两个非终结符全文未定义。
- **代码**：`if$cfg<contains>debug=true { <send> "on" [to] user }` —— 合法条件或无法构造。

### C-10 `[ok]` 的触发条件在「成功」与「结果为真」之间摇摆
- **涉及**：I-27、I-30。
- **矛盾**：§4.10「[ok] 判断『结果为真』时进入块」（truthy）；§4.11 又把 `[ok]/[error]` 称为「场景触发」（成功/失败）。
- **代码**：`<read> empty.yml [ok] { <send> "ok" [to] user }`，`<read>` 成功但返回 `""`（falsy）
  - 读法一：按「结果为真」，`[ok]` 不执行；
  - 读法二：按「场景触发」，`[ok]` 执行。

### C-11 §4.7「外层已存在则覆盖」与 each/parallel 块作用域未对齐
- **涉及**：I-19。
- **矛盾**：§4.7 用「运行时外层是否存在」决定覆盖还是新建局部，但 §4.13/§4.14 没有说 `each` 每轮、`parallel` 每个分支是不是新的块实例。
- **代码**：`each$f[in]xs { <send> $x [to] user <read> $f->$x }` —— 第 2 轮能否看到第 1 轮的 `$x`。

### 最影响可实现的 top 5

1. **介词与块头的三义**（I-08、I-09；C-1、C-2）：`[into] main`、`[ok] user` 是否合法，解析器第一道门就分叉；这不是补例子能解决的，必须删掉「`[ok]/[error]` 是普通介词」或给 `[into]` 增加「普通介词」判定。
2. **条件与表达式**（I-04；C-9）：`if$cfg<contains>debug=true` 是规范自己的示例，却推不出 §三 的 `condition`；`expr` 未定义。所有 `if/each/break` 都受影响。
3. **错误模型的分叉**（I-14、I-18；C-5、C-10）：`[into]` 失败是否走用户 `[error]`、`[ok]` 是按成功还是按 truthy 触发；同一段脚本会走两条执行路径。
4. **`$` 的基准指代**（I-24；C-4）：§4.8 首句与表格冲突，导致所有尾随块里的 `$` 语义随读法变化，而 `$` 是 v1.2 用来替代 `return` 的核心机制。
5. **调用绑定与管道落槽**（I-37、I-38）：DSL 侧只有「由注册表决定」一句边界声明，`<grep> "TODO" [in] src/a.c` 与 `<read> a.yml |> <replace> ...` 仍无法确定实参位置，引擎无法生成 `args_json`。

> 一句话结论：v1.2 把 v1.1 的「结构缺失」补掉了大半（39/51 闭合），但它在 `[into]/[ok]/[error]` 的介词身份、`$` 的基准定义、`[ok]` 的触发条件三处**改写过度**，把原来的「没写」变成了「写了两个互相冲突的版本」。这 11 条部分闭合里有 8 条属于这一类，优先修这三处，闭合率才能真正上去。
