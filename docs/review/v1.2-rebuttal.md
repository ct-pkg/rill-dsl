## 0. 我认为按现有文字解释得通、不附议的点

先列这些，避免把「能读懂」写成「有漏洞」：

- **`[in]` 与 `[into]` 的拼写本身不构成前缀歧义**。`in` 与 `into` 是不同单词，`]` 终止；`each_clause` 产生式也会吃掉循环头的 `[in]`。I-05 判已闭合，我同意。真正的新问题是 §六 示例 5 的 `each $f [in] xs`（见 R-11）。
- **`else-if` 的零空格写法成立**。它是关键字表里的一个连字符词，`else-if$cfg` 不需要词间空格。I-03 判已闭合，我同意。
- **`{}` 只能作块标记**。v1.2 没有对象字面量产生式，§4.12 的 `{}` 是「来自工具结果的空对象值」，不是可写字面量；`if$cfg{}` 的第一个 `{}` 只能是块。I-06 判已闭合，我同意。
- **`|>` 同行与折行规则可以自洽**。§4.6 允许同行，折行时留在前段行尾；I-26 的「只能行尾」冲突已消。我同意。
- **`[error]` 的 `$` 是字符串、无结构化字段**。§4.10 已明说，I-17 判已闭合，我同意；不要再暗示 `$.kind`。
- **`//map` 的正向查表规则可以自洽**。`<>` 内单词与反引号裸词共用一张表，`r<read` 声明动词长词；I-31 判已闭合，我同意。问题在反向映射与展示态（见 R-18..R-21）。

## 一、产生式与结构标记

### R-01 多个介宾短语无法由 §三 推导

**档：确有问题**

- **问题**：`simple_stmt` 只允许一组 `[[介宾]介宾宾语]`，但规范自己的例子一行有两个介宾短语。
- **最短反例**：

```rill
<replace> localhost [with] prod (global) [in] $file
```

- **依据**：§三 `simple_stmt := [主语] <动词> 宾语 [(状语)] [[介宾]介宾宾语] [->$变量] trailing_block* [|> simple_stmt]`；§4.13 与 §六 示例 9 均出现 `[with] prod ... [in] $file`；§八.6 又写「状语和介宾可无限叠加」。
- **为什么实现者无法唯一确定**：第二个 `[in]` 没有产生式可归约。若把 `[[介宾]介宾宾语]` 改成 `*`，AST 是「介宾列表」还是「每个介宾一个节点」未定；若把 `[in]` 归入状语，`[with]`/`[in]` 的槽位顺序又变了。示例 1 的 `[into]` 后面还跟 `[ok]/[error]`，一旦介宾可多个，尾随块的起点也要重新定义。
- **建议修补方向**：把介宾改成 `介宾短语*`，明确 0..N、顺序、同一介词是否可重复；同步 §八.6 与 §七.3 的扫描器。

### R-02 `parallel ... |> ...` 不可推导

**档：确有问题**

- **问题**：§六 示例 4 在 `parallel` 块后接 `|>`，但 §三 的 `parallel_clause` 没有管道产生式。
- **最短反例**：

```rill
parallel { <read> a.yml <read> b.yml } |> <write> out.yml
```

- **依据**：§三 `parallel_clause := "parallel" parallel_body`、`parallel_body := block trailing_block*`，无 `|>`；`statement` 中只有 `simple_stmt` 带 `[|> simple_stmt]`；§六 示例 4 却写 `} |> <write> out.yml`。
- **为什么实现者无法唯一确定**：parser 在 `parallel` 块结束、尾随块结束后看到 `|>`，没有可归约的产生式。若把管道右侧放宽成 `statement`，`if` 也能进管道，与 §4.12「if 不参与管道」冲突；若只允许 `simple_stmt`，示例 4 非法。
- **建议修补方向**：定义 `pipeline_segment := simple_stmt | parallel_clause | ...`，明确哪些 connector 可作管道段；或在示例 4 删掉管道，改为独立语句。

### R-03 独立形式 `[into] $cfg { ... }` / `[ok] $x { ... }` 不是 statement

**档：确有问题**

- **问题**：§4.9/§4.10 定义了独立形式，但 §三 没有对应的语句产生式；`simple_stmt` 必须以 `<动词>` 开头。
- **最短反例**：

```rill
[into] $cfg { .host <replace> [with] prod }
[ok] $x { <send> $x [to] user }
```

- **依据**：§4.9「独立形式：`[into] $cfg { ... }` 或 `[into] <语句> { ... }`」；§4.10「独立形式：`[ok] $x { ... }` / `[error] $x { ... }`」；§三 `statement := simple_stmt | connector_clause | break_stmt | fn_def`，无 `into_stmt`/`ok_stmt`。
- **为什么实现者无法唯一确定**：语句起始看到 `[`，parser 只能把它当成某个 `simple_stmt` 的介宾；但前面没有动词，无法归约。§六 示例 9 的独立 `[into] $cfg { ... }` 因此不可解析。
- **建议修补方向**：增加 `standalone_trailing := ("[into]"|"[ok]"|"[error]") ... block`，或删除独立形式，只保留尾随形式。

### R-04 `expr` / `block` / `condition` 未定义

**档：确有问题**

- **问题**：§三 引用了三个没有产生式的非终结符，`each`、`break`、`if` 都依赖它们。
- **最短反例**：

```rill
each $f [in] xs { <send> $f [to] user }
break 42 -> $x
```

- **依据**：§三 `prep_phrase := "[in]" expr`、`break_stmt := "break" [expr] [->$变量]`、`condition := simple_stmt_or_pipeline_with_trailing_blocks`；全文没有 `expr`、`block`、`simple_stmt_or_pipeline_with_trailing_blocks` 的产生式。
- **为什么实现者无法唯一确定**：`xs` 是 bare word、变量还是简单语句？`42` 是数字还是 bare word？`block` 是否 `{ statement* }`？`condition` 是否等价于 `simple_stmt` 或管道？这些直接决定 AST 与词法；没有定义就无法写 parser。
- **建议修补方向**：补 `expr := ...`、`block := "{" statement* "}"`、`condition := ...`；明确 `expr` 是否允许管道、尾随块、变量、字面量。

### R-05 `trailing_block*` 允许重复 `[ok]` / `[error]`

**档：说的不够清晰**

- **问题**：§三 的 `trailing_block*` 允许任意个、任意顺序，§4.10 却限定 `[ok]` 0..1、`[error]` 0..1。
- **最短反例**：

```rill
<read> a.yml [ok] { <send> "1" [to] user } [ok] { <send> "2" [to] user }
```

- **依据**：§三 `trailing_block := "[ok]" block // 0..1 | "[error]" block // 0..1 | "[into]" block // 0..N`，但用的是 `trailing_block*`；§4.10「数量：[ok] 0..1，[error] 0..1」。
- **为什么实现者无法唯一确定**：语法接受两个 `[ok]`，语义说最多一个；parser 是在语法层拒绝，还是接受后由语义检查报错？第二个 `[ok]` 的触发与段输出顺序也未写。
- **建议修补方向**：把 `trailing_block*` 换成带计数与顺序的产生式，或在 §三 明写「语法接受，语义校验拒绝」；给重复 `[ok]` 的错误阶段。

## 二、尾随块、段输出与默认错误

### R-06 `[ok]` 的触发条件是「结果为真」还是「成功」

**档：确有问题**（与 C-10 同源）

- **问题**：§4.10 说 `[ok]` 判断「结果为真」时进入块，§4.11 又说「成功且有 `[ok]`」就执行。
- **最短反例**：

```rill
<read> empty.yml [ok] { <send> "ok" [to] user }
```

- **依据**：§4.10「`[ok]` 判断『结果为真』时进入块」；§4.11「成功且有 `[ok]` → `[ok]` 执行后 `$` 的最终值」。
- **为什么实现者无法唯一确定**：`<read>` 成功但返回 `""`（falsy）。按 §4.10 不执行，按 §4.11 执行；段输出也随之不同：前者是 `""`，后者是 `[ok]` 块后的 `$` 值。
- **建议修补方向**：二选一——`[ok]` 是 truthy 门（按结果值）还是 success 门（按错误状态）；删除另一处措辞，并给空文件/空数组/`0` 的判定示例。

### R-07 `$` 在 `[ok]/[error]` 块内被嵌套语句的介词改写

**档：确有问题**

- **问题**：§4.8 说 `$` 是「最近介词宾语」，但 `[ok]` 块内又固定为「段成功结果」；块内一条 `<send> ... [to] user` 会把最近介词宾语变成 `user`。
- **最短反例**：

```rill
<read> a.yml [ok] { <send> "done" [to] user }
```

- **依据**：§4.8「`$` 是最近介词宾语（self）」；§4.8 表「`[ok]` 块内 `$` = 段成功结果」；§4.11「`[ok]` 执行后 `$` 的最终值决定段输出」。
- **为什么实现者无法唯一确定**：如果 `$` 随 `<send>` 的 `[to] user` 变成 `user`，段输出就变成 `user`，而不是 `<read>` 的结果；如果 `$` 不变，§4.8 首句「最近介词宾语」被违反。`[error]` 块内同样会出现这个问题。
- **建议修补方向**：明确 `$` 在 `[ok]/[error]` 块内是「块上下文绑定」，不被块内普通语句的介词重绑；或规定嵌套语句结束后恢复；给 `<send> [to]` 这种常见写法一个例子。

### R-08 无介宾的 `simple_stmt` 段输出没有 `$` 可指

**档：确有问题**

- **问题**：§4.11 说成功且无 `[ok]` 时段输出是「语句结果（`$` 当前值）」，但无介宾语句没有「最近介词宾语」。
- **最短反例**：

```rill
<read> a.yml |> <parse> yaml
```

- **依据**：§4.11「成功且无 `[ok]` → 语句结果（`$` 当前值）」；§4.8「`$` 是最近介词宾语（self）」。
- **为什么实现者无法唯一确定**：`<read>` 和 `<parse>` 都没有介宾，`$` 没有指代对象；「语句结果」和「`$` 当前值」不是同一个东西。下游拿到的是 `<read>` 的返回值、`<parse>` 的返回值，还是 undefined？
- **建议修补方向**：定义无介宾时 `$` 的默认值（建议就是语句结果），或把段输出改成「动词返回值」，不引用 `$`。

### R-09 `each` 的隐藏 do 上 `[ok]/[error]` 的 `$` 未定义

**档：确有问题**

- **问题**：§4.13 说 `each` 的尾随块挂在隐藏 do 上，但 §4.8 的 `$` 表只给了 each 循环体的「当前迭代项」，没给隐藏 do 的 `[ok]/[error]`。
- **最短反例**：

```rill
each$f[in]<search>*.yml { <send> $f [to] user } [ok] { <send> $ [to] user }
```

- **依据**：§4.13「each 有隐藏的『do』动作，尾随块挂在『do』上」；§4.8 表只有「each 循环体 → 当前迭代项」，没有 each 的 `[ok]/[error]` 行。
- **为什么实现者无法唯一确定**：`[ok]` 里的 `$` 是结果数组、最后一项、还是隐藏 do 的返回值？`[error]` 里的 `$` 是错误串，但 each 的 `$` 表没写；§六 示例 3 的 `[ok]` 只发消息、不引用 `$`，无法反推。
- **建议修补方向**：给隐藏 do 定义输出（建议按源序的结果数组），并在 §4.8 表补 each 的 `[ok]/[error]` 行；给一个引用 `$` 的例子。

## 三、`each` / `parallel` 与 `$`

### R-10 `each` 头表达式的尾随块与 `each_body` 块无法切分

**档：确有问题**

- **问题**：`each` 头的 `expr` 可以带尾随块（§4.12 说条件可带），`each_body` 本身又是一个 block；两个连续块没有归属规则。
- **最短反例**：

```rill
each$f[in]<search>*.yml [ok] { <send> "found" [to] user } { <send> $f [to] user }
```

- **依据**：§三 `each_clause := "each" $变量 prep_phrase each_body`、`prep_phrase := "[in]" expr`、`each_body := block trailing_block*`；§4.12「条件就是一条普通语句（或管道），可带尾随块」。
- **为什么实现者无法唯一确定**：第一个 `{...}` 是 `<search>` 的 `[ok]` 块，还是 each 的 body？第二个 `{...}` 是 body 还是多余块？`expr` 未定义，parser 不知道头表达式在何处结束。
- **建议修补方向**：禁止 `each` 头表达式带尾随块，或要求 body 前有显式 `do` 标记；正式定义 `expr` 的边界，并给「头有 `[ok]` + body」的最小例子。

### R-11 `each $f [in] xs` 的 `xs` 不是变量

**档：确有问题**（示例与规则不一致）

- **问题**：§六 示例 5 写 `each $f [in] xs`，但 v1.2 的变量必须是 `$name`，`xs` 是 bare word。
- **最短反例**：

```rill
each $f [in] xs { <send> $f [to] user }
```

- **依据**：§4.8「`$name` 是变量，`$`（后不跟标识符）是 self」；§4.13「`[in]` 是普通介词，带宾语（动宾从句）」；§三 `prep_phrase := "[in]" expr`。
- **为什么实现者无法唯一确定**：按变量规则，`xs` 是字面字符串，不是变量；`each` 会对字符串做「非数组 → 单元素数组」，只执行一次，`$f = "xs"`。如果作者想遍历变量，示例应写 `$xs`；如果 `expr` 允许 bare word 作变量名，则 §4.8 的 `$name` 规则被破坏。
- **建议修补方向**：示例改为 `$xs`；在 `expr` 产生式里明确「变量引用必须带 `$`，bare word 是字面量」；给一个 bare word 与 `$var` 的对照。

### R-12 `parallel` 分支内的 `$` 是最终结果数组，执行中形成循环依赖

**档：确有问题**

- **问题**：§4.8 规定 parallel 块内 `$` 是「按源序的结果数组」，但分支执行时结果数组尚未产生。
- **最短反例**：

```rill
parallel { <send> $ [to] user <send> "b" [to] user }
```

- **依据**：§4.8 表「parallel 块内 → 按源序的结果数组」；§4.14「块内一行一句，每句可以是复杂语法」「输出：按源序的结果数组」。
- **为什么实现者无法唯一确定**：第一个分支执行时，`$` 如果是最终结果数组，数组还没生成（循环依赖）；如果 `$` 是分支自己的上下文，§4.8 的表就不适用于「parallel 块内」的所有位置。分支需要引用自己的输入时没有可用符号。
- **建议修补方向**：明确 `$` 只在 parallel 的尾随 `[ok]/[error]` 中是结果数组；分支内 `$` 是分支自己的上下文，或禁止在分支内使用 `$`。

### R-13 `parallel` 的「任一分支失败」没有区分「已处理的失败」

**档：确有问题**

- **问题**：§4.14 说任一分支失败则整体失败，但分支可以用自己的 `[error]` 处理失败；处理过的失败是否仍算「失败」没有规则。
- **最短反例**：

```rill
parallel {
    <read> a.yml [error] { <send> "a failed" [to] user }
    <read> b.yml
} [error] { <send> "parallel failed" [to] user }
```

- **依据**：§4.14「失败语义：任一分支失败则整体失败，`[error]` 的 `$` 是失败分支的错误信息」；§4.10「用户写 `[error]` 覆盖默认实现」。
- **为什么实现者无法唯一确定**：第一个分支的 `[error]` 如果不 break，失败被吞掉，分支算成功还是失败？如果算失败，内层 `[error]` 无法隔离；如果算成功，§4.14 的「任一分支失败」就被改写。
- **建议修补方向**：区分「原始错误」与「未处理错误」；明确 parallel 只对未处理错误整体失败，或规定内层 `[error]` 处理后分支仍标记为失败。

## 四、`@` 函数

### R-14 `@` 调用没有产生式，且与定义同形

**档：确有问题**（与 C-8/I-49 同源）

- **问题**：§4.18 定义了 `@` 调用，但 §三 只有 `fn_def := "@" fn_template block`；调用和定义都以 `@` + SVO 开头。
- **最短反例**：

```rill
@ "prod" <read> "config.yml" [into] { .host <replace> [with] prod }
```

- **依据**：§三 `statement := ... | fn_def`，无 `call_stmt`；§4.18「调用：`@ "engineer" <read> "config.yml" (global) [in] $files`」；§七.3「`@` → 函数定义」。
- **为什么实现者无法唯一确定**：这段既可以是「调用 + `[into]` 尾随块」，也可以是「定义 + 模板里的 `[into]` 块 + 函数体块」；`@` 后都是 SVO，无法靠前缀区分。调用没有 block，定义必须有 block，但这里的 block 可以被两边解释。若调用传变量（`@ $x <read> $y`），连「模板含 `$` 才是定义」也失效。
- **建议修补方向**：给调用独立标记（如 `@@` 或 `call@`），或规定「`@` 后出现 `$变量` 模板且最后一个块是函数体」的判定顺序；补 `call_stmt` 产生式及调用在管道中的位置。

### R-15 `fn_template` 不含尾随块，示例 7 出现两个块

**档：确有问题**

- **问题**：§三 的 `fn_template` 没有 `trailing_block*`，但 §六 示例 7 在模板里写 `[into] { ... }`，后面再跟函数体 `{ ... }`。
- **最短反例**：

```rill
@ $subject <read> $path [into] {
    .host <replace> [with] prod
} {
    <read> $path |> <parse> yaml
    <write> $path
}
```

- **依据**：§三 `fn_template := [主语] <动词> 宾语 [(状语)] [[介宾]介宾宾语]`，无 `trailing_block*`；§4.18 示例把 `[into] { ... }` 写在模板里，再跟函数体；§三 `fn_def := "@" fn_template block` 只允许一个 block。
- **为什么实现者无法唯一确定**：第一个 `{...}` 是模板的 `[into]` 块还是函数体？`fn_def` 只吃一个 block；如果模板不能带尾随块，第一个块就是函数体，第二个块没有归属；如果模板能带，§三 产生式缺这一项。
- **建议修补方向**：允许 `fn_template` 带 `trailing_block*`，并规定「最后一个 block 是函数体，之前的是模板尾随块」；或禁止模板带尾随块，改写示例 7。

### R-16 `@` 返回值「最后一条语句结果（或 `$` 最终值）」是二选一

**档：确有问题**

- **问题**：§4.18 用「或」并列了两种返回值，调用方无法预测。
- **最短反例**：

```rill
@ $subject <read> $path {
    <read> $path [into] { .host <replace> [with] prod }
    <write> $path
}
```

- **依据**：§4.18「返回值：函数体最后一条语句的结果（或函数内 `$` 的最终值）」。
- **为什么实现者无法唯一确定**：最后一条 `<write>` 的结果通常是 null；`$` 的最终值可能是 `[into]` 改写后的对象。两者不同，函数调用拿到哪一个没有规则。
- **建议修补方向**：二选一，例如固定为「函数体最后一条语句的值；若最后一条是 `[into]` 段，则取段输出」，删除括号里的「或」。

### R-17 `@` 模板签名不含主语/宾语，默认值绑定无法确定

**档：确有问题**

- **问题**：§4.18 说签名只匹配「动词 + 状语 + 介词」，但实际参数绑定要落到 `$subject`、`$object`、`$params`，槽位顺序没有定义。
- **最短反例**：

```rill
@ $subject <read> $path ($params) [in] $array { ... }
@ "prod" <read> "config.yml" (global) [in] $files
```

- **依据**：§4.18「匹配签名：动词 + 状语 + 介词」「实参按位置绑定到模板里的 `$var`」；§三 `fn_template := [主语] <动词> 宾语 [(状语)] [[介宾]介宾宾语]`；§4.18「默认值格式：`$object?config.yml`」。
- **为什么实现者无法唯一确定**：签名不含主语/宾语，但模板里有 `$subject/$path`；调用实参如何按位置落到这些变量？如果某个参数有默认值、调用省略它，位置绑定如何跳位？`($params)` 是数组还是一个参数？没有完整槽位表，无法生成绑定。
- **建议修补方向**：给出完整的参数槽顺序（主语、宾语、状语、介宾）、默认值省略规则、`($params)` 是单参数还是列表；把「签名匹配」与「参数绑定」分开写。

## 五、`//map` 与双层可逆

### R-18 `//map` 短词含空格（示例 `my app`）

**档：确有问题**

- **问题**：§4.17 的短词字符集是「字母、数字、`-`、`_`」，但示例 `my app`my application` 的短词是 `my app`，含空格。
- **最短反例**：

```text
//map{
my app`my application
}
```

- **依据**：§4.17「短词：字母、数字、`-`、`_`，不含特殊符号」；同节示例 `my app`my application`。
- **为什么实现者无法唯一确定**：按字符集，`my app` 不是合法短词；按示例，它又是短词。parser 在空白处会结束短词，把 `app` 当成标记或长词的一部分，无法唯一切分。
- **建议修补方向**：示例改成 `myapp`my application`，或允许短词含空格并规定转义/引号；二者取一，并给短词边界例子。

### R-19 展示态示例 10 没有展开映射，与 §4.16 冲突

**档：确有问题**

- **问题**：§4.16 说展示态要做「展开映射表」，但 §六 示例 10 的展示态仍保留 `` `cfg` `` 引用。
- **最短反例**：

```text
压缩态：
//map{
cfg`configuration
}
<read>`cfg`.yml->$c

展示态：
//map{
cfg`configuration
}
<read> `cfg`.yml -> $c
```

- **依据**：§4.16「展示态只做三件事——加空格、按块缩进、展开映射表」；§六 示例 10 的展示态仍写 `` `cfg`.yml ``。
- **为什么实现者无法唯一确定**：如果展示态要展开，display 应是 `configuration.yml`；如果展示态不展开，§4.16 的「展开映射表」应删掉。两种输出对应不同的「展示 → 压缩」基准，双向可逆无从谈起。
- **建议修补方向**：二选一；若展开，示例 10 改成 `configuration.yml`，并说明展示态不再含 `//map` 引用；若不展开，删除 §4.16 的「展开映射表」。

### R-20 反向映射的前缀/子串歧义

**档：说的不够清晰**

- **问题**：§4.17 只保证「长词唯一」，没有排除一个长词是另一个长词的前缀；展示 → 压缩时可能切错。
- **最短反例**：

```text
//map{
a`alpha
b`alphabet
}
```

展示态文本 `alphabet` 反向压缩：是 `a` + `bet`，还是 `b`？

- **依据**：§4.16「展示 → 压缩：……查映射表把长词换短词」；§4.17「长词唯一：同一个长词在表内只能出现一次，保证双向可逆」。
- **为什么实现者无法唯一确定**：按最长匹配可得到 `b`，但规范没写；按短词优先会先命中 `alpha`，得到 `a` + `bet`。两种结果不同，「长词唯一」不足以保证可逆。
- **建议修补方向**：规定反向映射按「最长长词优先」，或禁止长词互为前缀/子串；在 §4.16 加一条 property test 要求。

### R-21 嵌套 `//map` 的长词唯一性与反向映射

**档：确有问题**

- **问题**：§4.17 说「不同块可各自定义」「长词唯一」「内层优先」，但没有说长词唯一是全局还是按块；内外层用同一长词时反向映射不知道回哪个短词。
- **最短反例**：

```text
//map{
c`configuration
}
{
    //map{
k`configuration
    }
    <read> `k`.yml
}
```

- **依据**：§4.17「重复：同块内重复短词报错；不同块可各自定义」「长词唯一：同一个长词在表内只能出现一次」「生效范围：所在块内从定义处之后到块结束。内层优先」。
- **为什么实现者无法唯一确定**：如果「表」是每个 map block，内外都可有 `configuration`，反向映射 `configuration` 应回 `c` 还是 `k`？如果「表」是全局合并表，内层定义直接违反长词唯一。两种读法，双向可逆都受影响。
- **建议修补方向**：明确长词唯一是全局还是按块；若是按块，规定反向映射的作用域（当前块内优先）并给出算法；给嵌套 map 的例子。

### R-22 `//map` 的内层优先与「从定义处之后生效」冲突

**档：确有问题**

- **问题**：内层块在定义 `//map` 之前引用同一短词时，是「内层优先」还是「从定义处之后」？
- **最短反例**：

```text
//map{
cfg`outer
}
{
    <read> `cfg`.yml
    //map{
cfg`inner
    }
    <read> `cfg`.yml
}
```

- **依据**：§4.17「生效范围：所在块内从定义处之后到块结束。内层优先」。
- **为什么实现者无法唯一确定**：第一行在内层 `//map` 之前；如果「内层优先」指整个内层块，第一行也展开成 `inner`；如果指「定义处之后」，第一行应展开成外层 `outer`。两行会得到不同结果，规范没有说哪个。
- **建议修补方向**：明确「内层优先」只在定义点之后生效；定义点之前继续用外层表；给作用域栈 + 当前表版本的算法。

## 六、`$` / `$name` / `.name` 与主语槽

### R-23 `.name` 是 self 字段，与 dotfile/普通宾语冲突

**档：确有问题**

- **问题**：§4.8 规定 `.name` 是 self 字段，但 §4.3 说宾语是裸词或引号；`<read> .env` 因此有两种身份。
- **最短反例**：

```rill
<read> .env
```

- **依据**：§4.8「区分规则：`$name` 是变量，`$`（后不跟标识符）是 self，`.name` 是 self 字段」；§4.3「宾语：裸词或引号」；§4.16 单引号/双引号字面量。
- **为什么实现者无法唯一确定**：`.env` 是普通文件名还是 self 的 `env` 字段？如果 `.name` 全局生效，读 dotfile 必须加引号，但 §4.3/§4.16 没有说；如果 `.name` 只在 `[into]`/self 块内生效，§4.8 又没有限定作用域。
- **建议修补方向**：把 `.name` 限定在 `[into]`/self 块内，或规定 dotfile 必须用引号；在 §4.3 加一个 `.env` 的反例。

### R-24 主语槽三义：角色 / 接收者 / 字段

**档：确有问题**

- **问题**：§三 的 `[主语]` 只允许裸词/引号，§4.1 说主语是角色，但 §4.2/§4.8/§4.12 又用 `$cfg` 作接收者、`.host` 作字段路径。
- **最短反例**：

```rill
engineer <read> a.yml
$cfg<contains>debug
.host <replace> [with] prod
```

- **依据**：§三 `simple_stmt := [主语] <动词> ...`；§4.1「主语是角色 + 权限的载体」；§4.2「动词即方法」；§4.8「`.name` 是 self 字段」；§4.12 示例 `if$cfg<contains>debug=true`。
- **为什么实现者无法唯一确定**：`$cfg` 是变量、`.host` 是字段，两者都不是 §4.1 的角色；语法也没有给它们主语槽。parser 不知道 `$cfg<contains>` 是否合法；语义层也无法判断这个槽是角色、接收者还是左值。
- **建议修补方向**：把主语拆成 `[角色]` 与 `[接收者]` 两个槽，或允许 `$var`/`.path` 作为接收者并明确优先级；§三 产生式与 §4.1/§4.2 同步。

## 七、赋值、错误与边界

### R-25 `[->$变量]` 在尾随块之前，段输出在尾随块之后

**档：确有问题**

- **问题**：§三 把 `[->$变量]` 放在 `trailing_block*` 之前，§4.11 又说段输出是尾随块处理后的值；`$x` 拿到的到底是哪个值？
- **最短反例**：

```rill
<read> a.yml ->$x [into] { $ <replace> [with] 1 }
```

- **依据**：§三 `simple_stmt := ... [->$变量] trailing_block* [|> simple_stmt]`；§4.11「执行顺序：`[into]` → `[ok]/[error]` → 段输出 → `|>`」。
- **为什么实现者无法唯一确定**：语法位置暗示 `$x` 拿 `[into]` 前的原始值；段输出规则暗示 `$x` 应拿 `[into]` 后的最终值。调用方无法预测 `$x` 是原对象还是改写后的对象。
- **建议修补方向**：明确 `->$变量` 绑定的是「段输出」还是「原始语句结果」；若绑定段输出，把赋值放到 trailing_block 之后，或定义为后置赋值。

### R-26 `[into]` 失败与用户 `[error]` 的接管冲突

**档：确有问题**（与 C-5 同源）

- **问题**：§4.10 说用户写 `[error]` 覆盖默认实现，§4.11 又说 `[into]` 失败默认 break，用户 `[error]` 是否执行没有答案。
- **最短反例**：

```rill
<read> a.yml [into] { $ <replace> [with] 1 } [error] { <send> "caught" [to] user }
```

- **依据**：§4.10「用户写 `[error]` 覆盖默认实现」；§4.11「`[into]` 失败：默认 break，中断管道，后续 `[into]` 不执行」。
- **为什么实现者无法唯一确定**：`[into]` 失败时，走用户 `[error]` 块，还是直接 `break "RILL DSL ERROR"`？两条路径的段输出、下游是否执行都不同。
- **建议修补方向**：明确 `[into]` 失败是否触发用户 `[error]`；若是，删除 §4.11 的「默认 break」；若否，§4.10 加例外并说明原因。

### R-27 顶层默认 `[error]` 的行为不明确

**档：确有问题**

- **问题**：§4.10 说失败默认 break、中断管道，但顶层语句没有管道；§4.15 说顶层 break「无包围场域时中断当前语句」，下一条语句是否执行没有说。
- **最短反例**：

```rill
<read> missing.yml
<send> "after" [to] user
```

- **依据**：§4.10「不写 `[error]` 时，失败默认执行 `break "RILL DSL ERROR"`，中断管道」；§4.15「顶层独立语句的 `break`：中断最近的包围场域（管道、循环、块）；无包围场域时中断当前语句」。
- **为什么实现者无法唯一确定**：顶层没有管道；「中断当前语句」后，`<send> "after"` 是继续执行，还是整个 program 终止？如果继续，默认错误没有阻止脚本；如果终止，§4.15 应写「终止 program」而不是「中断当前语句」。
- **建议修补方向**：明确顶层默认 `[error]` 是否终止整个 program，还是仅当前语句；给顶层错误的最小例子。

### R-28 §五 的边界声明与前面的语法自相矛盾

**档：确有问题**

- **问题**：§五 说 DSL 不做类型判断、不做数组实参、不做调用绑定，但 §4.4 的状语并列、§4.13 的数组判定、§4.18 的签名绑定都需要 DSL 做这些事。
- **最短反例**：

```rill
<read> config.yml (utf-8,backup:daily,timeout:30)
each$f[in]<search>*.yml { <send> $f [to] user }
```

- **依据**：§五.3「不支持数组实参语法」、§五.5「DSL 不做类型判断」、§五.6「DSL 不做调用绑定」；§4.4「逗号分隔为并列项」「支持带参数：名称:值」；§4.13「null → error；数组 → 遍历；其他非数组 → 单元素数组」；§4.18「匹配签名：动词 + 状语 + 介词」。
- **为什么实现者无法唯一确定**：`(utf-8,backup:daily,timeout:30)` 需要 DSL 解析并列项并绑定到方法参数；`each` 需要 DSL 判数组/null/其他；函数签名需要 DSL 绑定 SVO 槽。三处边界与语法直接冲突，实现者不知道哪些逻辑属于 DSL、哪些属于底层。
- **建议修补方向**：把边界改成「DSL 不做*隐式*类型转换/绑定，但语法层负责解析槽位和字面量分类」；明确 `each` 的数组判定、状语并列、函数签名绑定属于 DSL 语义。
