## 决策项 A：裸词在 `value` 位是否合法

### A.1 当前规则（裁定前 0.1.0 正文原话）

`§三` 的产生式：

> ```ebnf
> each_clause    := "each" $变量 "[in]" expr each_body
> break_stmt     := "break" [ value ] [ "->" $变量 ]
> call_stmt      := "@" STRING arg* trailing_block* [ "|>" simple_stmt ]
> arg            := value
>
> expr           := value | verb_call | pipe
> value          := STRING | NUMBER | $变量 | .字段
> ```

`§4.13`：

> `[in]` 是普通介词，带宾语 `expr`。

`§4.15`：

> `break` 后的 `value` 只能是字面量、变量或字段，不含动词调用；要传动词结果先 `->$x`，再 `break $x`。

`§4.18`：

> `arg         := value`

`§4.1` / `§4.3`（说明裸词在其他槽是合法的）：

> - 裸词：普通主语文本；
>
> 裸词或引号。DSL 不提供数组实参语法，逗号是否表示数组由底层方法解释。

### A.2 为什么卡住

**产生式对不上示例。** `each_clause` 的 `[in]` 后面是 `expr`，`expr` 最终只能落到 `value`；`value` 的四个分支是 `STRING` / `NUMBER` / `$变量` / `.字段`，没有裸词。但 `§六 示例 5` 写的是：

```rill
each $f [in] xs {
    ...
}
```

`xs` 是裸词，不是四个分支中的任何一个，所以这个示例无法从 `§三` 推导出来。

**同一处还有“字面量”的措辞不一致。** `§4.15` 说 `break` 后的 `value` “只能是字面量、变量或字段”。如果“字面量”包含裸词，那么 `break done` 似乎合法；但 `value` 产生式又不接受裸词。两句不能同时成立。

**最短问题输入：**

```rill
each $f [in] xs
break done
@ "name" bare
```

三行的卡点分别是：

| 输入 | 卡在哪条产生式 | 两种读法 |
| --- | --- | --- |
| `each $f [in] xs` | `each_clause → expr → value`，`value` 不含裸词 | 读法一：`xs` 是字符串 `"xs"`；读法二：`xs` 是变量 `$xs` 漏写 `$` |
| `break done` | `break_stmt → value`，且 `§4.15` 说“字面量” | 读法一：`done` 是字符串；读法二：`done` 是变量；读法三：非法 |
| `@ "name" bare` | `call_stmt → arg → value` | 读法一：`bare` 是字符串实参；读法二：`bare` 是变量；读法三：非法 |

这不是“示例写错了”那么简单：`each` 的 `[in]` 语义（字符串按单元素数组执行一次）会让 `xs` 被当成字符串时仍然“能跑”，只是结果与写示例的人可能想要的变量列表不同。规范必须决定这个歧义由语法消掉，还是由作者显式写 `$xs` / `"xs"` 消掉。

### A.3 候选方案

#### 方案 A1：维持非法（严格 `value`）

**可直接替换进正文的规则文本：**

```ebnf
value := STRING | NUMBER | $变量 | .字段
```

补一句规范性说明：

> 裸词不是 `value`。`value` 位出现裸词是解析期错误 `E_BARE_VALUE`；要传文本加引号，要传变量写 `$name`。

**示例改法：**

```rill
each $f [in] "xs" { ... }     // 若 xs 是文本
each $f [in] $xs { ... }      // 若 xs 是变量
break "done"
@ "name" "bare"
```

**后果：**

- **示例改动**：1 处正文示例（`§六 示例 5` 的 `xs`）；另 2 处是简报 §三 登记的受影响位置（`break done`、`@ "name" bare`），当前正文没有这两个写法，保留本口径时需在说明或负例中固定。
- **影响阶段**：phase 3（AST 必须拒绝裸词 value）、phase 4（解析期错误码 `E_BARE_VALUE` 进错误表）、phase 8（`each` 的 fixture 改用引号或 `$变量`）、phase 9（调用实参 fixture）、phase 10/11（两个宿主共用同一语法，不能一边放宽）、phase 12（pending 清单减少 3 项）。
- **新歧义**：不新增；但必须把 `§4.15` 的“字面量”改成“`value`（`STRING` / `NUMBER` / `$变量` / `.字段`）”，否则文字仍与产生式打架。
- **可逆性**：可逆，但以后再放宽会把“解析期错误”变成合法语法，错误码和 golden 都要改；属于“收紧容易、放宽贵”的方向。

#### 方案 A2：放回 `value`（裸词即字符串）

**可直接替换进正文的规则文本：**

```ebnf
value := STRING | NUMBER | 裸词 | $变量 | .字段
```

补一句规范性说明：

> 裸词在 `value` 位按 `STRING` 处理；词面即值，不查变量、不查映射表。

**示例改法：**

```rill
each $f [in] xs      // xs 是字符串 "xs"，非数组 → 单元素数组，执行一次
break done           // "done"
@ "name" bare        // "bare"
```

**后果：**

- **示例改动**：0 处。三处写法都变成合法。
- **影响阶段**：phase 3（`value` 增加裸词分支，AST 中记为 `STRING`）、phase 4（不再报 `E_BARE_VALUE`，但可能加 lint）、phase 8（`each` 的 `xs` 变成字符串，语义是“单元素数组”，不是变量列表）、phase 9（调用实参接受裸词字符串）、phase 10/11（两宿主一致放宽）、phase 12（pending 清单减少 3 项）。
- **新歧义**：`$name` 与裸词 `name` 在 value 位并存，作者写漏 `$` 时不再报错，而是静默变成字符串；`each $f [in] xs` 会“执行一次、`$f = "xs"`”，与“遍历变量列表”的直觉不同。这是用“能跑”换掉了“可诊断”。
- **可逆性**：可逆，但以后收紧会让已有脚本从合法变非法；属于“放宽容易、收紧贵”的方向。

#### 方案 A3：按位置拆分（只给 `each [in]` 开口）

**可直接替换进正文的规则文本：**

```ebnf
each_clause := "each" $变量 "[in]" each_source each_body
each_source := expr | 裸词
```

补一句规范性说明：

> 裸词在 `each_source` 中按 `STRING` 处理；`break` 值与调用实参仍只接受 `value`。

**示例改法：**

```rill
each $f [in] xs      // 合法；xs 是字符串 "xs"
break done           // 仍非法
@ "name" bare        // 仍非法
```

**后果：**

- **示例改动**：0 处改；2 处仍非法（`break done`、`@ "name" bare`）。
- **影响阶段**：phase 3（`each_clause` 单独走 `each_source`，其他 value 位不变）、phase 4（错误码只在 `break`/调用实参保留）、phase 8（`each` 的字符串单元素语义要写清）、phase 10/11（两宿主一致）、phase 12（pending 清单剩 2 项）。
- **新歧义**：不新增词法歧义，但新增**语法不对称**：同一个裸词在 `each [in]` 合法、在 `break`/调用实参非法；读者会问“为什么这里可以”。`xs` 仍是字符串，不是变量，漏 `$` 的意图仍无法诊断。
- **可逆性**：可逆；以后要么把 `each_source` 收回 `value`（收紧），要么把另外两处也放开（放宽），两条路都要改 golden。

#### 方案 A4（补充）：显式裸字符串标记（不作为主推）

**规则文本：**

```ebnf
value := STRING | NUMBER | "^" 裸词 | $变量 | .字段
```

`^` 表示“裸词按字符串处理”，`xs` 仍是非法，必须写 `^xs` 或 `"xs"`。

**后果：**

- 示例改动 3 处；phase 2/3 新增 `^` token，phase 4/8/9/10/11/12 全受影响；不新增语义歧义，但新增符号，且与 0.1.0 现有符号表冲突（`^` 未定义）。
- **为什么不主推**：它把“裸词问题”变成“新增语法问题”，改动面比 A1/A2/A3 都大；列在这里只是为了说明“显式标记”不是免费的。

### A.4 支持两边的最强理由

**支持 A1（维持非法）的最强理由：**

`value` 是闭集，`break` 与调用实参都靠它保证“传进来的一定是可求值的东西”；裸词在 `value` 位既可能是字符串、也可能是漏写 `$` 的变量，语法层无法区分。把它判非法，错误在解析期暴露，不会让 `each $f [in] xs` 静默变成“单元素字符串循环”。这也与 `$name` 是变量、裸词是文本的既有区分一致。

**支持 A2（放回 value）的最强理由：**

`each $f [in] xs`、`break done`、`@ "name" bare` 是自然写法；Shell 宿主尤其如此，脚本里的参数、退出信息、文件名经常就是裸词。强制加引号会让 0.1.0 在“像脚本语言”这一侧失真，也会让示例和简报长期对不上。裸词作为字符串的语义可以写死为“词面即值”，并不比 `STRING` 更模糊。

**支持 A3（只给 each 开口）的最强理由：**

它只修规范自己写出来的那个示例，不把 `break`/调用实参一起放宽；`each [in]` 本来就是“数据源”位置，允许裸词字符串有独立理由（文件名、命令名、单值源），而 `break` 的值和函数实参更应该显式。代价是语法不对称，但比 A2 的“全局静默字符串化”更容易解释。

### A.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`value` 就是‘值’，所以裸词当然可以。” | `value` 是产生式名，不是语义分类；裸词只在 `subject` / `宾语` / `介宾宾语` 槽出现。 | 先看 `value := ...` 的四个分支；裸词不在其中就是非法（A1/A3 的部分位置）。 |
| “`each $f [in] xs` 里的 `xs` 是变量名。” | 没有 `$`，按 A1 是解析错误；按 A2/A3 是字符串 `"xs"`，不是变量。 | 变量写 `$xs`；文本写 `"xs"`（A1）或裸词 `xs`（A2/A3，语义为字符串）。 |
| “`break done` 的 `done` 是变量。” | 变量必须带 `$`；`done` 在 `value` 位要么非法，要么是字符串。 | 要传变量写 `break $done`；要传文本写 `break "done"`。 |
| “`@ \"name\" bare` 的 `bare` 是函数名。” | 第一个 `STRING` 才是函数名；`bare` 是 `arg`，即 `value`。 | 函数名 `"name"`；实参写 `"bare"` 或 `$bare`。 |
| “`§4.15` 说‘字面量’，所以 `done` 一定合法。” | 这句是散文，和 `value` 产生式冲突；本项就是在裁定以哪边为准。 | 若选 A1，应把“字面量”改成 `value` 的四个分支；若选 A2/A3，应明确裸词是否算字面量。 |

### A.6 结论（已裁定 A2）

> 结论：**A2（裸词放回 `value`，裸词即字符串）**。
>
> 理由摘要：裸词写法在 Shell/Agent 两侧都自然；词面即值可判定，避免 `each [in]` 的变量漏写 `$` 被当作语法错误；配套 `W-01` 提示保留诊断。其余方案保留为备选记录。

**需要回答的具体问题（每问一句话可答）：**

1. 裸词在 `value` 位应判非法、判字符串，还是只在 `each [in]` 判字符串？
2. 若判字符串，裸词 `xs` 与 `"xs"` 是否必须得到同一个 `STRING` AST 节点？
3. 是否接受为此修改 `each`、`break`、`@` 三处示例（或其中哪几处）？
4. 裸词 value 应在解析期报错，还是允许运行期按字符串处理？

## 决策项 B：`//map` 的 `<` 标记与动词定界符 `<contains>` 同字符

### B.1 当前规则（裁定前 0.1.0 正文原话）

`§二` 符号总表：

> | **映射标记符** | `'` / `` ` `` / `<` | **短词与长词之间的分隔符，紧跟在短词后**；`'`、`` ` `` 产值，`<` 产动词名 | `p'a"b` / ``cfg`configuration`` / `r<read` |

`§3.2`：

> ```ebnf
> 短词     := [A-Za-z0-9_-]+
> 标记符   := "'" | "`" | "<"
> 长词     := 标记符之后到行尾的全部字符（不含换行）
> map_entry := 短词 标记符 长词
> ```
>
> - 短词后必须**紧跟**一个标记符；短词与标记符之间不允许空格。
> - 标记符只占一个字符，且不进入长词。
> - 长词从标记符之后开始，到行尾结束；原样保留，不转义、不解析、不认引号，行尾是唯一终止边界。
> - `'` 与 `` ` `` 是值类标记：展开为 `STRING` 节点。
> - `<` 是动词类标记：展开为 `VERB_NAME` token，用于 `<>` 内单词。

`§4.17`：

> - 标记符：`'`、`` ` ``、`<`，只占一个字符，不进入长词。
> - 长词：标记符之后到行尾的全部字符，原样保留，不转义、不解析、不认引号；行尾是唯一终止边界。
> - 值类标记 `'` / `` ` `` 展开为 `STRING` 节点；动词类标记 `<` 展开为 `VERB_NAME` token。
>
> - `<>` 内的单词和反引号包裹的裸词共用一张映射表查表展开；其他裸词不查。
> - 动词类映射 `r<read` 使 `<r>` 等价于 `<read>`，AST 中为同一 `VERB_NAME`。

`§三` 的 `verb_call`：

> `verb_call      := [ subject ] "<" 动词 ">" 宾语 [ "(" 状语 ")" ] prep_phrase*`

### B.2 为什么卡住

最短输入：

```text
//map{
r<read
}
```

在 `r<read` 这一行，至少有两种切法：

| 切法 | 切分 | 结果 |
| --- | --- | --- |
| 切法一：map_entry | 短词 `r` + 标记符 `<` + 长词 `read` | 合法映射项；`<r>` 展开为 `<read>` |
| 切法二：裸词 + 动词 | 裸词 `r` + 动词 `<read>`（后面的 `}` 不是 `>`，动词没有闭合） | 不是 `map_entry`；map 区块解析失败，或词法器把 `read` 吞成动词名 |

如果再写 `//map{ r<read> }`（单行形式），还会出现第三种冲突：按 `§3.2`，标记符 `<` 后的长词到行尾结束，所以长词是 `read> }`，把区块的 `}` 也吞掉；而动词切法会把 `read` 当成动词、`>` 当成动词闭合。两种切法都能“看起来合理”，但产生不同的映射表；单行 `//map{}` 还与“行尾是唯一终止边界”直接冲突。

**根因是两句话没有给优先级：**

- `§3.2` 说“长词从标记符之后开始，到行尾结束”，这暗示“map 行内 `<` 是标记符”；
- `§4.17` 说“`<>` 内的单词……查表展开”，这暗示“`<...>` 是动词”；
- `§三` 的 `verb_call` 又规定 `<` 是动词开界。

规范没有说明“在 `map_block` 的行内，`<` 是否优先于 `verb_call` 的 `<`”，也没有说明 lexer 是否要为 map 行切换模式。于是同一个 `<` 在两个产生式里各自成立，这就是词法消歧风险。

### B.3 候选方案

#### 方案 B1：上下文优先（保留 `<`，map 行进入行模式）

**可直接替换进正文的规则文本：**

```ebnf
map_entry := 短词 标记符 长词
标记符   := "'" | "`" | "<"
```

补一句规范性说明：

> 在 `map_block` 内，短词后的第一个非短词字符一律按标记符读；该行不再启动动词扫描；标记符之后到行尾为长词。

**示例：**

```text
//map{
r<read
}
<r> a.yml
```

**后果：**

- **示例改动**：0 处。`r<read` 保持原样；只需补一条“map 行内 `<` 优先”的说明和一个反例（正文 `<read>` 仍是动词）。
- **影响阶段**：phase 2（lexer 增加 map-block 行模式）、phase 3/4（map_entry 与 `<r>` 展开）、phase 5（展示/压缩）、phase 10/11（两宿主同一 lexer）、phase 12（相关 golden）。
- **新歧义**：map 块内不新增；map 块外 `<` 仍是动词，语义由上下文决定。风险转为“读者要知道 map 行模式”，不是词法二义。
- **可逆性**：可逆；以后换标记符只需改 map 行，不影响正文语法。

#### 方案 B2：换标记符（保留动词映射，改用非 `<` 字符）

**可直接替换进正文的规则文本：**

```ebnf
标记符 := "'" | "`" | "="
map_entry := 短词 标记符 长词
```

动词映射示例改为：

```text
//map{
r=read
}
<r> a.yml
```

**后果：**

- **示例改动**：3 处出现（`§二` 符号表示例、`§4.17` 声明块、`§4.17` 引用条目），全部 `r<read` → `r=read`；规则文本 4 处（`§二` 符号表行、`§3.2` 的 `标记符` 产生式与说明、`§4.17` 词法条、`§4.17` 引用条）。
- **影响阶段**：phase 2（lexer 去掉 `<` 标记分支）、phase 3（map_entry AST 的标记 token 变 `=`）、phase 4（map 表）、phase 5（展示）、phase 10/11、phase 12。
- **新歧义**：`=` 在正文里也用于 `debug=true` 与赋值 `->`，但 map 行的“短词后第一个非短词字符”仍可唯一切分；风险从“与动词 `<` 冲突”转为“与等号视觉混淆”。
- **可逆性**：可逆；已写 `r<read` 的脚本/golden 需要迁移。

#### 方案 B3：取消动词映射（`//map` 只做值映射）

**可直接替换进正文的规则文本：**

```ebnf
标记符 := "'" | "`"
map_entry := 短词 标记符 长词
```

删除 `§4.17` 的“动词类标记 `<` 展开为 `VERB_NAME` token”和 `r<read` 示例；动词一律写全名 `<read>`。

**后果：**

- **示例改动**：3 处删除（`§二` 符号表示例、`§4.17` 声明块、`§4.17` 引用条目）；规则文本 3 处（`§二` 符号表行、`§3.2` 标记符产生式与说明、`§4.17` 词法与引用条）。
- **影响阶段**：phase 2（lexer 不再有 `<` 标记）、phase 3（`VERB_NAME` 映射不存在）、phase 4/5/10/11、phase 12。
- **新歧义**：不新增；`<` 只做动词定界符，词法最干净。代价是失去动词压缩，`<r>` 成为未知动词/错误。
- **可逆性**：可逆，但恢复动词映射要重加语法与 golden；使用 `<r>` 的脚本会失效。

#### 方案 B4：独立 `//verbs{}` 区块

**可直接替换进正文的规则文本：**

```ebnf
header         := map_block | fn_block | verb_map_block
verb_map_block := "//verbs" "{" verb_entry* "}"
verb_entry     := 短词 "<" 长词
```

`//map{}` 只允许 `'` / `` ` ``；`//verbs{}` 只允许 `<`。

**示例：**

```text
//verbs{
r<read
}
```

**后果：**

- **示例改动**：3 处（`§二` 符号表示例、`§4.17` 声明块、`§4.17` 引用条目，`r<read` 从 `//map` 移到 `//verbs`）；规则文本 4 处（`§二`、`§3.1`、`§3.2`、`§4.17`）。
- **影响阶段**：phase 2（新 header token）、phase 3/4（两套表）、phase 5、phase 10/11、phase 12。
- **新歧义**：不新增；值映射与动词映射分块，`/` 头规则要同时识别 `map` / `fn` / `verbs`。代价是新增一个区块类型和一套表。
- **可逆性**：可逆；合并回 `//map` 需要迁移。

### B.4 支持两边的最强理由

**支持 B1（保留 `<`、map 行模式）的最强理由：**

`<` 已经是 RILL 的动词符号，`r<read` 读起来就是“短名 `r` 映射到动词 `read`”，不需要引入新字符；示例、符号表、已写的规范段落都不用改。只要规定 map 行内 `<` 优先于动词扫描，词法就没有二义，代价只是 lexer 知道“当前在 map 块内”。

**支持 B2/B3/B4（不再让 `<` 在 map 行内兼任标记）的最强理由：**

`<` 是 0.1.0 最重要的定界符；让同一个字符在 map 行内改当分隔符，是把上下文敏感性藏进了词法器。换标记（B2）、取消动词映射（B3）或独立区块（B4）都能让词法在任意位置用同一套 `<` 规则，读者也不会把 `r<read` 误读成动词调用。B3 最彻底，B2 改动最小，B4 命名空间最干净。

### B.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`//map{ r<read }` 里的 `<read>` 是一个动词调用。” | 在 map 行内，按 B1 它是标记符 `<` + 长词 `read`；按 B3 这行根本不合法。 | map 行内先按 `map_entry` 切；只有 map 块外才把 `<read>` 当动词。 |
| “`<r>` 就是动词 `<r>` 本身。” | `<r>` 是引用，查 map 表后等价于 `<read>`；AST 是 `VERB_NAME` `read`。 | 先查可见映射链，再得到动词名；不要跳过映射。 |
| “`<` 在 map 里和 `<contains>` 的 `<` 是同一个 token。” | 一个是 `map_entry` 的标记符，一个是 `verb_call` 的定界符；字符相同，角色不同。 | 按所在产生式判断：`map_entry` 内是标记符，`verb_call` 内是定界符。 |
| “`r<read` 写在正文里也是映射定义。” | 映射定义只在 `//map{}` 块内；正文里 `r <read>` 是主语 + 动词。 | 定义放 `//map{}`；正文只写 `<r>` 引用。 |

### B.6 结论（已裁定 B1）

> 结论：**B1（上下文优先，`//map{}` 行内进入行模式）**。
>
> 理由摘要：保留 `<` 作动词映射，不引入新符号；map 行内按“短词 + 第一个非短词字符 + 行尾”切分，切分唯一；非法标记与正文未闭合动词分别由 `E-01`/`E-02` 兜底。其余方案保留为备选记录。

**需要回答的具体问题（每问一句话可答）：**

1. `//map` 行内的 `<` 是否应一律优先作标记符？
2. 是否接受删除动词映射，或把动词映射改用非 `<` 的标记/独立区块？
3. 词法器是否应使用“map 块行模式”，还是保持全局 `<` 扫描？
4. 若保留 `<` 标记，`//map{ r<read }` 与正文 `<read>` 是否必须由同一 lexer 的两种模式处理？

## 决策项 C：0.1.1 正文与“同一份语法、两种宿主”的 7 处冲突

> 来源：roadmap §3.3.3。按正文出现顺序排列；每条只描述冲突与候选规则，不预设宿主优先级。
> 跨组耦合见 §0.2；C6 与 A 的关系（X-2）是本组最容易漏看的一条。

### C1：主语里的“角色 + 权限”是 Agent 形态

#### C1.1 当前规则（正文原话）

`§4.1`：

> 主语可省略（祈使句），省略时默认当前角色。主语槽允许四种形态：
>
> - 角色：权限载体，由内核角色清单定义；

`§4.1` 末段：

> `类型:值`（如 `file:/etc/passwd`）是裸词的一种形式。语法层不拆分、不校验；整体存入 AST，由宿主加载期按 TypeRegistry / RoleRegistry 拆分与判定。

`§五` 宿主接口表：

> | RoleRegistry | 角色名 + 权限 | 加载期校验主语角色 |

`§五` 加载期段：

> 加载期 = parse 完成之后、exec 之前。解析器核心只产 AST，不查注册表、不拆分 `类型:值`、不校验角色/动词/类型。两个宿主得到同一 AST，合法性差异在加载期体现。

`§4.1` 示例：

```rill
engineer <read> config.yml
auditor <review> docs/api.md
```

#### C1.2 为什么卡住

最短输入：

```rill
engineer <read> config.yml
```

Shell profile 没有 RoleRegistry；`engineer` 既可能被读成“角色名”，也可能被读成“普通裸词主语”，还可能是 OS 用户名，语法层无法区分。省略主语的写法同样没有落点：

```rill
<read> config.yml
```

“省略时默认当前角色”在 Shell 侧没有“当前角色”这个东西。

| 读法 | 结果 |
| --- | --- |
| `engineer` 是角色，必须查 RoleRegistry | Shell profile 没有角色表，加载期无表可查；要么补伪角色表，要么报错 |
| `engineer` 是裸词主语 | 语法通过，但 §4.1 的“权限载体”语义丢失，`engineer` 与普通文本没有区别 |
| `engineer` 是 OS 用户 | 需要 profile 把角色名映射到用户；规范没有这条映射，也没有规定省略主语时的默认用户 |

#### C1.3 候选方案

##### 方案 C1-1：保留角色槽，Shell 提供角色→用户映射

可直接替换 `§4.1` 主语段的规则文本：

```ebnf
subject := role | 裸词 | 引号 | $变量
role    := 裸词        // 由 HostProfile 提供的角色表解析
```

补一句规范性说明：

> RoleRegistry 由 HostProfile 提供：Agent profile 提供内核角色表；Shell profile 提供角色名到 OS 用户的映射，缺省角色 = 当前 OS 用户。

```text
Agent profile: engineer → RoleRegistry["engineer"]
Shell profile: engineer → OS user "engineer"（缺省 = 当前用户）
```

后果：

- **示例改动**：0 处。`engineer` / `auditor` 仍是角色名。
- **影响阶段**：phase 4（HostProfile 提供角色表）、phase 10/11（各自映射）、phase 12（双 profile 一致）。
- **新歧义**：`role` 与裸词同形，语法层本来就不可区分；歧义没有新增，只是把解释推到 profile。
- **可逆性**：可逆。撤回时删掉 Shell 映射即可，AST 不变。

##### 方案 C1-2：抽象成 `principal`

可直接替换 `§4.1` 主语段的规则文本：

```ebnf
subject    := principal | 裸词 | 引号 | $变量
principal  := 裸词        // Agent: 角色名；Shell: OS 用户名
```

补一句规范性说明：

> 省略主语时取 HostProfile 的默认 principal；parser 只产出 `principal` 槽，不判断它是角色还是用户。

```text
Agent profile: principal = RoleRegistry["engineer"]
Shell profile: principal = OS user "engineer"（缺省 = 当前用户）
```

后果：

- **示例改动**：0 处。`engineer` / `auditor` 仍落在 `principal` 槽。
- **影响阶段**：phase 3（`subject` 产生式增加 `principal` 分支）、phase 4（profile 解析）、phase 10/11、phase 12。
- **新歧义**：`principal` 与普通裸词主语同形；一个裸词到底是 principal 还是普通文本，仍由 profile 决定。
- **可逆性**：可逆。把 `principal` 合并回裸词即可，但已产出的 AST 槽名要迁移。

##### 方案 C1-3：从语法移除角色

可直接替换 `§4.1` 主语段的规则文本：

```ebnf
subject := 裸词 | 引号 | $变量
```

补一句规范性说明：

> 删除“角色”槽与“省略时默认当前角色”。主语只是文本；身份与权限由 HostProfile 在执行前绑定，DSL 不表达 principal。

```rill
engineer <read> config.yml   // 裸词主语；权限由 HostProfile 绑定
```

后果：

- **示例改动**：0 处改写；`engineer <read>` 仍是合法的裸词主语，但 `§4.1` 与 `§六 示例 8` 的“角色”读法要改说明 2 处。
- **影响阶段**：phase 3（`subject` 少一个语义分支）、phase 4（RoleRegistry 从必选变可选）、phase 10/11、phase 12。
- **新歧义**：Agent 侧角色只能靠动词/工具封装，脚本不能按角色分流；同一裸词在两宿主含义不同。
- **可逆性**：可逆。重新引入 `principal` 需改 AST 槽与 phase 3 产生式。

#### C1.4 支持两边的最强理由

**支持 C1-1 / C1-2 的最强理由：**

角色是 RILL 既有语义（`§4.1`、`§六 示例 8`），Agent 宿主需要它；`principal` 能在不改“主语槽”这一 AST 结构的前提下，让 Shell 映射 OS 用户、Agent 映射角色，保留“省略主语 = 当前身份”的统一直觉。C1-1 改动最小，C1-2 命名最诚实。

**支持 C1-3 的最强理由：**

语言核心不应知道身份。Shell 的用户模型与 Agent 的角色模型不是同一个概念，强行用一个名词覆盖，只会让加载期规则变得不可解释。把权限完全交给 HostProfile，parser 不引入任何身份概念，最符合“同一份语法、差异只在能力层”的约束；代价是 Agent 的“角色”从语法降为宿主约定。

#### C1.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`engineer` 一定是角色。” | 它是裸词形态；是不是角色由 profile 决定。 | 先看 profile：Agent 查角色表，Shell 查用户映射。 |
| “省略主语 = 没有权限。” | 省略只是不写，加载期仍要绑定默认身份。 | 省略 = 取 profile 的默认 principal/角色。 |
| “Shell 没有角色，所以 `engineer <read>` 非法。” | 合法性由 profile 决定，不是语法层。 | C1-1/C1-2 下由 profile 映射；C1-3 下是普通裸词主语。 |

### C2：“脚本无权声明授权”与 Shell 能力声明

#### C2.1 当前规则（正文原话）

`§五.1`：

> 不支持授权头：工具白名单和权限由内核角色配置控制，脚本无权声明。

`§五` 宿主接口表：

> | RoleRegistry | 角色名 + 权限 | 加载期校验主语角色 |

#### C2.2 为什么卡住

最短输入：

```rill
<run> "git" "status"
```

Shell 宿主要执行进程，就必须有 `proc` 能力。规范只说“脚本无权声明”，没有说 Shell 侧的能力边界从哪里来。两种读法：

| 读法 | 结果 |
| --- | --- |
| 脚本必须由外部 manifest 授权 | 规范没有 manifest 的形状、位置与加载时机；仓库里也没有这个文件 |
| 脚本不声明，Shell 按当前 OS 用户权限直接执行 | 等于没有能力边界；`§五.1` 的“白名单和权限”在 Shell 侧落空 |

#### C2.3 候选方案

##### 方案 C2-1：维持“脚本不声明”，能力由 HostProfile 声明

可直接替换 `§五.1` 的规则文本：

> 不支持脚本内授权声明：能力边界由 `HostProfile` 在加载期声明并校验。Agent 宿主用内核角色/工具白名单；Shell 宿主用 manifest 或 CLI 参数（如 `--allow=proc,fs`）。DSL 无授权语法，脚本不可自证能力。

```text
Shell: rill run --allow=proc,fs script.rill
Agent: 内核配置声明 proc/fs
```

后果：

- **示例改动**：0 处。
- **影响阶段**：phase 4（profile 声明与校验）、phase 10（manifest/CLI）、phase 11（内核配置）、phase 12。
- **新歧义**：同一脚本在两宿主需要两份外部声明，脚本本身不可移植自证。
- **可逆性**：可逆，只改加载期与文档。

##### 方案 C2-2：新增 `//caps{}` 需求声明（不授予）

可直接替换 `§三` header 与 `§五.1` 的规则文本：

```ebnf
header     := map_block | fn_block | caps_block
caps_block := "//caps" "{" cap_name* "}"
cap_name   := 裸词
```

补一句规范性说明：

> `//caps` 只声明“需要哪些能力”，不授予；HostProfile 可拒绝（加载期错误）或忽略；缺省为空 = 不额外申请。两宿主共用同一语法，解释由 profile 决定。

示例：

```text
//caps{
proc fs
}
<run> "git" "status"
```

后果：

- **示例改动**：1 处（新增 `//caps` 示例）；规则文本 3 处（`§三` header、`§3.1` 头词法、`§五.1`）。
- **影响阶段**：phase 2（新 header token）、phase 3（header AST）、phase 4（profile 校验）、phase 10/11、phase 12。
- **新歧义**：“声明需求”与“授予权限”容易被读成同一件事；能力名需要两宿主映射表。
- **可逆性**：可逆，删 `//caps` 即可；已写该头的脚本需迁移。

##### 方案 C2-3：能力声明放 shebang/CLI，不进语法

可直接替换 `§五.1` 的规则文本：

> 脚本不声明授权，也不新增授权语法。Shell 宿主从 shebang 或 CLI 读取能力声明（如 `#!/usr/bin/env rill --allow=proc,fs`）；Agent 宿主从内核配置读取。两条路径都不进入 DSL 语法。

```text
#!/usr/bin/env rill --allow=proc,fs
<run> "git" "status"
```

后果：

- **示例改动**：0 处（若要固定写法，可加 1 个 shebang 示例）；规则文本 2 处（`§五.1`、`§五` 宿主接口段）。
- **影响阶段**：phase 4（profile 读取）、phase 10（shebang/CLI）、phase 11（内核配置）、phase 12。
- **新歧义**：shebang 是文件级元数据，Agent 侧忽略，同一文件两宿主行为不同。
- **可逆性**：可逆，只改宿主加载逻辑。

#### C2.4 支持两边的最强理由

**支持 C2-1 的最强理由：**

它与 `§五.1` 原文最一致：脚本不可自我提权，安全边界清晰，Agent 侧零改动。能力声明留在宿主，DSL 不被授权语法污染，也符合“脚本无权声明”的原始意图。

**支持 C2-2 / C2-3 的最强理由：**

Shell 脚本必须能描述自己的依赖，否则同一脚本换机器就跑不起来。声明“需求”不等于“授权”，既保留宿主否决权，又让脚本可读可移植；C2-2 用同一语法覆盖两宿主，C2-3 用 OS 惯例避免新增语法，两者都绕开了“脚本内授权”的安全指责。

### C3：`[error]` 只承载字符串，装不下 stderr 与退出码

#### C3.1 当前规则（正文原话）

`§4.10`：

> `[error]`：`ok == false` 时触发，`$ =` 错误信息字符串，默认值 `"RILL DSL ERROR"`，无结构化字段。

`§4.8` 表：

> | `[error]` 块内 | 错误信息字符串 |

`§4.11`：

> 失败且有 `[error]` → `[error]` 执行后 `$` 的最终值；若块内 break 则中断当前场域。

#### C3.2 为什么卡住

最短输入：

```rill
<run> "sh" "-c" "echo boom >&2; exit 3" [error] {
    <send> $ [to] user
}
```

进程实际产生了 `stderr = "boom"` 与 `code = 3`，但 `$` 只能是错误信息字符串；脚本既拿不到 `code`，也拿不到 `stderr`。另一个更短的写法直接暴露字段缺失：

```rill
<run> "false" [error] {
    if .code == 1 { <send> "retry" [to] user }
}
```

`$` 是字符串，`.code` 没有定义，条件无法归约成可判定的值。

| 读法 | 结果 |
| --- | --- |
| 宿主把 code/stderr 压进错误串 | 可读不可编程；脚本无法按退出码分支，也无法区分 stdout 与 stderr |
| `$` 应是结构化对象 | 与 `§4.10`“错误信息字符串、无结构化字段”直接冲突 |

#### C3.3 候选方案

##### 方案 C3-1：维持字符串，结构化信息走 `host_meta`

可直接替换 `§4.10` 的规则文本：

> `[error]` 的 `$` 恒为 `STRING`，默认 `"RILL DSL ERROR"`，不含结构化字段。退出码、stderr、stdout 等宿主信息放在 `ExecOutcome.host_meta`，只对宿主适配器/诊断可见，DSL 脚本不能读取。

```rill
<run> "false" [error] {
    <send> $ [to] user      // 只有错误串；code/stderr 在 host_meta
}
```

后果：

- **示例改动**：0 处。
- **影响阶段**：phase 6（`ExecOutcome.host_meta`）、phase 7（`[error]` 段输出）、phase 10/11、phase 12。
- **新歧义**：同一失败在 Shell 侧信息丰富、DSL 侧不可见，脚本无法按退出码分支。
- **可逆性**：可逆；以后改成对象要改 `$` 的类型与段输出。

##### 方案 C3-2：`$` 改为错误对象

可直接替换 `§4.8` 表与 `§4.10` 的规则文本：

```ebnf
[error] 的 $ := { message: STRING, code: NUMBER?, stderr: STRING? }
```

补一句规范性说明：

> `$` 是对象；`.message` 恒有，`.code` / `.stderr` 由宿主提供，缺失为 `null`；`<send> $` 按 `message` 字符串化。

示例：

```rill
<run> "sh" "-c" "exit 3" [error] {
    if .code == 3 { <send> "retry" [to] user }
}
```

后果：

- **示例改动**：1 处新增（`.code` 用法）；既有 `<send> $` 的语义要复核 1 处；规则文本 3 处（`§4.8` 表、`§4.10`、`§4.11` 段输出）。
- **影响阶段**：phase 6（错误对象值）、phase 7（`[error]` 段输出与字符串化）、phase 10/11、phase 12。
- **新歧义**：`$` 从字符串变对象，`<send> $` 与 `[error]` 的默认值都要重新定义；空对象在 truthy/falsy 里是 falsy，可能与“失败”语义混淆。
- **可逆性**：可逆，但已写 `<send> $` 的脚本语义会变。

##### 方案 C3-3：双通道，`$` 保持字符串并预置 `$code` / `$stderr`

可直接替换 `§4.8` 表与 `§4.10` 的规则文本：

> `[error]` 块内 `$` 恒为 `STRING`；另预置只读 `$code`（`NUMBER` 或 `null`）与 `$stderr`（`STRING` 或 `null`）；宿主不提供时为 `null`。这些名字在 `[error]` 块内保留，用户不可赋值。

```rill
<run> "sh" "-c" "exit 3" [error] {
    if $code == 3 { <send> "retry" [to] user }
}
```

后果：

- **示例改动**：0 处；规则文本 3 处（`§4.8` 表、`§4.10`、`§4.7` 变量/保留名）。
- **影响阶段**：phase 6（保留变量）、phase 7（`[error]` 求值）、phase 10/11、phase 12。
- **新歧义**：新增两个保留变量名，与用户 `$code` 冲突；`$stderr` 是文本还是字节取决于 C6（X-3）。
- **可逆性**：可逆，删除保留名即可；已写同名用户变量会受影响。

#### C3.4 支持两边的最强理由

**支持 C3-1 的最强理由：**

保持 `$` 类型稳定（字符串），不破坏既有 `<send> $` 与默认错误串；结构化信息属于宿主能力，DSL 不应把 Shell 的进程模型写进核心。这也是 `§4.10` 现有文字的直接延续。

**支持 C3-2 / C3-3 的最强理由：**

退出码与 stderr 是脚本语言的基本诊断面；只给字符串会迫使所有宿主把结构压平，丢失可编程性。C3-2 给完整对象，语义最清楚；C3-3 用两个保留名换最小的语法改动，`$` 的字符串契约不破。

#### C3.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`$` 是错误对象，可以直接 `.code`。” | 只有 C3-2 成立；C3-1/C3-3 下 `$` 仍是字符串。 | 先看选定方案，再决定 `.code` 是否存在。 |
| “`[error]` 的 `$` 等于工具返回值。” | 它是错误通道，不是 `{value, ok}` 或 `ProcessResult`。 | `$` 只承载错误信息；结构化字段另设通道。 |
| “stderr 一定等于错误串。” | 规范只保证 `$` 是错误信息，不保证同源。 | stderr 是否等于 `$` 由宿主决定。 |

### C4：顶层失败没有定义退出码

#### C4.1 当前规则（正文原话）

`§4.10`：

> 顶层语句失败：中断整个 program；管道内失败：中断管道；块内失败：中断当前块。

`§4.11`：

> 失败且无 `[error]` → 默认 `break "RILL DSL ERROR"`，中断当前场域。

`§4.15`：

> 任何区块内触发 break 都中断当前管道；管道内中断管道，块内中断块，顶层中断整个 program。

#### C4.2 为什么卡住

最短输入：

```rill
<run> "false"
```

在 Shell 里执行 `rill run s.rill; echo $?`，规范没有说应该得到什么。两种读法都“说得通”：

| 读法 | 结果 |
| --- | --- |
| 顶层失败 = 进程非 0 | 具体是 1、127 还是 `false` 的 1，没有定义；CI 无法写成稳定断言 |
| 顶层失败 = DSL 已处理，进程仍 0 | 调用方无法判断脚本成败，Shell 宿主失去意义 |

`break "x"` 在顶层同样没有退出码规则。

#### C4.3 候选方案

##### 方案 C4-1：只留宿主映射，不写死数字

可直接替换 `§4.10` 的规则文本：

> 0.1.0 不定义数字退出码。DSL 只定义“成功 / 未处理失败”二态；Shell 宿主把未处理失败映射为非 0，Agent 宿主映射为工具错误。具体数字由 HostCapabilities 决定，正文不写死。

```text
rill run s.rill; echo $?   // 只保证非 0，具体数字由宿主决定
```

后果：

- **示例改动**：0 处；规则文本 2 处（`§4.10`、`§4.11`/`§4.15`）。
- **影响阶段**：phase 7（顶层失败终止）、phase 10（数字映射）、phase 12；phase 11 只保留 `ok == false`。
- **新歧义**：同一脚本在不同 Shell 可能返回不同非 0 码，测试只能断言“非 0”。
- **可逆性**：可逆，补数字表即可。

##### 方案 C4-2：最小数字表

可直接替换 `§4.10` 的规则文本：

```text
成功结束（无未处理失败）        → 0
未处理失败（含默认 break）      → 1
break $x，且 $x 为 0..255 数字   → exit code = $x
```

补一句规范性说明：

> 其余值按 1 处理；Agent 宿主忽略数字，只保留 `ok == false`。

示例：

```rill
<run> "false"          // Shell 退出码 1
break 3                // Shell 退出码 3
```

后果：

- **示例改动**：1 处（`break 3`）；规则文本 2 处。
- **影响阶段**：phase 7、phase 10、phase 11（忽略数字）、phase 12。
- **新歧义**：`break "done"` 的字符串值如何映射（按 1？）；与 C3 的 `code` 字段关系要写清（X-4）。
- **可逆性**：可逆；已依赖数字的脚本在撤回时会变。

##### 方案 C4-3：显式退出动词

可直接替换 `§4.10` 的规则文本：

> 顶层失败默认退出码 1；用户可用 `<exit> N`（动词，由 Shell 宿主提供）显式指定；Agent 宿主把 `<exit>` 映射为终止当前 program，不产生 OS 退出码。

```rill
<exit> "3"
```

后果：

- **示例改动**：0 处；规则文本 2 处（`§4.10`、`§五` 宿主接口动词表）。
- **影响阶段**：phase 7、phase 10、phase 12；另外影响 VerbRegistry（`<exit>` 的签名）。
- **新歧义**：`<exit>` 是普通动词还是控制流；与 `break` 场域的关系需要定义。
- **可逆性**：可逆，删动词即可；已写 `<exit>` 的脚本失效。

#### C4.4 支持两边的最强理由

**支持 C4-1 的最强理由：**

0.1.0 已明确“宿主接口”分层，数字码是 OS 细节；写死会迫使 Agent 侧伪造退出码，且不同 Shell 的信号、127、命令未找到等语义无法统一。只定义二态，最符合“差异只在能力层”。

**支持 C4-2 / C4-3 的最强理由：**

脚本语言必须能被 CI 判成败；没有稳定退出码，Shell 宿主无法验收。C4-2 给最小可预测规则，调用方可以写 `if rill run x; then`；C4-3 用动词提供显式控制，不把数字规则写死进核心。

#### C4.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “顶层失败 = 退出码 1。” | 只有 C4-2 成立；C4-1 下不保证具体数字。 | 先看是否采用数字表；未采用时只保证非 0。 |
| “`break "done"` 会把 `done` 当退出码。” | 字符串不是合法退出码。 | C4-2 按 1；C4-3 需 `<exit>`。 |
| “Agent 也有退出码。” | Agent 没有 OS 退出码，只有 `ok`/错误。 | 退出码是 Shell 宿主的映射，不是 DSL 值。 |

### C5：`|>` 是 DSL 值管道，与 OS 管道未区分

#### C5.1 当前规则（正文原话）

`§4.6`：

> `|>` 是纯数据流变换的主路径。前一步输出即后一步的隐式输入。

> 管道只传 `value`，不传 `{value, ok}`。每段执行后得到 `{value, ok}`；`ok` 在段内由 `[ok]/[error]` 消费。

`§4.2`：

> 尖括号包裹，开放——由框架提供的方法集决定。一句一动词，多动词必须拆成管道。

#### C5.2 为什么卡住

最短输入：

```rill
<run> "cat" "a.txt" |> <run> "wc" "-l"
```

Shell 读者会把它读成 OS 管道：`cat` 的 stdout 进 `wc` 的 stdin。但 `§4.6` 说 `|>` 传的是 DSL `value`，且 `ok` 不向下传；`<run>` 的进程 stdin 是否被连接，规范没有说。两种读法：

| 读法 | 结果 |
| --- | --- |
| `|>` 就是 OS 管道 | `wc` 应从 stdin 读；但 RILL 的 `|>` 不传 `ok`，也不定义 stdout/stderr 的取舍 |
| `|>` 只传 DSL 值 | `wc` 收到的是一个值，不是 stdin；进程 stdin 为空，结果不是用户预期 |

#### C5.3 候选方案

##### 方案 C5-1：澄清并禁止隐式 OS 管道

可直接替换 `§4.6` 的规则文本：

> `|>` 只连接 DSL 语句，传递的是 `value`，不是进程 stdin/stdout；它不创建 OS 管道，也不传递 `ok`/退出码。进程间数据传递必须由 `ProcessCapability` 的显式参数或 `ProcessResult` 字段表达。

```rill
<run> "sh" "-c" "cat a.txt | wc -l"   // OS 管道写在命令串里
<run> "cat" "a.txt" |> <run> "wc" "-l"   // DSL 值管道，不接进程 stdin
```

后果：

- **示例改动**：0 处；规则文本 2 处（`§4.6`、`§五` 宿主接口）。
- **影响阶段**：phase 8（管道语义）、phase 10（进程能力）、phase 12。
- **新歧义**：不新增；只是把“`|>` 不是 shell 管道”写明。
- **可逆性**：可逆，纯文档澄清。

##### 方案 C5-2：新增 OS 管道运算符 `|`

可直接替换 `§三` 与 `§4.6` 的规则文本：

```ebnf
simple_stmt := verb_call trailing_block* [ ( "|>" | "|" ) simple_stmt ]
```

补一句规范性说明：

> `|>` = DSL 值管道；`|` = 进程 stdout→stdin，仅当两侧动词都声明 `process` 能力，否则加载期报错；`|` 不经过 `$`。

示例：

```rill
<run> "cat" "a.txt" | <run> "wc" "-l"
```

后果：

- **示例改动**：1 处新增；规则文本 3 处（`§三`、`§4.6`、`§五`）。
- **影响阶段**：phase 2（新符号）、phase 3（`simple_stmt` 分支）、phase 8、phase 10、phase 12。
- **新歧义**：`|` 与 `|>` 视觉相近；`||` 是否逻辑或需要明确排除。
- **可逆性**：可逆，删 `|` 即可；已写 `|` 的脚本需迁移。

##### 方案 C5-3：让 `|>` 对进程动词做字节投影

可直接替换 `§4.6` 的规则文本：

> 当 `|>` 的下游动词声明 `process.stdin` 时，上游段输出按以下规则投影为 stdin：
>
> | 上游值 | stdin |
> | --- | --- |
> | `STRING` | UTF-8 字节 |
> | `Bytes` | 原样字节 |
> | 其他 | 加载期错误 |
>
> 上游为进程动词时，默认取 `stdout`，不取 `stderr`；`stderr` 只能经 C3 的错误通道读取。

后果：

- **示例改动**：0 处新增；既有示例语义改变，需复核 1 处；规则文本 3 处（`§4.6`、`§五`、值类型章）。
- **影响阶段**：phase 6（值投影）、phase 7（段输出）、phase 8、phase 10、phase 12；依赖 C6（X-1）。
- **新歧义**：`|>` 变成“有时是值、有时是 stdin”，与“管道只传 value”需重写；`Bytes` 未定义时（C6-2）只能投影 `STRING`。
- **可逆性**：可逆，撤回投影规则即可，但脚本语义会变。

#### C5.4 支持两边的最强理由

**支持 C5-1 / C5-2 的最强理由：**

`§4.6` 已经明确 `|>` 只传 value、不传 `ok`；保持它与 OS 管道分离，读者不会误以为 DSL 管道能替代 shell 管道。C5-2 给需要进程管道的人一个显式符号，而不是偷偷改变 `|>` 的语义。

**支持 C5-3 的最强理由：**

Shell 宿主的核心用例就是 `cat a | wc -l`；如果 `|>` 不能接进程 stdin，Shell 侧必须发明另一套调用形态，脚本会变得不像脚本。让 `|>` 对进程动词做字节投影，能复用现有语法，代价是给 `|>` 增加一条宿主相关语义。

### C6：缺少二进制与流值

#### C6.1 当前规则（正文原话）

`§4.17`：

> 值类标记 `'` / `` ` `` 展开为 `STRING` 节点；动词类标记 `<` 展开为 `VERB_NAME` token。

> 展示态展开时，值类长词按双引号规则输出：含空格、`"`、`\` 或语义符号时加双引号并转义，否则输出原文。

`§4.16`：

> 双引号 `"..."` | 字面量，支持转义：`\"` `\\`。可包含单引号。不做插值——`$var` 是字面文本。

`§4.12`：

> falsy：`null`、`false`、`0`、`""`、`[]`、`{}`（来自工具结果的空对象值）。

这个列表里没有字节或流。

#### C6.2 为什么卡住

最短输入：

```rill
<read> "logo.png" |> <write> "copy.png"
```

如果 `read` 返回字节，`|>` 会把字节传给 `write`；`[ok]` 的 `$` 也可能是字节。但 `§4.17` 只定义了 `STRING` 节点与“按双引号规则输出”的展示态，字节值既不能写进 `//map`，也没有展示/压缩规则。两种读法：

| 读法 | 结果 |
| --- | --- |
| 宿主把字节强转 `STRING` | 二进制被破坏；展示/压缩/拼接都可能改写内容 |
| 字节不是合法 RILL 值 | `<read> logo.png` 无法返回文件内容，Shell 宿主的核心用例失效 |

#### C6.3 候选方案

##### 方案 C6-1：增加 `Bytes` / `Opaque` 值变体

可直接替换 `§三` 的 `value` 产生式：

```ebnf
value := STRING | NUMBER | Bytes | Opaque | $变量 | .字段
```

补一句规范性说明：

> `Bytes` 是不可按文本格式化/拼接的字节序列；`Opaque` 是宿主私有句柄。二者不可进入 `STRING` 操作；展示态遇到时报 `cannot_format`（或按宿主提供的占位符输出）；`//map` 值类映射仍只产 `STRING`。

后果：

- **示例改动**：1 处新增（二进制 read/write）；规则文本 4 处（`§三` `value`、`§4.16`、`§4.17`、`§五`）。
- **影响阶段**：phase 5（展示态拒绝/占位）、phase 6（值模型）、phase 10/11、phase 12。
- **新歧义**：`Bytes` 与 `STRING` 在 `[ok]` 的 `$` 上如何区分；`each` 是否把 `Bytes` 当单元素（应明确）。
- **可逆性**：可逆性中等；撤回要改运行时值类型与展示规则，已返回 `Bytes` 的宿主适配器要改。

##### 方案 C6-2：只允许文本，二进制由宿主编码为 base64 `STRING`

可直接替换 `§4.17` 的规则文本：

> RILL 值只有 `STRING` / `NUMBER` / 数组 / 对象 / `null` / `bool`。二进制与流不进 DSL：宿主必须编码为 `STRING`（推荐 `data:` 或 base64 前缀），脚本按文本处理；解码由动词负责。

```text
<read> "logo.png" -> $b64
<write> "copy.png" [with] $b64     // $b64 是 base64 STRING，编解码由宿主负责
```

后果：

- **示例改动**：0 处；规则文本 2 处（`§4.17`、`§五`）。
- **影响阶段**：phase 6（不做新值）、phase 10（编码/解码）、phase 12。
- **新歧义**：base64 字符串与普通字符串无法区分；体积与内存开销翻倍。
- **可逆性**：可逆，但已按 base64 写的脚本要迁移。

##### 方案 C6-3：增加惰性 `Stream`

可直接替换 `§三` 的 `value` 产生式：

```ebnf
value := STRING | NUMBER | Bytes | Stream | $变量 | .字段
```

补一句规范性说明：

> `Stream` 是惰性字节流，只能被声明 `stream` 能力的动词消费；`|>` 可传 `Stream` 不物化；`[ok]`/`[error]` 的 `$` 可为 `Stream`；展示态不可格式化。

后果：

- **示例改动**：1–2 处新增（流式读写）；规则文本 4–5 处（`§三`、`§4.6`、`§4.16`、`§4.17`、`§五`）。
- **影响阶段**：phase 5、phase 6、phase 7、phase 8、phase 10/11、phase 12。
- **新歧义**：`Stream` 的生命周期/关闭语义、并行分支共享、`[ok]` 的 `$` 被读取两次怎么办，都要补规则。
- **可逆性**：可逆性低；撤回要改运行时核心与宿主适配器。

#### C6.4 支持两边的最强理由

**支持 C6-1 / C6-3 的最强理由：**

Shell 的文件、进程输出、stdin 天然是字节/流；强制 base64 会让所有二进制操作变成两倍体积加编解码，`<read> png |> <write>` 这类最基本脚本失真。phase 6 预留 `Bytes`/`Opaque` 的成本低，后补会改运行时核心；`Stream` 则进一步避免大文件整块物化。

**支持 C6-2 的最强理由：**

0.1.0 的值模型、展示/压缩规则都是文本的；引入 `Bytes`/`Stream` 会让 `//map`、展示态、`[ok]` 的 `$` 都必须回答“二进制怎么显示”，而这些是规范里最不稳定的部分。base64 `STRING` 用现有类型就能表达，不需要改 AST，也不需要新增格式化分支。

#### C6.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`Bytes` 就是 `STRING` 的别名。” | 若选 C6-1/C6-3 则不是；它不能参与文本拼接/映射。 | 先看选定方案；文本与字节是两种值。 |
| “二进制可以放进 `//map` 的长词。” | 长词到行尾、按文本处理。 | 二进制只能来自宿主值，不能写进映射表。 |
| “`Stream` 会自动关闭。” | 规范未定义生命周期。 | C6-3 必须补关闭/消费规则，否则泄漏。 |

### C7：`parallel` 的调度语义未定义

#### C7.1 当前规则（正文原话）

`§4.14`：

> `parallel` 块内一行一句，每句可以是复杂语法。

> 可用外部变量；块内定义的新变量块外不可见；禁止分支写外部变量。

> `[results]` 只用于 `parallel` 块级，全部完成后触发一次；`$` = 按源序的结果数组，长度 = 分支数。

`§4.7`：

> `parallel` 分支禁止写外部变量——共享访问通过动词封装，线程安全由底层保证。

#### C7.2 为什么卡住

最短输入：

```rill
parallel {
    <run> "sleep" "10"
    <run> "echo" "x"
} [results] { <send> $ [to] user }
```

规范只说“全部完成后触发一次”，没有说分支是否真的并发、是否同时启动、失败是否取消其他分支、并发度由谁控制。两种读法：

| 读法 | 结果 |
| --- | --- |
| 逻辑并行，调度归宿主 | 脚本无法知道两个分支会不会同时跑；同一脚本在不同宿主耗时不同 |
| 顺序执行 | `parallel` 名不副实，但仍能保证结果与 golden 稳定 |

#### C7.3 候选方案

##### 方案 C7-1：只定义逻辑并行

可直接替换 `§4.14` 的规则文本：

> `parallel` 只定义逻辑并行：分支之间不保证启动顺序、不保证同时执行、不保证完成顺序；`[results]` 在全部分支结束后按源序给出数组。是否真并发、并发度、超时与取消由 HostCapabilities 决定；DSL 不提供并发控制语法。

```rill
parallel {
    <read> a.yml
    <read> b.yml
} [results] { <send> "done" [to] user }   // 只保证结果按源序
```

后果：

- **示例改动**：0 处；规则文本 2 处（`§4.14`、`§五`）。
- **影响阶段**：phase 9（parallel 求值）、phase 10/11（调度）、phase 12。
- **新歧义**：不新增；明确“不保证”后，时序不可断言，golden 只能断言结果数组。
- **可逆性**：可逆，纯语义澄清。

##### 方案 C7-2：并发度语法

可直接替换 `§三` 与 `§4.14` 的规则文本：

```ebnf
parallel_clause := "parallel" [ "(" NUMBER ")" ] "{" branch* "}"
                   [ "[results]" block ] [ "|>" simple_stmt ]
```

补一句规范性说明：

> 括号内为最大并发度，缺省由 HostProfile 决定；`parallel(1)` 语义上等价于顺序执行。

示例：

```rill
parallel(4) {
    <read> a.yml
    <read> b.yml
}
```

后果：

- **示例改动**：1 处新增；规则文本 3 处（`§三`、`§4.14`、`§五`）。
- **影响阶段**：phase 3（`parallel_clause` 分支）、phase 9、phase 10/11、phase 12。
- **新歧义**：并发度是上限还是精确值；超限时排队还是报错。
- **可逆性**：可逆，删括号分支即可。

##### 方案 C7-3：语义顺序、实现可并行

可直接替换 `§4.14` 的规则文本：

> `parallel` 的语义等价于按书写顺序依次执行各分支；宿主可以并行执行，但必须保证可观察结果与顺序执行一致（结果数组仍按源序）。任何依赖共享副作用的脚本不得依赖实际并发。

```rill
parallel {
    <read> a.yml
    <read> b.yml
}   // 语义等价顺序执行
```

后果：

- **示例改动**：0 处；规则文本 2 处。
- **影响阶段**：phase 9、phase 10/11、phase 12。
- **新歧义**：“可观察等价”对进程副作用不可判定（两个 `sleep` 并行与顺序的耗时不同）。
- **可逆性**：可逆，改回“不保证顺序”即可。

#### C7.4 支持两边的最强理由

**支持 C7-1 / C7-2 的最强理由：**

`parallel` 的价值是让宿主决定并发（Agent 限流、Shell 进程池），语言层只保证结果按源序；写死调度会把宿主策略塞进语义。C7-2 再给脚本一个显式上限，仍不规定线程模型，适合 Shell 宿主控制进程数。

**支持 C7-3 的最强理由：**

没有顺序保证的语言结构会让脚本不可测试；把 `parallel` 定义为“语义顺序、实现可并行”，能让 golden 稳定，同时不禁止宿主优化。代价是“并行”名不副实，且真实并行副作用无法用语义等价覆盖。

#### C7.5 读者会在哪里读错

| 典型误读原文 | 为什么错 | 正确读法 |
| --- | --- | --- |
| “`parallel` 保证同时开始。” | C7-1 明确不保证；C7-2 只给上限。 | 只保证逻辑并行与结果数组，时序由宿主决定。 |
| “`[results]` 按完成顺序。” | 永远按源序。 | 结果数组顺序 = 分支书写顺序。 |
| “分支失败会取消其他分支。” | 规范未定义取消。 | C7-1/C7-2 需宿主决定；C7-3 顺序执行不存在取消。 |
