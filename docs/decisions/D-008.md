## 判决

`upheld`（C 方案；拒绝 A/B/D/E）。

1. 运行时值 = `(payload, meta)`；`payload` ∈ `null/bool/number/string/json_object/json_array`；`meta = { truncated: bool, original_size: int }`。
2. 工具边界：handler 与工具参数只拿 `payload`；管道、实参、emit payload 都取 `payload`。
3. 伪字段优先：`x.truncated`/`x.original_size` 先读 `meta`，再读 `payload` 的同名字段。
4. 逃逸：读 JSON 自带字段用 `get "truncated" x`（普通工具调用，不新增语法）。
5. 传播：`let`、管道、`into`/`$`、`fn` 返回、`|?` 胜出分支都携带 `(payload, meta)`。
6. 粘性：`truncated = 本次截断 || 任一输入 truncated`；`original_size` 若本次截断取切前字节数，否则取任一截断输入的最大值，再否则取本值序列化字节数。
7. 单位：UTF-8 字节，与 `ExecLimits.max_output_bytes` 同口径。
8. 内联读元数据必须分组：`(read "big").truncated`；`read "big".truncated` 是 `read("big".truncated)`。
9. `ToolResult` 增 `value_json`/`truncated`/`original_size`；不引入 `.value` 字段，表达式本身就是值。

## 生效范围

下一版规范 §4 R5、§6.1 `ToolResult`、§10 字段访问映射；M2/M3。不含截断控制语法（用户已否 `limit N`）。

## 理由

选 C 的首要依据是判据 6：用户更正已定 DSL 层规定通用元数据且字段访问可读 `truncated`；E 把元数据完全交给各工具 payload，DSL 不再规定形状，等于撤回该更正。其次判据 1：A/B 让记录进入工具边界或迫使解释器自动拆包（第四条隐式规则），违反 v0.1 §1 原则 3；C 的侧车对工具边界零影响。反证席对 C 的两点攻击均可闭合：JSON 同名冲突用“伪字段优先 + `get` 逃逸”给出唯一读法，且逃逸不需要专用操作符；B 的形状依赖 callee 并经 fn/管道泄漏，反证席自己已给出反例。D 被两席共同否掉（形状随数据变）。粘性规则针对可证明的假阴性：`read 截断 -> grep` 若把 `truncated` 洗白为 false，agent 会误判“没有匹配”。

## 失效条件

- 用户明确要求 `truncated` 只描述本次调用 → 重开粘性规则，另设假阴性告警。
- 真实脚本中业务 JSON 的 `truncated` 读取频率高于元数据读取 → 重开逃逸语法（可能引入 `meta` 前缀）。
