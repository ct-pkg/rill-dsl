## 判决

`upheld`（采纳主张席 T，并吸收反证席的可捕获集与可观测项）。

```
expr          := pipe_expr
pipe_expr     := fallback_expr ("|>" fallback_expr)*
fallback_expr := or_expr ("|?" or_expr)*      # 左结合
```

1. `|?` **高于** `|>`：`a |> f b |? g c` = `a |> (f b |? g c)`；`read "p" |? read "f" |> json_parse` = `(read "p" |? read "f") |> json_parse`。
2. 链的最左操作数必须是单个 call（工具或 `fn`，按 D-001 同一节点），加载期检查，链式时只看最左；分组管道 `(f a |> b) |? c` 报错并提示用 `fn` 包裹。
3. 失败单元 = 该 call 的整次求值（含实参求值失败）；左侧更早的管道阶段失败不由它捕获。
4. 右侧独立求值，不接收左侧管道值；右侧可以是任意 `expr`；`|?` 允许出现在 emit payload 的值位（值位就是 `expr`），header 仍无表达式。~~`|?` 不出现在 emit payload 与 header~~（前半句已按本轮裁定收回：不为 payload 字面量再造一条文法例外）。
5. 可捕获：`not_found | invalid_input | transient | type | for_not_array | condition_not_bool`；不可捕获：`denied | constraint | limit | internal | approval_required | approval_denied | approval_stale | approval_reused | revoked | script_changed | dup_key | emit_schema | unconstrained_arg`，遇到即按 R4 中止块。`null` 是值，不是失败；工具失败由 `error_kind` 表达；加载期错误不参与 `|?`。
6. `$` 注入：显式参数（书写序）→ 管道值 → 隐式 `$`；仅当显式+管道参数个数 n < 固定位置形参 m 且工具声明 `accepts_context` 时注入；变长/未知 schema 不注入，要求显式 `$`；`|?` 两侧各自独立计算。
7. 内核可观测：`DslResult.degraded`（0/1）与 `error_kind`，使“全部走兜底”与“全部正常”可区分；MVP 不向脚本暴露错误值。

## 生效范围

下一版规范 §3.3、§4 R2/R3、§6.2；M3 解释器与 golden。不含块级恢复（D-010 明确不做）。

## 理由

判据 2 是决定性的：按“低于 `|>`”，`read "primary" |? read "fallback" |> parse` 在 primary 成功时不执行 `parse`，成功路径反而少跑一步，且不报错；这是语法直接决定的求值轨迹，不是风格问题。因此改判“高于”。反方“整条链兜底更符合直觉”不成立：`fn load() { ... }` + `load |? fallback` 已能表达粗粒度兜底，不需要牺牲管道连续性。判据 3 上，若 `|?` 捕获 `denied`/`limit`，越权尝试会被静默改写成合法读取且脚本成功退出，审计看不到越权，故必须显式排除。判据 4 上，“总是追加 `$`”会与 R2 的管道追加叠加成 3 参对 2 参 schema 的错位，按形参位注入是唯一能同时容纳 R2/R3 的规则。

## 失效条件

- 真实语料中 `(a |> b) |? c` 高频到必须支持整链兜底 → 重开 B2-1，评估自动改写成 `fn`；不得直接改成“低于 `|>`”。
- 工具 schema 普遍无固定 arity，导致注入规则退化 → 重开判据 4，可能改为强制显式 `$`。
