## 争点

示例 3/5 需要把字符串与数字拼成一行输出，示例 4/5 需要数组长度。v0.1 与 D-002..D-015 都没有定义 `+` 的非数值行为，也没有定义 `.length` 挂在哪些值上。

## 判决

`upheld`。两条值层规则：

1. `+`：
   - `number + number` → 数值相加；
   - `string` 与任意标量（`string`/`number`/`bool`/`null`）→ 字符串拼接，**任一侧**为 `string` 即可；`null` 渲染为 `"null"`，其余标量按规范文本（`true`/`false`/无多余零的数字）；
   - `json_array + json_array` → 连接；
   - 其他组合 → 运行时 `type`。
2. `.length`：
   - 只挂在 `json_array` 上，返回元素个数（`number`）；
   - `json_object`、`string`、`null` 及其他值访问 `.length` → `null`（与缺字段一致，不报错）；
   - `x.length` 是普通后缀字段访问，不是语法特例；`$.length` 只在 `$` 持有数组时成立。

## 生效范围

[03 §1](../spec/dsl/03-semantics.md)、[03 §8](../spec/dsl/03-semantics.md)、[08 §4/§5](../spec/dsl/08-examples.md)、[S-024](../spec/S-024-value-concat-length.md)。不含工具侧格式化（如 `join`/`to_string`）。

## 理由

示例必须有最小可运行的拼接与长度读取；不引入数组字面量，长度就只能内建；不引入格式化工具，拼接就只能由 `+` 承担。反方“拼接等于隐式转换”不成立：`==` 的严格性用于判定相等，拼接用于生成文本，两者目的不同；把拼接限制为“至少一侧是 string”已经把隐式转换收窄到显式文本场景，且 `number + string` 与 `string + number` 都按字符串拼接，规则唯一。只把 `.length` 挂在数组上，是因为对象已有键访问、字符串长度可由工具取，给三类值都定义 `length` 会制造“`{}.length` 是 0 还是 null”的第二套歧义。

## 失效条件

- M3 发现把 `null` 拼成 `"null"` 造成下游误判 → 改为 `E_TYPE` 并要求工具 `to_string`，同时提升本条为破坏性变更。
- 真实脚本大量对 `string` 取 `.length` → 单独评估是否给 `string` 定义长度，不得顺手扩展。
