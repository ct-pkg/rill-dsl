## 争点

现行 RILL 0.1.1 的函数是“名字 + 模板”：定义写 `@ "announce" <send> $who [to] user {}`，调用写 `@ "announce" 'RILL'`。用户的判断是 `@ "announce"` 这一层名字属于传统语言的“函数名思想钢印”——在 RILL 已有的 SVO 形状语言里，函数本可以用形状区分，而不必再借一层字符串名字。

争点是：去掉名字之后，函数靠什么被唯一标识与选中；同名冲突、调用形态、可选参数这些原本由名字兜住的问题怎么收。

## 判决

`upheld`。函数**不带名字**：`@` 之后直接写一个 `verb_call` 形状。`@ "announce" $who?world <send> $who (friendly, with:smile) [to] $whom?user {}` 去掉名字后即

```text
@ $who?world <send> $who (friendly, with:smile) [to] $whom?user { ... }
```

`@` 保留，语义变为“在函数表里按形状查定义”，与直接 `<send>` 查工具注册表区分开。

### 1. 签名构成

签名 = 一份从模板机械导出的**形状键**，只由下列成分构成：

| 成分 | 是否进签名 | 说明 |
| --- | --- | --- |
| 动词词面 | 进 | 精确、大小写敏感；函数表不查映射表，`<send>` ≠ `<Send>` |
| 主语位 | 进（仅身份） | 区分“无主语”“参数位”“常量位”；`$who?world` 是可选参数位，见第 4 条 |
| 宾语 / 介宾宾语的位身份 | 进 | 每个位是参数位（`$变量`）、常量位（引号/数字/裸词）还是缺失；参数位的**个数**与**出现位置**进签名 |
| 常量位的值 | 进 | 按值的字符串形态比较，`"ok"`、`'ok'`、`ok` 视为同一个值。这是唯一进入签名的“值”，否则模板里的常量无法被强制 |
| 状语名称 | 进 | `(friendly, with:smile)` → `{friendly, with}`；顺序无关、重复不计 |
| 介词名称与顺序 | 进 | `[to]`、`[with]`、`[in]` 等按书写顺序；`[into]/[ok]/[error]/[results]` 是尾随块或结果块，**不**是介宾，不进签名 |
| 模板 `\|>` 之后的段 | 不进 | 只有第一段 `verb_call` 是形状；`\|>` 之后属模板执行步骤 |

明确**不进**签名：参数变量名（`$who` 只是模板内名字）、默认值（`?world`）、尾随块、函数体、注释与空白、展示态空格。主语若写死具体角色名，按“常量位”处理（进签名，按值比较）。

### 2. 形状完全相同：加载期报错，不许静默覆盖

- 同一 `//fn{}` 内两个定义签名相等 → **加载期错误**，指向后一个定义的 span，Hint 给出两份形状与首个定义的行号。
- 禁止“后定义覆盖前定义”，禁止“取第一个”，禁止仅给警告。理由：传统语言靠名字区分重载，名字去掉后**只有形状能区分**；静默覆盖会让“改了没生效”变成无法定位的缺陷，而这类冲突在加载期完全可判。
- 错误码建议 `E-03`（规范 §4.20 表新增一行）；实现侧 `E-LOAD-FN-SHAPE-DUP`。
- 推论：两个定义如果只差默认值（`$a?x` vs `$a?y`）、只差状语的值（`with:smile` vs `with:loud`）、只差参数变量名（`$a` vs `$b`）、只差常量之外的写法，都**是同一个签名**，一律报冲突。这是用户方向下的必然结果，不是缺陷。

### 3. 调用点

- 语法：`call_stmt := "@" verb_call trailing_block* [ "|>" simple_stmt ]`。`@` 后不再有 `STRING` 名字。
- 原来的 `@ "announce" 'RILL'` 变成与定义同形的句子，值写在参数位：`@ <send> 'RILL' (friendly, with:smile) [to] user`。
- 同一参数在模板多个位置出现时（如 `$who` 同时在主语与宾语位），调用点**每个位都要写值**，且各次给出的值必须相等；不等则报绑定冲突（建议 `E-06` 或实现码 `E-RUN-FN-BIND-CONFLICT`）。不引入“空位”语法。
- 选型：对调用构造同样的形状键，与函数表求精确相等；**不做最近匹配、不做优先级**。
  - 0 个候选 → 加载期报“未声明的函数形状”（建议 `E-04` / `E-LOAD-FN-SHAPE-UNDECLARED`），Hint 列出同动词的已定义形状；错误串不携带名字。
  - 多个候选 → 报二义（建议 `E-05` / `E-LOAD-FN-SHAPE-AMBIGUOUS`），列出全部候选与其定义行。按第 2 条这不应发生；此错误码只防御宿主注入或热加载合并绕过同一 `//fn{}` 的检查。
- 实参个数：函数表按“参数位个数”绑定；调用省略尾部可选位时用默认值，中间不可跳（沿用现行 §4.18 尾部规则）。

### 4. 可选参数与状语的匹配

- 默认值（`?world`）**不参与**签名匹配：它只决定该参数位可省略，不参与区分。因此仅靠默认值区分的两个定义 = 同形 = 第 2 条的冲突。
- 带默认值的参数位如果位于介宾里（`[to] $whom?user`），调用可整段省略该介宾；该介宾与其位不进“必需形状”，但出现在调用里时仍按位绑定。
- 状语**参与**匹配：名称集合必须相等（顺序无关）；匹配不比较状语的值。调用多一个或少一个状语名 → 不匹配，按第 3 条报未声明形状。

## 生效范围

函数的定义与调用形态；`//fn{}` 内的唯一性检查、调用选型、默认值与状语的匹配口径。不改变动词表、介宾语义、尾随块语义、注册表分工（§五）与错误报告方式。

## 理由

名字在 RILL 里是冗余的：动词、状语、介宾已经把“这个函数干什么”写在了形状上，再叠一个字符串名字，等于让作者同时维护两套标识，而且名字与形状可以不一致（`@ "check" <send> ...`）。去掉名字后，函数的可读性来自句子本身，与工具调用保持同一种读法。

冲突必须显式，是因为名字消失后重载不再有兜底：两个同形定义在语义上无法区分，任何一个被选中都是猜。加载期报错把成本放在写脚本的人身上一次，而不是放在读日志的人身上每次。

保留 `@` 而不是让函数调用与工具调用同形，是因为两者查的是两张表：`<send>` 走 VerbRegistry（工具），`@ <send>` 走脚本内的函数表。没有 `@` 就无法在加载期机械决定该查哪张表，也违反 §五“两个宿主得到同一 AST，合法性差异在加载期体现”。

反方“名字是检索锚点”在本项目说得通但不成立：现行错误文案本来就带行号与形状可读文本；LLM 生成代码时依赖的是当前动词表与形状，而不是历史函数名。

## 失效条件

- 若 Phase 实测显示同形冲突在真实脚本里高频出现（>10% 的脚本需要改写），说明形状的区分度不足，应重新评估“是否给形状加可选标签”，而不是恢复字符串名字。
- 若 P-025 裁定类型前缀参与签名，签名键需递增版本并在 §判决 1 的表里补一行。
- 若宿主需要跨脚本共享函数，本条“同一 `//fn{}` 内唯一”的边界需扩展为“合并后唯一”，并同步第 3 条的二义错误。
