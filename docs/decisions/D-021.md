## 争点

RILL 的长期产品形态是什么；当前只做脚本执行器与最小 CLI，是否意味着交互式终端、子命令体系、管道组合能力不在设计考虑之内。

| 2 | 设计不得因当前范围小而排除终态能力 | 本条方向；09 §1 原则 3（每里程碑可运行样例，不封闭后续形态） | 满足 |

## 判决

`upheld`。RILL 的演进目标是 **rillShell**：具备完整 CLI 能力的产品形态——子命令体系、管道组合、脚本执行，且可同时被交互式 shell 与 Agent 内核调用。

- **当前阶段**：脚本执行器 + 最小 CLI。这是范围，不是终态。
- **暂缓而非砍掉**：交互式终端 / REPL 是推迟，不得因当前范围小而在文法、接口、错误模型上做出排除它们的决定。凡出现“为了当前简单而永久封死”的取舍，必须显式登记为偏离或另立决策。
- **产品名与入口名**：当前入口 `ct/bin/rill`；演进目标名 `rillShell`。二者是否改名、是否合并为同一二进制，**本条不裁**，登记为 [P-024](../spec/PENDING.md)。
- **对本轮实现的约束**：不改任何实现或规范正文的行为条款；本条只定方向。

`no-test` 理由：纯文档记录，不改变任何可执行行为，无可红可绿的断言。

## 生效范围

产品方向与后续设计的取舍边界。适用于此后所有 phase 的范围裁定；不改变 09 里程碑的当前排序，也不新增里程碑。

## 理由

若只按“当前是单文件脚本执行器”来裁设计，很容易顺手把入口固定为一次性执行、把参数模型固定为单脚本调用，等到要做子命令与管道时只能推翻重来。把终态写清楚，可以让当前每个取舍多问一句“这一步会不会挡住 rillShell”。反过来，方向写进决策记录不等于承诺时间点：本条只约束“不得做窄”，不承诺 REPL 何时实现。

## 失效条件

- 用户改判产品形态（例如放弃 CLI 方向、或改为库形态）时，本条由新决策记录取代，并在 [decisions/README](README.md) 标 `superseded`。
- P-024 裁定后，若更名为 `rill` 之外的名称，需同步入口路径与 09 的样例命令；本条其余内容不变。
