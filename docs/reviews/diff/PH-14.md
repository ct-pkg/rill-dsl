## 8. `ct build` 多单元：本相未采用，阻塞项如下

本相沿用 PH-13 的 `ctc` 单文件构建（卡片 §2 的交付物也是 `ct/rill_ct.ct`）。按指令尝试
`~/.local/bin/ct build ct/rill_ct.ct` 时，在源码层面撞到 4 项 CT 工具链限制，均以最小
复现确认：

| # | 限制 | 最小复现 / 命令 | 退出码 / 现象 | 需要的 CT 能力 |
| --- | --- | --- | --- | --- |
| 1 | 前向 `typedef` 不被接受 | `typedef struct JVal JVal;`（本文件 L115） | `ct build` → `unexpected token`，rc=1 | 接受 `typedef struct X X;`，或文档化“必须带定义体” |
| 2 | `impl` 块尾 `;` 不被接受 | `impl Emitter for StdoutEmitter { ... };`（本文件 L277） | `ct build` → `expected a type (tok ';')`，rc=1 | 与 C 一致地接受 `};`，或给出明确诊断 |
| 3 | 反斜杠续行的 `#define` 不被支持 | `#define f(x) \` + 次行 | `ct build` 把续行当独立语句 → `unexpected token`，rc=1 | 支持多行宏，或明确报错 |
| 4 | 单行宏超过约 159 字符被静默截断 | 505 字符的 `#define is_kw(x) (...)` | 生成 C 只保留前 159 字符，随后 `cc` 报 `expected expression`，rc=1 | 修复发射端定长缓冲（应为无上限或明确报错） |

本文件现有 64 处宏续行、11 个宏超过 159 字符（`is_keyword`、`ast_*`、`p_is_*`、
`p_reject_results` 等）。要迁到 `ct build`，必须先把这些宏改写成短宏或函数，再谈多单元
拆分；这会改动本相范围外的词法/JSON 构造代码，且可能影响已验证的 token 层。
**未做规避式改写，也未把这一项写成通过。**

另有两项 PH-13 已记录的 CT 缺陷会影响后续多单元组织：导出头里 `pub struct` 内嵌
`Map<K, 用户 struct>` 生成不完整类型（PH-13 closeout §6），以及指针变量上的 `.` 方法调用
发射 `S_f(&p)`（传 `S**`）。
