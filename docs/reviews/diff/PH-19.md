## 3. E-1：12 个 Shell fixture 逐例

`--sut` 跑的是同一份 `expect.json` 断言（exit / ok / value / value_contains /

| fixture | profile | exit | 关键观测 |
| --- | --- | --- | --- |
| `env-get-ok` | min | 0 | `value="8080"` |
| `env-get-missing` | min | 0 | `[error]` 捕获后 `value` 含 `E-HOST-ENV-MISSING`，stderr 含变量名 |
| `fs-read-ok` | min | 0 | `value="port: 8080\n"` |
| `fs-read-missing` | min | 0 | `value`/stderr 含 `E-HOST-FS-READ` |
| `fs-write-ok` | full | 0 | `value="out.txt"`，`out.txt` 内容为 `copied\n` |
| `fs-write-denied` | min | 2 | 诊断 `E-HOST-CAPABILITY-DENIED`，message 含 `fs.write`；`out.txt` 不存在 |
| `process-run-ok` | full | 0 | `value="hi\n"`，`host_meta.process.code=0` |
| `process-run-fail` | full | 0 | `[error]` 捕获 `E-HOST-PROCESS-EXIT: 进程退出码 3` |
| `stdio-send-ok` | min | 0 | `value="hello"`，stderr 为 `hello\n` |

## 4. E-2：ProcessResult 三字段与 stdin 两种形态

`host_meta.process` 与 Python `ProcessResult.as_meta()` 同形：
`{"argv", "code", "stdout", "stderr", "timed_out"}`。覆盖：

- `code`：`process-run-ok` 的 0、`exit-fail` 的 5、`process-run-fail` 的 3；
- `stdout`：`process-run-ok` 的 `hi\n` 同时是 `value`；
- `stderr`：定向 `process-stderr`（进程退出 0、stderr 写 `e`），两侧
  `value=""`、`host_meta.process.stderr="e"`。

stdin 文本与二进制各 1 例（定向用例，两侧逐字段相等）：

| 用例 | 输入 | 观测 |
| --- | --- | --- |
| `text-run` | `<read> text.txt \|> <run> "cat"` | `value="hello\n"` |
| `bytes-run` | 同一个管道，输入文件是 `ff fe 80 00 41` | `value={"$bytes":"//6AAEE="}`，`host_meta.process.stdout` 同值 |
| `bytes-read` | `<read> bin.dat` | 非法 UTF-8 不替换，直接 `{"$bytes": ...}` |
| `bytes-truthy` | `if $b { break "yes" } else { break "no" }` | `value="yes"` |

`Bytes` 在 CT 侧是新值形态 `J_BYTES`，写出为 `{"$bytes": <base64>}`；比较、拼接、
truthy 均按 Python 对象语义处理（默认 truthy）。

## 5. E-3：退出码逐例

规则与 Python `CLI.cmd_run` 一致：

- 有 `--host-profile` / 默认 Shell 策略时，`code = policy.exit_code(outcome.ok)`，
  即 `exit_codes.ok` / `exit_codes.unhandled`（本相 fixture 为 0/1）；
- 能力拒绝（`CapabilityDenied`）不进 `ok=false`，而是 run 诊断、退出 2；
- 测试传输（`--fakes`）保持 0/1，不读能力清单。

12 例的 exit 断言见 §3；其中 2 例为诊断退出 2、1 例为未处理失败退出 1。

## 8. E-6：能力派发只用函数指针表

`ct/src/host/host.h.ct` 的 `HostOps` 是 C 函数指针表：

## 10. `str.isalnum()` 与非 ASCII 词边界：结案

PH-18 §8 把这条登记为悬案。本相给出结论：**CT 的行为是对的，Python 参考实现
在这一点上有候选缺陷；登记为已知偏差，判据锚点如下。**

判据锚点（`docs/RILL-0.1.0.md`）：

- §4.16「双向可逆」：压缩 → 展示必须保持「去空白后的 token 序列」；展示 → 压缩
  同样必须保持 token 序列。
- §1 定位：「零冗余」的前提是「符号即边界」——只有符号在场时，空白才可以去掉。

探针（`a —b`，`—` 是非 ASCII 标点，不是字母数字）：

```console
$ python3 -m rill fmt --compress p.rill
a—b
$ ./ct/bin/rill_ct fmt --compress p.rill
a —b

$ python3 -m rill tokenize p.rill
[('BARE', 'a'), ('BARE', '—b'), ('NEWLINE', '\n'), ('EOF', '')]
$ python3 -m rill tokenize py.out        # 压缩结果
[('BARE', 'a—b'), ('NEWLINE', '\n'), ('EOF', '')]
$ ./ct/bin/rill_ct tokenize ct.out       # 压缩结果
[('BARE', 'a'), ('BARE', '—b'), ('NEWLINE', '\n'), ('EOF', '')]
```

Python 的去空格把两个 `BARE` 并成了一个，token 序列不守恒，违反 §4.16；CT 多留
一个空格，序列守恒。原因在 Python `formatter.py::_merges` 用 `str.isalnum()` 判边界：
`—` 的 `isalnum()` 为 False，于是被当成「可去空白的边界」。CT 的
`is_word_byte` 把所有非 ASCII 字节视为词内容，宁可少压缩也不改变切分。

结论与后续：

- 这不是「CT 与 Python 不一致所以 CT 错了」，而是「Python 的输出不可逆」；
- 不修 Python（卡 §1 禁止改参考实现），不把 CT 改成逐字节对齐 Python 的错误行为；
- 71 例 fmt 语料不含非 ASCII 标点，fmt 层 0 差异不受影响；
- 若未来要修 Python，判据是「compress 输出重新 tokenize 后与原文 token 序列相等」，
  不是「与 CT 字节相同」。0.1.1 backlog 收录。

## 11. E-5（PH-16 Bytes/Opaque）在本相的状态

PH-16 的 E-5 是「`Bytes`/`Opaque` 可透传，不被 truthy 误判；value 单测 + run 用例」。

- **Bytes：已有运行期入口并通过。** `fs.read` 的非法 UTF-8、进程 stdout/stderr、
  stdin 管道都能构造 Bytes；本相用 `bytes-read` / `bytes-run` / `bytes-truthy` 三个
  run 用例覆盖透传与 truthy，两侧 0 差异。没有单独的 value 单测框架（CT 无
  `Value` 类），但同一断言由 host 层定向用例承担。
- **Opaque：仍无入口，不记通过。** Shell 宿主的五类能力没有任何返回值是宿主句柄；
  `read/write/run/env/send` 只产文本、Bytes 或路径。构造不出触发条件的判据按规则
  继续挂着，不挪到别的相，也不写成通过。

因此 PH-16 E-5 只能记「Bytes 部分已验收，Opaque 部分不通过」；这会影响 0.1.0 的
完工判定（见 `docs/reviews/closeout-19.md`）。
