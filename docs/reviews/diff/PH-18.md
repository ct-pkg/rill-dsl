# PH-18 差异报告：格式化与 round-trip（fmt 层）

> 口径见 `tools/diff/diff.py --layer fmt`：同一输入分别跑 Python 参考实现的
> `fmt --compress|--display`（stdout 是**纯文本**，不是 JSON 信封）与 CT 的同名命令，
> 逐字节比较。round-trip 另跑 `compress → display → compress`，把三段文本落盘后
> 用两侧 parser 各解一次 AST（忽略 `span`）。
> 语料固定 71 例：45 个 `case.json.kind ∈ {ast, check, run, warning, host-ast-equal}`
> 的正例 + 26 个 `testdata/0.1.0/host/**` 下同时有 `script.rill` 与 `expect.json` 的脚本。

## 3. E-2：逐字节一致

71 例 × 2 模式逐字节相等，差异为 **0**。换行归一口径：两侧都在读入时把 `\r\n` / `\r`
归一为 `\n`（Python `format_tokens` 的 `_normalize` + 文件文本模式；CT `read_source`），
语料内 0 处触发，无待解释差异。

本层错误路径**不比字节**：两侧词法错误都输出 JSON 诊断，但 Python 的
`json.dumps` 默认带空格、CT 的写出器是紧凑格式（这是 PH-13 起的既有契约，四层只比
`stage/code/line/col` 与退出码）。71 例全是可词法正例，不经过这条路径。

## 4. E-3：长词定向用例

`FMT_DIRECTED` 三个内联源，compress / display 均由两侧逐字节对比：

| 用例 | 长词 | 输入 | CT/Python 一致输出（compress） | （display） |
| --- | --- | --- | --- | --- |
| `space-longword` | `s'my application` | ``<write> `s`.yml`` | ``<write>`s`.yml`` | `<write> 'my application.yml'` |
| `dquote-longword` | `p'a"b` | ``<write> `p` `` | ``<write>`p` `` | `<write> "a\"b"` |
| `squote-longword` | `q'it's here` | ``<write> `q` `` | ``<write>`q` `` | `<write> "it's here"` |

`space` 例同时验证了「展开时相邻 `.yml` 并进同一字符串」：展示态输出
`'my application.yml'`，与 Python 相同；`dquote` 例验证 `"` 走双引号 + `\"` 转义；
`squote` 例验证含 `'` 时改双引号且不额外转义。

## 5. E-4：头写法空格容忍

`//map{` 与 `//map {` 两个内联源，要求两侧输出一致且两种写法输出相同：`header_diffs=0`。
对照：`testdata/0.1.0/positive/comments/not-header`（`//map` 后无 `{` 按注释处理）仍在
ast/token 层 0 差异，两件事互不影响。

## 6. round-trip 口径与结果

对每个输入：

1. 两侧各自 compress、display、再 compress，三段文本逐字节比较（0 差异）；
2. 原文 AST 两侧比较（0 差异）；
3. 三段文本各用两侧 parser 解析，要求与「本实现原文 AST」和「另一实现原文 AST」都相等。

71 例全部通过。这一步强于 `tests/phase12/test_roundtrip.py`（它只比 Python 自己），
因为格式化的中间文本不在 ast 层语料里，必须现场比一次跨实现 AST。

## 7. 口径外差异（已解释，不计入通过）

Python 的合并/边界谓词用 `str.isalnum()`（Unicode 类别 L*/N*），而两套词法器的裸词
规则都把**所有非 ASCII 字节**当作词内容。因此非 ASCII 标点（`—`、`，`、emoji…）
落在词边界时，Python 视为边界、CT 视为词内容。两个探针：

| 输入 | Python | CT |
| --- | --- | --- |
| `a —b`（不构成合法语句，仅 token 流） | `a—b` | `a —b` |
| `//map{s'my application}` + `<write> 'my application—x'` | ``<write>`s`—x`` | `<write>'my application—x'` |

第二例两侧 AST 都仍与原文等价（Python 侧实测 `ast equal: True`）。CT 选择与词法器
对齐：多留一个空格只会少压缩，而去掉空格才可能改变切分，所以 CT 的压缩在可逆性上更
保守。71 例语料不含这类字符，E-2 的 0 差异不受影响。

不把这条改成逐字节对齐的原因：要精确复刻 Python 的 `isalnum` 需要 Unicode 表；用
「非 ASCII 一律不是字母数字」近似会在中文词边界反向出错（`好`/`中` 是字母类）。
卡 §1 也禁止改 Python 参考实现。故登记为口径外差异，留给 PH-5 的格式化完整化再定。

**PH-19 已结案**：见 `docs/reviews/diff/PH-19.md` §10。判据锚点是规范 §4.16
「双向可逆」——压缩输出重新 tokenize 必须与原文 token 序列相等。探针 `a —b` 在
Python 侧变成单个 `BARE 'a—b'`，CT 侧保持两个 `BARE`，因此按判据 CT 正确、
Python 为候选缺陷；登记为已知偏差，不改参考实现、不改本层 0 差异口径。
