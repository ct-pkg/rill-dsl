## 1. 主张席：类型前缀应当进入签名

**立场：进。常量位的值就是作者写下的那串字面原文，前缀字符是其中一部分；剥掉它才是特例。**

理由：

1. **D-022 自己的规则已经蕴含“进”。** D-022 §判决 1 写的是“常量位的值按值的字符串形态比较”。`file:x` 的字符串形态就是 `file:x`，不是 `x`。现行实现先剥再比，等于在“字符串形态”之外加了一条未写进裁定的规则；这条规则没有任何规范依据，只有 PH-22 E-26 的临时约定。

2. **不进会产生真实的误匹配，而且不是理论问题。** 实测：
   - 定义 `@ <read> file:config.txt` 与定义 `@ <read> net:config.txt` 被判同形 → **E-03**，两个语义不同的定义不能共存。
   - 定义 `@ <read> file:config.txt`，调用 `@ <read> net:config.txt` → `classify` 返回 `exact`。更糟的是 F7：模板常量位不绑定参数，调用方写的 `net:config.txt` **被静默丢弃**，函数体照旧用 `file:config.txt`。这是“匹配成功但值没生效”的缺陷，按 D-022 第 2 条的理由（静默覆盖不可定位）正是要避免的。

3. **不进的代价是一个无法正确实现的启发式。** 要判断“哪一段是类型前缀”，要么查 TypeRegistry（宿主相关，见反证席），要么按字面猜（现行做法）。猜的结果已经实测：`http://example.com` 被剥成 `//example.com`，`backup:daily` 被剥成 `daily`。也就是说，“不进”并不能干净地做到“类型无关”，它只是把前缀边界换成了一个更差的边界。

4. **“进”不需要新概念，只需要删代码。** 不需要解析类型、不需要 AST 新字段、不需要 TypeRegistry。把 `_strip_type_prefix` / `shape_strip_type` 删掉，常量位直接取 `Bare.text` / `String.value` / 数字规范形态，就完成了。D-022 L111 担心的“类型前缀在 AST 的落点与拆分时机”在这个方案下**不存在**：签名层根本不拆。

5. **类型前缀改动导致调用点失配，是常量匹配的固有性质，不是本方案的缺陷。** `file:x` 改成 `net:x` 本来就是值变了；常量位本来就钉死字面值。若作者想要“任意路径”，应写参数位 `$p`，而不是写常量再指望类型被忽略。

**主张席底线：`file:x` 与 `net:x` 必须是两个形状；`file:x` 与 `"file:x"` 仍是同一个值（引号透明）。**

## 2. 反证席：反对类型前缀进入签名

**立场：不进。签名是语法形状，类型是宿主解释；把两者混在一起，无论怎么实现都会破界。**

理由：

1. **“类型前缀”在签名层不可定义。** 按 F1/F2，它是宿主加载期按 TypeRegistry 拆分的结果；Shell 根本没有这张表（F3）。那么签名层只有两条路：
   - **查注册表**：同一份脚本在 Agent 下 `file:x` 是 `(file, x)`，在 Shell 下是字面量 `file:x`，两宿主的函数表不同 → 同一脚本一边合法、一边 E-03/E-04。这直接违反 §五“两个宿主得到同一 AST，合法性差异在加载期体现”的初衷：现在连“哪张函数表”都不一致了。
   - **不查注册表、按字面猜**：那 `http://example.com`、`time:30`、`backup:daily` 都会被误拆（已实测）。这不是“类型进签名”，这是“冒号进签名”。

2. **注册表是可变的宿主配置，签名不应被配置追溯修改。** 今天 `backup:daily` 是普通字面量；明天有人在 Agent 的 `types` 里注册 `backup`，同一份脚本里这个常量的形状就从“字面量 `backup:daily`”变成“类型 `backup` + 值 `daily`”，已有定义可能突然 E-03、已有调用可能突然 E-04。**没有任何其他签名字段有这种性质**：动词、位身份、介词、状语名都只由源码决定。让一份策略文件的改动静默改变语言层分派，是把两层的边界打通了。

3. **合法写法会塌成同形。** 一旦承认“按类型拆分”，就必须决定 `String` 要不要拆。现行实现是拆的（F5），于是：
   - `file:x`（裸词、类型前缀）与 `"file:x"`（引号、字面字符串）都变成 `(file, x)` → 同形。两种在语言层地位不同的写法塌成一个形状。
   - 若规定“只拆裸词、不拆字符串”，则 `file:x` 与 `"file:x"` 变成两个形状，而 D-022 明说 `'ok'` / `"ok"` / `ok` 同值——**同一份规范里，冒号一出现，引号就从透明变成有意义**。这是边界被冒号切开，不是被类型切开。

4. **冒号在句内已经有两种含义。** §4.4 状语项写 `名称:值`（`with:smile`），签名取名称、忽略值（[RILL-0.1.0.md L206](file:///Users/samxx/trae-ws/rill-dsl/docs/RILL-0.1.0.md#L206)、[shape.py L66-L77](file:///Users/samxx/trae-ws/rill-dsl/src/rill/shape.py#L66-L77)）；而值位的 `file:x` 被当作 `类型:值`。同一个 `x:y` 表面，靠位置区分两种语义。再往签名里塞“类型”这一层，等于要求签名同时懂位置语法和宿主类型表；这不是签名该做的事。

5. **反证席的替代方案：类型不进签名，且模板常量位不允许写类型前缀。** 想要“固定一个带类型的值”，写成参数位加默认值：`@ <read> $p?file:config.txt`。默认值不进签名（D-022 已定），调用时按位置绑定，值原样交给宿主。这样：
   - 形状只由语法成分构成，不依赖注册表；
   - `file:x` 不会作为常量参与分派，误匹配问题从根上消失；
   - 代价是新增一条加载期错误（模板常量位出现可识别的类型前缀 → 报错并要求改参数位），以及少量语料迁移。

6. **“按字面原文进签名”是半措施。** 它让类型文本影响分派（类型一改，调用失配），却不提供任何类型语义（不能表达“任意 file 路径”）；既拿到了“类型耦合”的成本，又没拿到“类型匹配”的收益。若接受类型文本影响分派，不如直接做完整的注册表方案；若不想耦合，就应走本席的“禁止模板类型常量”。

**反证席底线：签名层不得出现“类型前缀”这个概念；要么常量位禁止类型前缀，要么接受 `file:x` 与 `net:x` 同形并由宿主在执行期区分。**

## 4. 裁定建议（可签字）

**选 B。但把“类型前缀进入签名”改写成更准确的表述：**

> **签名层不引入“类型前缀”概念。常量位按字面原文（`Bare.text` / `String.value` / 数字规范形态）进入签名；前缀字符因属于字面原文而事实上参与签名。不拆分、不查 TypeRegistry、不改 AST。**

这样既满足主张席的核心诉求（`file:x` ≠ `net:x`，不再误匹配），又不落进反证席指出的“签名依赖宿主注册表”的坑：签名层从不判断“这是不是类型”，只比较作者写下的字符串。类型前缀的拆分与校验仍完全留在宿主加载期（F1/F2 不变）。

**附带约束（六条，缺一不算完成）：**

| # | 约束 |
| --- | --- |
| C1 | 签名构造只读 AST；**禁止** import host / policy / TypeRegistry；`shape.py` 与 CT 对应模块不得出现类型名表 |
| C2 | 只影响**字面量常量位**（`Bare` / `String` / `Number`）；参数位、默认值、状语值、尾随块、`\|>` 后段一律不变 |
| C3 | 引号透明：`file:x` 与 `"file:x"` 同值。这是 D-022 字符串形态规则的直接结果，需在 §4.18 写明，避免被当成漏洞 |
| C4 | 类型前缀的校验仍归宿主：Agent 拆、Shell 不拆；同一脚本在两宿主下**函数表相同、运行语义可不同**，这是 §五 的既定边界 |
| C5 | 形状键版本升到 2；版本落点必须可机械核对（见 §7 不确定 1）；所有受影响的 `FnDef.shape` / trace golden 逐条登记 `golden-change:` |
| C6 | 不采纳 C（注册表拆分），也不采纳“禁止模板类型常量”。前者破界，后者禁止一种合法写法并新增错误码，而 B 已用零新错误码解决误匹配 |

**为什么不选 A：** A 不是“类型无关”，是“冒号后缀无关”。`file:x` 与 `net:x` 在 Shell 下就是两个不同的字面值，A 却判同值；这是值比较的缺陷，不是类型语义的取舍。

**为什么不选 C：** C 要实现“类型进签名”，就必须回答“哪张 TypeRegistry 说了算”。Agent 有、Shell 没有（F3），答案只能是“宿主相关”，于是同一脚本的函数表随宿主变化，违反 §五；或者“全局统一表”，那是改宿主模型，不是改签名。

**为什么不选反证席的“禁止模板类型常量”：** 它把一个合法写法变成错误，需要新错误码与迁移，而 B 不需要新增任何错误码就能消除误匹配。反证席对“半措施”的批评成立，但 B 并不是“给类型以语义”，而是“拒绝在签名层识别类型”；这个区别正是它不破界的原因。

## 5. 机械判据（可直接变成加载期断言）

| # | 断言 | 负例/反例 |
| --- | --- | --- |
| M1 | `const_value(Bare("http://a")) == "http://a"`；`const_value(String("a:b")) == "a:b"` | 任何返回值不等于原文即失败 |
| M2 | `shape_of(Bare("a:b"))["object"] == shape_of(String("a:b"))["object"] == {"role":"const","value":"a:b"}` | 两者不等 → 引号透明被破坏 |
